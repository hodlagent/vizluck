# vizluck · Game tab 玩法设计文档

> 状态：已定稿，待实现
> 适用范围：`src/tabs/Game.svelte` 及其下的 `src/game/`
> 相关模块：`src/hex/`（密钥构造与命中流程全部复用）

---

## 0. 一句话概括

**把「搜索」变成「生存」。** 玩家在一个遍布怪物的 3×3 竞技场里躲避、击杀、成长；每一秒存活都在推进密钥流的采样，玩家自身的状态就是密钥材料。

---

## 1. 为什么要做这个

Hex tab 是一个「暴力搜索实验室」：盯着一排字节滚动，看 hash160 刷过去。它把彩票式的等待做得很透明，但玩家除了按 Random / Auto 之外**没有任何介入手段** —— 搜索是个黑箱，玩家是旁观者。

Game tab 是同一件事的另一种讲法。目标不是让搜索变快（不可能），而是：

1. **把等待变成有意义的操作** —— 有决策、有风险、有成长曲线；
2. **产生真正无偏的密钥采样** —— 这正是彩票所需要的；
3. **让「命中」这件事有叙事** —— 命中时玩家是在一场自己打出来的局里撞上的，而不是盯着屏幕等出来的。

### 1.1 必须写在最前面的诚实声明

**这个玩法不会「搜出」puzzle。**

`b ≥ 9`（真实数据集里 `b` 取 9..20）意味着一个 puzzle 的区间至少有 `2^72` 个密钥。任何玩法、任何存活时长、任何操作水平都不可能穷尽它。这一点 Hex tab 的 auto 模式同样成立 —— 它跑一整年也扫不完 puzzle #71 的一个零头。

所以请**不要**把 Game tab 理解成「通过玩来解开 puzzle」，也不要据此去评估它的数值平衡。它是一个**把长期无反馈的等待过程游戏化的外壳**，命中是极小概率的彩票事件，而不是可攻略的目标。

## 2. 核心循环

```
        ┌──────────────────────────────────────────┐
        │                                          │
   击杀怪物 ──► 获得算力 ──► 密钥采样提速 ──► 更快推进 puzzle 空间
        │           │
        │           └──► 获得经验 ──► 升级 ──► 属性成长 ──► 活得更久
        │                                          │
        └────────── 怪物刷新（n 秒后）◄─────────────┘
                        │
                   躲避攻击（走位）
```

一句话：**怪物是搜索的燃料。**

- 躲在角落不打 → 算力衰减到 0 → 扫描速率掉到 2 keys/s，几乎没有推进。
- 冲进中心作战 → 算力拉满 → 扫描 20 keys/s，但也是死得最快的地方。

玩家每一秒都在做这个权衡。**这是整个玩法的支点。**

## 3. 密钥映射

> 对应需求第 2、6 条。这是整个设计的核心，也是唯一需要精确到字节的部分。

### 3.1 字节布局

`b = puzzle.hex_bytes_len`（真实数据集为 9..20）。32 字节私钥的排布沿用 `src/hex/range.ts` 已有的语义：

```
   [ 32-b 个 0x00 填充 ] [ 受 range 限制的字节 ] [ b-1 个自由字节 ]
         恒为 0x00          [start_top, end_top]      0x00 – 0xFF
```

以 puzzle #71（`b = 9`，range `[2^70, 2^71)`）为例：

```
 00 ×23  |  0x40 .. 0x7f  | bb bb bb bb bb bb bb bb
   ↑              ↑                      ↑
 填充，恒为 0   受 range 限制        游戏状态唯一的输出口
```

三个部分的归属：

| 部分 | 字节数 | 取值 | 由谁决定 |
|---|---|---|---|
| 填充 | `32 - b` | 恒 `0x00` | 无（游戏不碰） |
| 受 range 限制的字节 | 1 | `[start_top, end_top]` | `randomTopByte(puzzle)`，复用 hex tab 的实现 |
| **自由字节** | `b - 1` | `0x00 – 0xFF` | **游戏状态** |

`end_top === 0` 的上溢情形由 `src/hex/range.ts` 的 `topByteBounds()` 处理，游戏侧不需要关心。

### 3.2 复用：游戏就是一个「由玩法驱动的 grid」

因为自由字节是全范围的，游戏只需要产出 `b-1` 个字节，然后原样喂给已有的构造函数：

```ts
// src/hex/range.ts —— 与 hex tab group 模式完全同一条路径
puzzleKeyHex(puzzle, randomTopByte(puzzle), gameBaseBytes)
```

**零新代码**：密钥构造、range 校验、私有密钥十六进制格式化全部复用。

这个类比很准确：

| | Hex tab | Game tab |
|---|---|---|
| grid 的格子数 | `b - 1` | `b - 1` |
| 格子由谁驱动 | Random 按钮 / hover 循环 / auto 模式 | 走位 / 战斗 / 升级 |
| 高位字节 | `randomTopByte()` | `randomTopByte()`（同左） |

### 3.3 每个自由字节的取值

```
byte[j] = ( owner(V, j) + diffuse(V, j) ) & 0xFF        j = 0 .. b-2
```

| 分量 | 定义 | 作用 |
|---|---|---|
| `owner(V, j)` | `V[j]`，定长状态向量的第 j 项 | **可读性 + 玩家能动性**。字节 j 有固定归属，HUD 能显示「byte 3 ← player.posX」，玩家的操作直接推动它 |
| `diffuse(V, j)` | `expand(fold(V))` 的第 j 个字节 | **均匀覆盖 + 状态完整性**。把全场状态（含每一只怪物）折叠扩散到所有字节 |

#### 为什么必须混合

**纯直接映射不可行**：`player.dir` 只有 8 个取值。若某个字节直接等于它，那个字节就永远只覆盖 `0..255` 中的 8 个值 —— 浪费掉 96% 的范围。方向、区域编号、怪物原型这类低基数属性都有同样的问题。

**纯扩散又丢掉了可读性**：玩家无法感知自己的操作影响了什么，游戏就退化成一个「有怪物陪伴的随机数生成器」。

叠加之后的数学性质：`owner` 是有界的任意项，`diffuse` 是均匀项，**模 256 下均匀项加任意项仍然是均匀的**。所以 `byte[j]` 的整体分布由 `diffuse` 主导，覆盖率得到保证；同时 `owner` 保留了「哪个属性影响哪个字节」的可读性和玩家的直接操控感。

#### `fold` / `expand` 的具体选择

- `fold`：FNV-1a 32 位，以 **`puzzle 编号`** 为初始种子，逐字节吞掉整个 `V`。
- `expand`：splitmix32 PRNG，用 `fold` 的结果作种子，按需吐出字节。

> ⚠️ **`V` 里不包含 puzzle 编号，但 `fold` 的种子必须异或上它。** 否则切换到另一个 puzzle 时会产出完全相同的密钥串。

### 3.4 状态向量 V（定长，`|V| = 64`）

**定长是关键设计约束。** 怪物数量每时每刻都在变；如果 `V` 长度可变，那么某只怪物一死，它后面所有字节的归属就会整体错位，HUD 上的归属提示会疯狂乱跳，玩家会觉得「字节在乱变」。

因此固定布局，空槽位补 `0`：

```
V[0]       = tick & 0xFF            // 密钥 tick 计数器
V[1]       = player.dir             // 0..7
V[2]       = q(player.posX)
V[3]       = q(player.posY)
V[4]       = q(player.hp / maxHp)
V[5]       = q(player.attackPower)  // 升级会改变它
V[6]       = q(player.moveSpeed)
V[7]       = q(player.attackSpeed)
V[8]       = q(player.attackRange)
V[9]       = q(player.hpSpeed)
V[10]      = q(player.level)
V[11]      = q(hashpower)
V[12]      = region.index           // 玩家所在区域 0..8
V[13]      = q(region.targetCount)  // 该区域的目标怪物数（场景数据）
V[14]      = q(region.respawnSec)   // 该区域的刷新间隔（场景数据）
V[15]      = q(kills)
─────────── 以下 8 只怪物 × 6 项 = 48 ───────────
V[16+6i+0] = m.dir
V[16+6i+1] = q(m.posX)
V[16+6i+2] = q(m.posY)
V[16+6i+3] = q(m.hp / m.maxHp)
V[16+6i+4] = q(dist(player, m))
V[16+6i+5] = m.attacking ? 1 : 0
```

`q()` 是量化到 `0..255` 的整数（位置按竞技场尺寸归一化，比率按百分比，绝对值按各自量程缩放后 clamp）。

#### 怪物窗口 = 8

只取**离玩家最近的 8 只**怪物填入 `V`，排序键为 `(距离, spawnId)` —— 加 `spawnId` 是为了在距离相同时保证**确定性**，否则同一帧内排序结果不稳定，密钥会抖。

这个窗口设计让「靠近怪物」这件事本身改变密钥：**贴脸战斗和躲在角落的采样路径完全不同**，与「怪物是燃料」的核心循环一致。

#### 低基数属性的处理

`player.dir`（8 值）这类属性，即使作为 `owner` 也只贡献 8 个值；它们对密钥的**主要贡献来自 `fold`**（进入种子），`owner` 只是让玩家在 HUD 上看得见它。

## 4. 场景与区域

> 对应需求第 4 条。

场景 `w × h`（= `GAME_WIDTH × GAME_HEIGHT` = 960 × 540）划分为 **3×3 = 9 个区域**，每个区域的**目标怪物数**与**刷新间隔**相互独立。

### 4.1 风险/收益的空间梯度

| 区域 | 位置 | 目标怪物数 | 刷新间隔 | 主要怪物 | 算力产出 |
|---|---|---|---|---|---|
| 4 个角落 | 四角 | 2 | 6.0 s | 游荡者 | 低（安全但饿） |
| 4 个边中 | 四边 | 4 | 4.0 s | 游荡者 / 追猎者 | 中 |
| 1 个中心 | 中央 | 6 | 2.5 s | 重装者 / 追猎者 | 高（富但致命） |

**地图本身就是一个风险旋钮：**

- **角落 = 回血区。** 安全，但算力会衰减到 0，扫描速率掉到 2 keys/s，几乎没有推进。待在这里是「活着但不搜索」。
- **中心 = 收益区。** 密度最高、刷新最快、掉落最好，是唯一能维持高扫描速率的地方 —— 也是死得最快的地方。

于是「走到哪」成为玩家的核心决策，而**移动本身又会直接改变密钥字节**（`player.posX/posY` 在 `V` 里）。空间决策与搜索推进在这里是同一件事。

### 4.2 刷新规则

每只怪物被击杀后，按**它所属区域**的刷新间隔、在**该区域内**的随机位置重生。各区域节奏完全独立 —— 这就是「每个区域的怪物数量和刷新速度是独立的」。

### 4.3 全局难度升级

每存活 **30 秒**，所有区域：目标怪物数 `+1`、刷新间隔 `×0.9`（各有上限/下限封顶）。

这让任何一局最终都会结束 —— 存活时间因此成为一个有意义的分数。没有这个升级，高手可以无限期地待在角落，分数失去区分度。

## 5. 玩家

> 对应需求第 3 条。

| 属性 | 初始值 | 说明 |
|---|---|---|
| `dir` | 由输入决定 | **8 方向**，与需求一致 |
| `moveSpeed` | 160 px/s | 走位速度，躲攻击靠它 |
| `attackSpeed` | 1.5 次/s | **自动攻击**的冷却 |
| `attackPower` | 8 | 每次攻击伤害 |
| `attackRange` | 55 px | 自动攻击的索敌半径 |
| `hp` | 100（上限 100） | 归零即本局结束 |
| `hpSpeed` | 1.0 /s | 脱战 3 秒后开始回血 |
| `posX, posY` | 角落区域中心出生 | 不得越出场景边界 |

### 5.1 为什么攻击是自动的

需求第 1 条规定 UI 只有 2 个控件：**下拉框** 和 **暂停/运行按钮**。没有攻击键的位置。

所以攻击设计为**对 `attackRange` 内最近的怪物自动出手**。这个选择有三个好处：

1. 符合 2 控件的 UI 约束；
2. 玩家只需要专注走位，操作门槛低、反馈直接；
3. `attackPower / attackSpeed / attackRange` 从「按钮」变成**可被感知、可成长的属性** —— 也正好让它们作为密钥材料有意义。

### 5.2 脱战回血

最后一次受伤后 **3 秒**开始按 `hpSpeed` 回复。

这是「退回角落」这个决策的收益来源，让撤退不等于纯损失。它和 4.1 的区域梯度配合，形成完整节奏：**中心冒险 → 受伤 → 撤回角落回血 → 再冲进去**。

## 6. 怪物

> 对应需求第 5 条。

三种原型，字段全部来自需求 5：

| 原型 | `m_hp` | `m_moveSpeed` | `m_attackPower` | `m_attackSpeed` | `m_attackRange` | `m_range`（感知） | 算力掉落 | 经验 |
|---|---|---|---|---|---|---|---|---|
| **游荡者** | 20 | 50 | 5 | 0.8 /s | 22 px | 140 px | +1 | 10 |
| **追猎者** | 35 | 120 | 8 | 1.2 /s | 26 px | 260 px | +2 | 20 |
| **重装者** | 90 | 40 | 18 | 0.6 /s | 34 px | 110 px | +4 | 40 |

`m_dir` 同样是 8 方向，始终朝向自己的移动方向 / 朝向目标。

### 6.1 行为

```
if dist(player) <= m_range and player 在自己 home 区域内:   # 锁定
    m_dir = 朝向玩家（8 方向取整）
    朝玩家移动（移动范围夹在自己的 home 区域内）
    if dist(player) <= m_attackRange and 攻击冷却就绪:
        对玩家造成 m_attackPower 伤害
        攻击冷却 = 1 / m_attackSpeed
else:                                   # 未感知 / 玩家已离开本区域
    在自己的 home 区域内随机游荡
```

**感知范围 `m_range` 是设计里最有意思的一个字段。**

- **重装者**感知只有 110 px，但攻击力 18（游荡者的 3.6 倍）。它「看不见」远处的你 —— **只要不进它的圈就绝对安全**。
- **追猎者**感知 260 px，在整个区域内几乎全程锁定，是强制位移压力 —— 逼你在边中/中心区域持续移动，而不是站桩输出。

于是走位从「跑开」升级为**绕开视野圈**：玩家需要读怪物的感知半径，规划一条不触发高危怪物的路线。这是躲避玩法的技术深度所在。

### 6.2 追击边界：怪物被拴在自己的区域内

**怪物永远不会离开它的 home 区域** —— 游荡不离开，追击也不离开（§6.1 的两个条件）。

这不是细节，是让 §4 的区域梯度**成立**的前提。反例很直接：追猎者的 `m_range` 是 260 px，而边中区域只有 320 × 180 px —— 一只待在边中区域靠内侧的追猎者，能直接「看见」角落区域中心的玩家并一路追进去。若允许跨区追击，**角落这个「安全区」根本不存在**，只是死得慢一点，§4 表格里的风险梯度、§5.2 的脱战回血、乃至需求 4 说的「每个区域独立」全部落空。

于是走位有了两层含义：

1. **区域内**：绕开感知圈（§6.1 的 `m_range` 战术）。
2. **区域间**：跨过边界就是断仇恨 —— 打不过就退回去。

反过来，这条规则也**没有**制造「站在边界外无伤刷怪」的漏洞：玩家的 `attackRange` 只有 55 px，想够到区域内的怪物就必须贴到边界上，而那时怪物的 `m_attackRange`（22–34 px）同样够得到你。贴边蹭怪是要付血价的，只是不至于被一路追杀回角落。

## 7. 战斗

| 方向 | 触发条件 | 节奏 |
|---|---|---|
| 玩家 → 怪物 | 目标在 `attackRange` 内，取**最近**的一只 | 按 `attackSpeed` 冷却 |
| 怪物 → 玩家 | 目标在 `m_attackRange` 内 | 按 `m_attackSpeed` 冷却 |

**躲避是空间性的，不是数值赌博。** 怪物的攻击有冷却窗口：玩家只要在冷却走完之前走出 `m_attackRange`，就不吃这次伤害。这让「躲避怪物的攻击」是一个真实的、可以用走位执行的操作，而不是比拼闪避率。

**死亡**：`hp <= 0` → 本局结束，存活时间定格。

## 8. 成长与资源

### 8.1 算力（hashpower）—— 把击杀和搜索焊在一起

| 项 | 设计 |
|---|---|
| 上限 | 100 |
| 击杀获得 | 游荡者 +1 / 追猎者 +2 / 重装者 +4 |
| 自然衰减 | 3 /s |
| **密钥采样速率** | `2 + 18 × (hashpower / 100)` → **2 ~ 20 keys/s** |

**这是整个玩法的支点。** 躲在角落苟着 = 2 keys/s；在中心持续作战 = 20 keys/s。**扫描速度相差 10 倍。**

玩家「要不要冒险」的权衡，被直接换算成搜索推进的倍率。这也是唯一让「击杀怪物」这件事在搜索层面产生实际收益的机制 —— 否则杀怪只是一个生存手段，与搜索无关。

### 8.2 等级

击杀获得经验（= 掉落 × 10）。升到第 N 级需要 `100 × N` 经验。每次升级：

```
hp +10 · attackPower +1 · moveSpeed +2 · attackSpeed +0.05 · attackRange +1 · hpSpeed +0.1
```

因为**所有属性都在 `V` 向量里**，升级会改变密钥字节 —— 玩家变强这件事本身就在移动采样位置。这是「玩家的状态就是密钥材料」这句话的具体兑现。

## 9. 运行 / 暂停 / 匹配流程

> 对应需求第 1、6 条。

### 9.1 状态机

```
   未选 puzzle ──► IDLE         ▶ 禁用，画布显示「请选择一个 puzzle」
        │ 选择 puzzle
        ▼
   READY ⇄ RUNNING              ▶ / ⏸ 手动切换
        │        │
        │        ├── 切到别的 tab ──► 自动暂停，运行意图复位
        │        │                    切回来保持暂停，必须手动点 ▶
        │        │
        │        └── hp 归零 ──► DEAD，存活时间定格，▶ 可重开
        │
        └── hash160 命中 ──► MATCHED，全部暂停 + 保存私钥
```

### 9.2 三条硬规则

1. **未选 puzzle 不能运行。** 没有 range 就没有字节布局（§3.1），`▶` 直接禁用。
2. **切走 tab 自动暂停。** 复用 `App.svelte` 已有的 `active` prop 协议。注意：`hidden` 属性**不会**触发 `document.visibilitychange`，所以 Phaser 自带的可见性处理在这里是失效的，必须由这条协议接管。
3. **切回来不自动恢复。** 这是与 Hex tab 的**关键差异**：Hex tab 选择继续后台跑（见 `App.svelte` 的注释），Game tab 必须**手动点 ▶ 继续**。实现上，`setActive(false)` 时要顺手把「运行意图」也复位成 `false`，这样切回来按钮就是 ▶。

### 9.3 暂停 = 停止搜索

暂停时**密钥 tick 一并停掉**，不产生任何密钥。游戏与搜索是同一个开关，不存在「暂停着还在后台扫」的状态。

### 9.4 命中流程

每个密钥 tick：

1. `randomTopByte(puzzle)` 取得受 range 限制的字节
2. 游戏状态 → `b-1` 个自由字节（§3.3）
3. `puzzleKeyHex()` → 64 字符私钥 hex
4. 调 **`derive_group([keyHex])`**（`src/hex/api.ts`）
5. 命中 → 暂停 + 落盘 + `MatchBanner` + 标题行上的 ✅

> ⚠️ **必须用 `derive_group`，不能用 `derive_full`。**
> `derive_full`（`src-tauri/src/homepage.rs:618-627`）只做比对，**从不调用 `save_match`**，命中结果不会落盘。
> `derive_group`（`homepage.rs:640-672`）是唯一对「调用方已知私钥」执行持久化的命令，且在命中时自动写入 `{timestamp}.txt`。
> 这也正是 Hex tab group 模式使用的同一个命令。

## 10. UI

### 10.0 顶栏 = 一行

标题行不再是「标题 + 状态」，而是整条顶栏：左边是读数，右边是 §10.1 的两个控件。

```
survive  efc98e13967c0a07…  1KKKK…KKKKK  ❌  running        [ #130 · 17 bytes ▾ ]  [ ⏸ ]
└ 标题 ┘ └─ 私钥非零部分 ─┘ └ 压缩地址 ┘ 命中  状态 ┘        └──── 需求第 1 条的 2 个控件 ────┘
```

控件用 `margin-left: auto` 顶到最右，与左侧读数分开——两者性质不同，一片留白比一个 gap 更能说明这件事。窗口变窄时整行 `flex-wrap` 换行，控件连同状态落到第二行，仍然靠右，不溢出。

左侧读数三项：

- **私钥的非零部分**：`puzzleKeyHex()` 在 range 之上全是 `00` 填充，展示完整 64 字符等于一堵零墙，把本局真正的产出挤到最右边。剥掉填充后剩下的就是玩家正在推动的那一段。点击复制完整 64 字符。
- **压缩地址**：点击复制。命中时转绿（`✅`），未命中为暗色（`❌`）。
- **命中图标**：`address_match`，与 `handleMatch()` 读的是同一个字段。

> 早期版本在底部复用 `AddrInfoPanel` 显示私钥 / xprv / 地址三张卡片。xprv 对本局没有意义（它由私钥唯一决定，不会随玩法变化），三张卡片的信息密度又远低于它占的位置，因此收进标题行。

### 10.1 控件（需求第 1 条：只要 2 个）

```
[ puzzle 下拉框 ▾ ]   [ ▶ / ⏸ ]        ← 位于 §10.0 的顶栏右端
```

- **下拉框**：列出全部 puzzle，显示 `#71 · 9 bytes`。选中后才允许运行。
- **按钮**：`▶` 运行 / `⏸` 暂停。未选 puzzle 时禁用；命中后锁定；死亡后按下 = 重开新局。

### 10.2 HUD（只读）

```
存活 02:47.3   最佳 05:12.8   等级 7   HP 84/170   算力 62   采样 13 keys/s   keys 4,182
```

外加一行**字节归属提示**，把 §3.3 的可读性兑现成玩家看得见的信息：

```
byte2 ← player.posX    byte3 ← player.posY    byte16 ← m[0].dir   …
```

这是「混合式映射」相对于「纯扩散」唯一但关键的回报：玩家能看到自己的操作在推动哪些字节。

字节条会**完整**展示 `b-1` 个自由字节（8–19 个）—— 它就是 Game tab 版的「grid」。归属说明只标前 4 个，避免 b 较大时糊成一片。

### 10.3 画布上的可见性规则

环形感知圈（`m_range`）是核心战术，但场上有约 30 只怪物 —— **全部画出来会织成一张网，反而谁都看不清**。所以：

- **只画玩家可能踏入的那些圈**：`dist(player, monster) ≤ m_range + 60`。60 px 略大于玩家的 `attackRange`（55），于是「看得见的圈」= 「打得着的怪」= 「需要绕的怪」。
- **已锁定的圈更亮**（alpha 0.5 vs 0.22），一眼能分辨「它看见我了」和「我在它边缘」。

地图其余部分因此保持安静，区域色调（角落偏蓝 / 边中偏金 / 中心偏红）才能真正读出来。

### 10.4 操控

- **移动**：WASD / 方向键（8 方向）
- **攻击**：自动（见 §5.1）
