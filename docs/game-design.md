# vizluck · Game tab 玩法设计文档

> 状态：已实现。本文档是**契约** —— `src/game/` 下的代码注释按 §编号引用它，因此**只增不删、不重排编号**。
> 适用范围：`src/tabs/Game.svelte` 及其下的 `src/game/`
> 相关模块：`src/hex/`（密钥构造与命中流程全部复用）

---

## 0. 一句话概括

**把「搜索」变成「生存」。** 玩家在一个遍布怪物的 3×3 竞技场里躲避、击杀、成长；玩家自身的状态**就是**密钥材料，世界的每一次变化都对应一个新密钥 —— 静止的世界不产生密钥。

---

## 1. 为什么要做这个

Hex tab 是一个「暴力搜索实验室」：盯着一排字节滚动，看 hash160 刷过去。它把彩票式的等待做得很透明，但玩家除了按 Random / Auto 之外**没有任何介入手段** —— 搜索是个黑箱，玩家是旁观者。

Game tab 是同一件事的另一种讲法。目标不是让搜索变快（不可能），而是：

1. **把等待变成有意义的操作** —— 有决策、有风险、有成长曲线；
2. **产生真正无偏的密钥采样** —— 这正是彩票所需要的；
3. **让「命中」这件事有叙事** —— 命中时玩家是在一场自己打出来的局里撞上的，而不是盯着屏幕等出来的。

### 1.1 必须写在最前面的诚实声明

**这个玩法不会「搜出」puzzle。**

`b ≥ 9`（真实数据集里 `b` 取 9..20）意味着一个 puzzle 的区间至少有 `2^72` 个密钥。任何玩法、任何存活时长、任何操作水平都不可能穷尽它。这一点 Hex tab 的 auto 模式同样成立 —— 它跑一整年也扫不完 puzzle #71 的一个零头。

所以请**不要**把 Game tab 理解成「通过玩来解开 puzzle」，也不要据此去评估它的数值平衡。它是一个**把长期无反馈的等待过程游戏化的外壳**，命中是极小概率的彩票事件，而不是可攻略的目标。

## 2. 核心循环

```
   击杀怪物 ──► 获得经验 ──► 升级 ──► 生命上限 ×1.05 ──► 容错变高
        │
        └──► 掉落药剂 ──► 走过去捡起 ──► 攻击力/攻速/移速 ×1.05 ──► 杀得更快
                              │                                     │
                              └─────────────────────────────────────┘

   上述每一步都会改写 V（§3.4），而 V 就是密钥。
   换句话说：**世界的每次变化都是一个新密钥。**

   与此同时：怪物按 n 秒刷新（§4.2）并随时间变强
   （§4.3 密度、§4.4 血量），躲避攻击（走位）贯穿始终。
```

一句话：**怪物是搜索的燃料 —— 但烧的是状态，不是速率。**

**杀怪给两样东西，它们的兑现方式完全不同：** 经验直接入账（只要杀就有，且立刻进 `V[10]`），战斗力则要先**走到怪物倒下的地方**把药剂捡起来（§8.3）。所以「打得动 → 杀得快 → 但站得越久越危险」这个循环里，多了一个空间决策：**什么时候离开安全位置去捡收益。**

**密钥推进不是奖励，是已发生事实的记录。** 游戏不发放「扫描速度」这样的资源（§8.1），所以这里没有速率可以权衡：杀怪之所以推动搜索，是因为杀怪改变了世界 —— 经验、击杀数、怪物集合、走位、拾取后的属性 —— 而这些都是 `V` 的组成部分。

## 3. 密钥映射

> 对应需求第 2、6 条。这是整个设计的核心，也是唯一需要精确到字节的部分。

### 3.1 字节布局

`b = puzzle.hex_bytes_len`（真实数据集为 9..20）。32 字节私钥的排布沿用 `src/hex/range.ts` 已有的语义：

```
   [ 32-b 个 0x00 填充 ] [ 受 range 限制的字节 ] [ b-1 个自由字节 ]
         恒为 0x00          [start_top, end_top]      0x00 – 0xFF
```

以 puzzle #71（`b = 9`，range `[2^70, 2^71)`）为例：

```
 00 ×23  |  0x40 .. 0x7f  | bb bb bb bb bb bb bb bb
   ↑              ↑                      ↑
 填充，恒为 0   受 range 限制        游戏状态唯一的输出口
```

三个部分的归属：

| 部分 | 字节数 | 取值 | 由谁决定 |
|---|---|---|---|
| 填充 | `32 - b` | 恒 `0x00` | 无（游戏不碰） |
| 受 range 限制的字节 | 1 | `[start_top, end_top]` | `randomTopByte(puzzle)`，复用 hex tab 的实现 |
| **自由字节** | `b - 1` | `0x00 – 0xFF` | **游戏状态** |

`end_top === 0` 的上溢情形由 `src/hex/range.ts` 的 `topByteBounds()` 处理，游戏侧不需要关心。

### 3.2 复用：游戏就是一个「由玩法驱动的 grid」

因为自由字节是全范围的，游戏只需要产出 `b-1` 个字节，然后原样喂给已有的构造函数：

```ts
// src/hex/range.ts —— 与 hex tab group 模式完全同一条路径
puzzleKeyHex(puzzle, randomTopByte(puzzle), gameBaseBytes)
```

**零新代码**：密钥构造、range 校验、私有密钥十六进制格式化全部复用。

这个类比很准确：

| | Hex tab | Game tab |
|---|---|---|
| grid 的格子数 | `b - 1` | `b - 1` |
| 格子由谁驱动 | Random 按钮 / hover 循环 / auto 模式 | 走位 / 战斗 / 升级 / 拾取药剂 |
| 高位字节 | `randomTopByte()` | `randomTopByte()`（同左） |

### 3.3 每个自由字节的取值

```
byte[j] = ( owner(V, j) + diffuse(V, j) ) & 0xFF        j = 0 .. b-2
```

| 分量 | 定义 | 作用 |
|---|---|---|
| `owner(V, j)` | `V[j]`，定长状态向量的第 j 项 | **可读性 + 玩家能动性**。字节 j 有固定归属，HUD 能显示「byte 3 ← player.posX」，玩家的操作直接推动它 |
| `diffuse(V, j)` | `expand(fold(V))` 的第 j 个字节 | **均匀覆盖 + 状态完整性**。把全场状态（含每一只怪物）折叠扩散到所有字节 |

**`V` 是仿真状态的纯函数，公式里没有时钟也没有计数器。** 所以同一个 `V` 一定产出同一串自由字节 —— 「世界没变」就等于「没有新密钥」，这不是优化，是这套映射的定义（§3.4 结尾、§9.4）。

#### 为什么必须混合

**纯直接映射不可行**：`player.dir` 只有 8 个取值。若某个字节直接等于它，那个字节就永远只覆盖 `0..255` 中的 8 个值 —— 浪费掉 96% 的范围。方向、区域编号、怪物原型这类低基数属性都有同样的问题。

**纯扩散又丢掉了可读性**：玩家无法感知自己的操作影响了什么，游戏就退化成一个「有怪物陪伴的随机数生成器」。

叠加之后的数学性质：`owner` 是有界的任意项，`diffuse` 是均匀项，**模 256 下均匀项加任意项仍然是均匀的**。所以 `byte[j]` 的整体分布由 `diffuse` 主导，覆盖率得到保证；同时 `owner` 保留了「哪个属性影响哪个字节」的可读性和玩家的直接操控感。

#### `fold` / `expand` 的具体选择

- `fold`：FNV-1a 32 位，以 **`puzzle 编号`** 为初始种子，逐字节吞掉整个 `V`。
- `expand`：splitmix32 PRNG，用 `fold` 的结果作种子，按需吐出字节。

> ⚠️ **`V` 里不包含 puzzle 编号，但 `fold` 的种子必须异或上它。** 否则切换到另一个 puzzle 时会产出完全相同的密钥串。

### 3.4 状态向量 V（定长，`|V| = 63`）

**定长是关键设计约束。** 怪物数量每时每刻都在变；如果 `V` 长度可变，那么某只怪物一死，它后面所有字节的归属就会整体错位，HUD 上的归属提示会疯狂乱跳，玩家会觉得「字节在乱变」。

因此固定布局，空槽位补 `0`：

```
V[0]       = player.dir             // 0..7
V[1]       = q(player.posX)
V[2]       = q(player.posY)
V[3]       = q(player.hp / maxHp)
V[4]       = q(player.attackPower)  // 只有强化药剂会改变它（§8.2）
V[5]       = q(player.moveSpeed)
V[6]       = q(player.attackSpeed)
V[7]       = q(player.attackRange)
V[8]       = q(player.hpSpeed)
V[9]       = q(player.level)
V[10]      = q(xp / xpForNext(level))
V[11]      = region.index           // 玩家所在区域 0..8
V[12]      = q(region.targetCount)  // 每区的目标怪物数（九区同一个数，§4.1）
V[13]      = q(region.respawnSec)   // 每区的刷新间隔（九区同一条曲线，§4.1）
V[14]      = q(kills)
─────────── 以下 8 只怪物 × 6 项 = 48 ───────────
V[15+6i+0] = m.dir
V[15+6i+1] = q(m.posX)
V[15+6i+2] = q(m.posY)
V[15+6i+3] = q(m.hp / m.maxHp)
V[15+6i+4] = q(dist(player, m))
V[15+6i+5] = m.attacking ? 1 : 0
```

`q()` 是量化到 `0..255` 的整数（位置按竞技场尺寸归一化，比率按百分比，绝对值按各自量程缩放后 clamp）。

`V[10]` 用 `xp / xpForNext(level)` 而不是固定除数：`xp` 会一直涨到 `100 × level` 才归零，任何常数都会很快饱和。这和 `V[3]` 用 `maxHp` 归一化是同一个形状 —— 分母是活的，所以这个字节**始终铺满整个 `0..255`**，不会随着等级升高而挤在某一端。（`sim.ts` 的 `while (s.xp >= xpForNext(s.level))` 保证了 `xp < xpForNext`，所以 `q()` 的上界恰好用满；`xpForNext(level) = 100 × level ≥ 100`，也不存在除零。）

#### 为什么删掉了 tick

`V[0]` 曾经是一个 tick 计数器，存在的唯一理由是「玩家站在空角落里不动时密钥也要动」。**这个前提是错的**：密钥是**世界状态**的函数（§3.3），而 tick 是时间 —— 它用时间伪造了一个「状态变了」的假象，代价是整个映射里混进一个和玩法无关的量，还让「世界不变则密钥不变」这条性质不再成立。

删掉之后 `V[0]` 回到 `player.dir`，而**静止的世界也不会永久静止**：§4.3 的密度升级每 30 秒改写一次 `region.targetCount`，§4.1 的等级公式每次升级改写 `region.respawnSeconds`，两者都在 `V` 里；怪物自己也在游荡。

> **一条代价，记在这里待拍板。** `V[12]` / `V[13]` 过去是**空间**读数（你站的那个格子有多密、回填多快），九区一视同仁之后它们变成**全局**读数：`V[12]` 是生存时钟的函数（时间不在 `V` 里，所以它仍有信息量），而 `V[13]` 现在是 `V[9]`（`level`）的确定性函数 —— 对 `fold` 而言它不再贡献任何区分度，63 个字节里有一个是冗余的。修法（把 `V[13]` 换成一个别的字段）要动本节的字节归属表与 HUD 的归属条，本次**没做**。

> ⚠️ 「世界不变则密钥不变」这句话说的是**自由字节**（`b-1` 个低位字节），不是最终密钥：高位字节仍然来自 `randomTopByte()`（§3.1），每次调用都是新的 CSPRNG 取样（`src/hex/range.ts`）。实现之所以比较 `V` / 自由字节而不是比较密钥，正是因为密钥每次都不同（§9.4）。

#### 怪物窗口 = 8

只取**离玩家最近的 8 只**怪物填入 `V`，排序键为 `(距离, spawnId)` —— 加 `spawnId` 是为了在距离相同时保证**确定性**，否则同一帧内排序结果不稳定，密钥会抖。

这个窗口设计让「靠近怪物」这件事本身改变密钥：**贴脸战斗和躲在角落的采样路径完全不同**，与「怪物是燃料」的核心循环一致。

#### 低基数属性的处理

`player.dir`（8 值）这类属性，即使作为 `owner` 也只贡献 8 个值；它们对密钥的**主要贡献来自 `fold`**（进入种子），`owner` 只是让玩家在 HUD 上看得见它。

#### 不进 `V` 的东西

**药剂（§8.4）与弹体（§15）都不进 `V`。** 它们不是密钥材料 —— 只通过改变 `V` 已经携带的玩家 / 怪物属性间接影响密钥 —— 而 `V` 定长承载不动新窗口：加一个「场上的掉落物」或「飞行中的弹体」窗口，会让每个字节的归属随一次击杀、一次开火而整体位移，HUD 的归属提示会跟着抖。

## 4. 场景与区域

> 对应需求第 4 条。

场景 `w × h`（= `GAME_WIDTH × GAME_HEIGHT` = 960 × 540）划分为 **3×3 = 9 个区域**。**九个区域完全一样** —— 同样的目标怪物数、同样的刷新间隔、同样的原型搭配，差异只有各自的坐标。九宫格是**分区处理**：让击杀能记在某本配额账上、让重生能落在某个格子里，如此而已。

### 4.1 九宫格是分区，不是难度分层

**本节曾被写成「风险/收益的空间梯度」** —— 四角 2 只 / 6.0s、四边 4 只 / 4.0s、中央 6 只 / 2.5s，各自一套原型，画布上标成 SAFE / CONTESTED / DANGER。用户否掉了这条设计：分区是为了处理，不是为了把场地分成不同的危险层，更不是给不同区域配不同参数的怪群。**应一视同仁。** 于是九个格子只剩一个数字，而且那个数字不属于格子。

| 参数 | 值 | 由谁定 |
|---|---|---|
| 目标怪物数 | **4**（九区一致，全场 36 只起） | §4.3 的生存时钟，每 30s 全体 +1 |
| 刷新间隔 | **5.0s − 0.1s × (等级 − 1)**，下限 `minRespawn` 0.8s | **玩家等级**（§8.2） |
| 原型 | 游荡者 / 追猎者 / 重装者，等概率 | 全场同一张表（§6） |

等级这条线是这次改动的**新梯度**：难度不再问「你站在哪」，而问「你长到哪」。1 级 5.0s，11 级 4.0s，21 级 3.0s，43 级触到 0.8s 的地板。刷新间隔在**击杀那一刻**读一次，正在倒数的条不追改 —— 与 §4.4 对待怪物血量的理由相同。

**代价如实记在这里，不能只引好处：**

- **「走到哪」不再是风险决策。** 原来的设计里空间选择与搜索推进是同一件事（移动会直接改写 `V` 里的 `player.posX/posY`）；现在九区同权，站哪都一样，空间决策只剩战术性的「离怪多远、离墙多远」，不再有「去哪一档」。
- **等级这条曲线在短局里几乎不生效。** `xpForNext = 100 × 等级`，一只怪 10 / 20 / 40 XP：升到 11 级要约 5500 XP，约 240 次击杀。**已实测：机器人中位存活 14.83 s、每局 80 次击杀 —— 整局刷新间隔都停在 5.0s 的初值上，等级规则贡献为 0。**（§14.5 的「＋九区拉平」列）也就是说机器人的典型一局里这条梯度等于没接上电；它对人类长局才是收紧的。而**空间那条梯度拆掉之后，代价由密度自己付了**：每格的刷新比旧的 2.5–6s 更松，但总数从 30 涨到 36，中位存活因此从 22.33s 掉到 14.83s（同机同种子的对照臂），详见 §14.5。
- **角落不再稀薄。** 四角从 2 只变成 4 只，重装者也会出现在那里。角落唯一的特殊性回到几何：它是墙构成的死角（§14.2 的 `TRAP_WEIGHT`），与配额无关。
- **难度因此全部压在总数上，而总数涨了。** 每格 4 只 = 全场 36 只（旧的 2/4/6 是 30 只），四角是翻倍的那部分。实测（同机同种子的对照臂，§14.5 的「＋九区拉平」列）：**机器人中位存活 22.33s → 14.83s、击杀 168 → 80**，而站桩存活反而 1.82s → **2.43s**（场地正中不再是全图最密的一格）—— 同一张图**对站桩更宽、对会玩的人更狠**。
  > **这里曾经写着一条建议：把 `regionTargetCount` 从 4 降到 3（全场 27 只），好让「等级才是唯一的梯度」在开局也成立。用户已经就这个数明确指示过 —— 「数量可以了，不用再调整」，所以它不再是待选项，`regionTargetCount` 定在 4。** 留这段是因为它记着那个数当初是从哪来的，而不是因为它还开着。**难度这个旋钮要动的话，下一根可动的杠杆是 `senseRange`（§13 第一次有了它的实测值）。**

**出生点：场地正中。** 这一条与本次改动无关（它由 §6.2 决定，早在区域扁平化之前就已经反转）。判据是**先手距离**：拴区解除之后，贴在墙上的起点要先花一段跑道在「跑出来」上，而脱战需要一次 3.9s 不中断的直线跑（§14.2）。旧数据（32 颗种子，策略不变，只挪出生点）是：中位存活 **9.9s → 17.6s**、平均净空 **47px → 71px**；这组数字量于旧地图，方向仍成立（中心离墙远），量值待重测。

值得注意的是，挪出生点**并没有**治好「往边界跑」这个缺陷本身：两臂的贴墙比例都随时间上升。出生点是**先手距离**，不是吸引力 —— 吸引力在 `flee` 的纯径向目标与墙滑的切向残差上（§14.6）。

### 4.2 刷新规则

每只怪物被击杀后，在**它所属区域内**的随机位置重生，延迟取**击杀那一刻的等级**所对应的间隔（§4.1）。九区同一节奏 —— 账本是分开的，节奏是共用的。

### 4.3 全局难度升级（密度）

每存活 **30 秒**，所有区域目标怪物数 `+1`，封顶 `maxTargetCount` = 14。

**刷新间隔不再参与这条曲线。** 它曾经每 30 秒 `×0.9`，现在整条交给 §4.1 的等级公式：同一个旋钮上叠两条曲线，谁也读不出是哪一条在起作用。

密度仍由生存时钟推进，理由是原来那条：这让任何一局最终都会结束，存活时间因此成为一个有意义的分数。没有它，高手可以无限期地苟着，分数失去区分度。

### 4.4 怪物血量按分钟复利升级

> 对应**迭代二**需求第 1 条（怪物的升级）。下文同：§8.2 对应迭代二需求第 2 条，§8.3 / §8.4 对应第 3 条。

每存活 **60 秒**，怪物血量乘数 `×1.05`（复利），即第 N 分钟结束时的乘数为 `1.05^N`。

实现上**不新增计时器字段**，直接从存活时间推导：

```
monsterHpMul(time) = monsterHpGrowth ** floor(time / monsterHpEvery)
```

`spawnMonster()` 在生成时把 `arch.hp × monsterHpMul(s.time)` 同时写进 `hp` 和 `maxHp`。

**只作用于新刷新的怪物，已存在的怪物不追溯。** 这不是偷懒，是有意的：

- 刷新间隔在 1 级只有 5.0 秒、之后只会更短（§4.1），一分钟内场上怪物基本换过一轮，追溯与否的效果差异很小；
- 而给一只**正在挨打**的怪物凭空加血，读起来是「打不动了」的 bug，不是难度。血条凭空变长是最容易被误解成故障的反馈。

§4.3 抬的是**密度**（更多怪），§4.4 抬的是**单只怪的分量**，§4.1 的等级公式抬的是**回填速度**。三条曲线叠加，才让「苟着」的边际收益随时间真正归零。

## 5. 玩家

> 对应需求第 3 条。

| 属性 | 初始值 | 说明 |
|---|---|---|
| `dir` | 由输入决定 | **8 方向**，与需求一致 |
| `moveSpeed` | 160 px/s | 走位速度，躲攻击靠它 |
| `attackSpeed` | 1.5 次/s | **自动攻击**的冷却 |
| `attackPower` | 8 | 每次攻击伤害 |
| `attackRange` | 55 px | 自动攻击的索敌半径 |
| `hp` | 100 | 归零即本局结束。上限见 `maxHp`，两者**不是一回事** |
| `maxHp` | 100 | **唯一的成长轴**：升级与生命药剂各自 `×1.05`（§8.2 / §8.3）。抬高上限**不回血** |
| `hpSpeed` | 1.0 /s | 脱战 3 秒后开始回血 |
| `posX, posY` | 场地正中出生 | 不得越出场景边界 |

### 5.1 为什么攻击是自动的

需求第 1 条规定 UI 里没有战斗键的位置：**下拉框** 和 **暂停/运行按钮**，加上 §14 的模式开关——后者不进游戏循环，见 §10.1。没有攻击键的位置。

所以攻击设计为**对 `attackRange` 内最近的怪物自动出手**。这个选择有三个好处：

1. 符合 2 控件的 UI 约束；
2. 玩家只需要专注走位，操作门槛低、反馈直接；
3. `attackPower / attackSpeed / attackRange` 从「按钮」变成**可被感知、可成长的属性** —— 也正好让它们作为密钥材料有意义。

### 5.2 脱战回血

最后一次受伤后 **3 秒**开始按 `hpSpeed` 回复。

这是「脱离接触」这个决策的收益来源：**只要真的跑出所有感知圈，血就回来了。** 但它的搭档在 §6.2 之后换了人 —— 曾经的节奏是「中心冒险 → 受伤 → 撤回角落回血 → 再冲进去」，靠的是角落那一档既低产出又安全；§4.1 把九区拉平、§6.2 又拆了拴区之后，「角落」既不是一档、也不再安全，回血只与「多久没挨打」有关，与站在哪里无关。所以撤退的方向不再是「回角落」，而是**任何一条能跑出感知圈的路**，而跑出去需要的那 ~3.9 秒不中断直线见 §6.2。

## 6. 怪物

> 对应需求第 5 条。

三种原型，字段全部来自需求 5：

> 下表是 `m_hp` 的**基准值**。实际生成时还要乘以 §4.4 的时间乘数 `monsterHpMul(time)`，`hp` 与 `maxHp` 同时取该结果。

| 原型 | `m_hp` | `m_moveSpeed` | `m_attackPower` | `m_attackSpeed` | `m_attackRange` | `m_range`（感知） | 经验 | 半径 | 弹体（§15） |
|---|---|---|---|---|---|---|---|---|---|
| **游荡者** | 20 | 50 | 5 | 0.8 /s | 22 px | 140 px | 10 | 6 px | 子弹 |
| **追猎者** | 35 | 120 | 8 | 1.2 /s | 26 px | 260 px | 20 | 7 px | 子弹 |
| **重装者** | 90 | 40 | 18 | 0.6 /s | 34 px | 110 px | 40 | 11 px | 炸弹 |

`m_dir` 同样是 8 方向，始终朝向自己的移动方向 / 朝向目标。

**身体半径**（6 / 7 / 11 px）由 `sim.ts` 拥有，而不是留在渲染层：它既是剪影的绘制半径，也是 §15 弹体命中判定的门槛（`半径 + bulletRadius`）—— 也就是 §10.3 那条「画出来的就是判定的」在多了一个消费者之后的写法。

### 6.1 行为

```
if dist(player) <= m_range:              # 感知到就锁定
    m_dir = 朝向玩家（8 方向取整）
    朝玩家移动（移动范围只夹在场地边界内，见 §6.2）
    if dist(player) <= m_attackRange and 攻击冷却就绪:
        发射按原型决定的弹体（§15），伤害随弹体飞
        攻击冷却 = 1 / m_attackSpeed
else:                                   # 未感知
    在自己的 home 区域内随机游荡
```

**注意两行的夹取范围是不同的，这是 §6.2 的改动。** 游荡仍然夹在自己的 home 区内（那是刷新配额的账本，不是移动边界），而**追击可以跨出 home 区直到场地边缘** —— 感知范围是唯一的追猎边界。打断追击的只有一件事：玩家跑出 `m_range`。

**冷却计的是「出手」，不是「命中」。** 冷却在弹体生成的那一刻重置，与 hit-scan 时代完全一致 —— 变的是伤害的到达时间，不是出手的节奏。所以 §6 这张表里 `m_attackSpeed` 的含义一个字都没变。

**感知范围 `m_range` 是设计里最有意思的一个字段。**

- **重装者**感知只有 110 px，但攻击力 18（游荡者的 3.6 倍）。它「看不见」远处的你 —— **只要不进它的圈就绝对安全**。
- **追猎者**感知 260 px，跨过整个场地也不衰减，是强制位移压力 —— 逼你持续移动，而不是站桩输出。

于是走位从「跑开」升级为**绕开视野圈**：玩家需要读怪物的感知半径，规划一条不触发高危怪物的路线。这是躲避玩法的技术深度所在。

### 6.2 区域划分刷新，不划分移动

**怪物可以离开它的 home 区域** —— 游荡会走遍全场，追击也会（§6.1 的两个条件）。唯一的边界是**场地边缘**：`wander` 与追击位置都夹在 `arenaPad` = 14 px 的内缩矩形里，撞到就镜像方向。

九宫格因此退回它本来的身份：**刷新分区 + 刷新配额账本**（`countInRegion` 按 home 计数，§4.2）。它不划分怪物的活动范围，也不划分战斗。

**这条规则是刻意反转的，反转的代价必须写在这里。** 曾经的版本是「怪物被拴在自己区域内」，理由是让当时 §4 的区域梯度成立 —— 若允许跨区追击，角落那一档「安全区」就不存在了（那一档本身随后也在 §4.1 被删掉）。反转的直接后果就是如此：

- **没有哪一格是安全的。** 追猎者的 `m_range` 260 px 远超一个格子的尺寸（一格只有 320 × 180），所以 t=0 就罩得到隔壁、甚至更远。区域的边界因此从来只是**配额**的边界，不是威胁的边界。
- **脱战变成一件要练的事，而不是走回边界。** 仇恨现在只看 `m_range`（§6.1），所以断仇恨的唯一办法是**拉开距离**。实测三种原型：游荡者（50 px/s）0.3 s、重装者（40 px/s）0.1 s，而**追猎者（120 px/s）需要约 3.9 s 不间断的直线跑**（= 160 px 间距 ÷ 40 px/s 的净接近差，需要约 640 px 跑道；场地 960 × 540）。一旦在墙上转身，收益全部归零。
- 这条 3.9 s 的门槛**正是** §14.2 要机器人「锁定方向」的原因：一个每几帧翻一次方向的机器人永远凑不出这 3.9 s，对它而言脱战机制等于不存在。
- **已知的、用户尚未拍板的代价**：站桩存活从 92 s 塌到约 3.2 s。这是拴区解除的直接后果（t=0 就被邻格的怪罩住），属于难度基调问题，与机器人策略分开处理。数字量于旧地图，量值待重测，方向不变。

反过来，这条规则也**没有**制造「站在区域外无伤刷怪」的漏洞：玩家的 `attackRange` 只有 55 px，想够到怪物就要贴上去，而那时怪物的 `m_attackRange`（22–34 px）同样够得到你。贴上去蹭怪仍然要付血价。

## 7. 战斗

| 方向 | 触发条件 | 节奏 | 伤害到达 |
|---|---|---|---|
| 玩家 → 怪物 | 目标在 `attackRange` 内，取**最近**的一只 | 按 `attackSpeed` 冷却 | 弹体命中时（§15） |
| 怪物 → 玩家 | 目标在 `m_attackRange` 内 | 按 `m_attackSpeed` 冷却 | 弹体命中 / 炸弹爆炸时（§15） |

**躲避是空间性的，不是数值赌博。** 这条主张有两个窗口，而不是一个：

1. **冷却窗口。** 玩家只要在冷却走完之前走出 `m_attackRange`，这次出手就不成立。
2. **飞行窗口**（§15）。出手成立之后，伤害还要飞一段才到 —— 目标在弹体到达之前离开那条线，这一枪就是空的。炸弹把第二个窗口放大成肉眼可见的一档：落点圈画在地上，0.4 秒的引信足够走开（§15.3）。

**死亡**：`hp <= 0` → 本局结束，存活时间定格。弹体随之冻结 —— `stepSim` 在 `!alive` 时直接返回，所以死在一发炸弹落地之前的话，它会停在半空中。

## 8. 成长与资源

### 8.1 算力（hashpower）—— 已移除

> 这一节保留编号，因为它记录的是一次**删除**：代码注释按 §编号引用本文档，重排编号会让别处的引用失效。

**曾经是什么。** 一个 0..100 的资源：击杀 +1/+2/+4，自然衰减 3/s，再线性映射到密钥采样速率 `2 + 18 × (hashpower / 100)`，即 2~20 keys/s。它是「击杀 → 搜索」的唯一换算通道，被称为「整个玩法的支点」。

**为什么删掉。** 它假设「采样速率」是玩家可以用玩法买到的东西 —— 但密钥是世界状态的函数（§3.3 / §3.4），所以「每秒采多少个」根本不是一个游戏能控制的量：它是**世界自身的变化速率**，上限是帧率（每个仿真步至多一次提交，§9.4）。把一个不由游戏决定的量当成资源来发放，只会让数值平衡去调一个假旋钮。

**随之而来的三处改动：**

1. `V` 里原本放 hashpower 的那个槽位现在放 `xp`（§3.4）；
2. §4.1 曾把区域梯度改用「状态变化量」重新解释 —— 那一版后来连同区域梯度本身一起被删掉了（§4.1：九区一视同仁）；
3. §10.2 的 HUD 少了「算力」和「采样 keys/s」两个读数。

**活下来的是什么。** 杀怪依然推动搜索 —— 通过经验、击杀数、怪物集合、走位、以及拾取后的属性，全部都在 `V` 里 —— 而不是通过一个读表节奏。

### 8.2 等级：只涨生命力

> 对应迭代二需求第 2 条。经验值系统本身在迭代一就已存在（`xpForNext(level) = 100 × level`），本次改的是**升级的内容**。

击杀获得经验（游荡者 10 / 追猎者 20 / 重装者 40，见 §6 表；与 §8.3 的药剂掉落无关）。升到第 N 级需要 `100 × N` 经验。每次升级：

```
maxHp *= 1.05        （hp 不变）
```

**升级不再提供攻击力/攻速/移速。** 上一版那六项加法加成已经删除，原因只有一个：如果升级本身就涨战斗力，药剂就只是「慢一点的升级」，掉落系统失去存在理由。现在分工是干净的：

| 轨道 | 提供 |
|---|---|
| 等级（经验） | **血量上限** —— 容错空间 |
| 药剂（掉落） | **战斗力与机动** —— 攻击力 / 攻速 / 移速 |

两条轨道的来源也不同：经验来自「击杀数量」，药剂来自「击杀位置」—— 后者要求你走过去，见 §8.3。

抬高上限时**当前 `hp` 不动**（`50/100` → `50/105`），与生命药剂语义完全一致：上限是容量，不是补给。

因为**所有属性都在 `V` 向量里**，升级会改变密钥字节 —— 玩家变强这件事本身就在移动采样位置。这是「玩家的状态就是密钥材料」这句话的具体兑现。

经验的另一处可见性：击杀位置会飘出 `+10` / `+20` / `+40` 的数字（§10.3），读的正是 §6 表的经验列，所以它不可能和真正让玩家升级的规则不一致。

### 8.3 掉落与药剂

> 对应迭代二需求第 3 条。

怪物死亡时，在**死亡点**掉落药剂。四种药剂**各自独立掷骰**，所以一次击杀可能什么都不掉，也可能同时掉多个。

| 药剂 | 概率 | 效果 |
|---|---|---|
| 回复药剂 `heal` | 22% | `hp = min(maxHp, hp + 0.30 × maxHp)` —— **封顶不回溢** |
| 强化药剂 `power` | 14% | `attackPower ×1.05` **且** `attackSpeed ×1.05` |
| 敏捷药剂 `agility` | 14% | `moveSpeed ×1.05` |
| 生命药剂 `vitality` | 9% | `maxHp ×1.05`，`hp` 不变 |

**「独立判定，且不保证掉落」是刻意的。** 加权单抽表（总和 100%）会让每次击杀都必然有产出，击杀变成稳定的收入流；独立判定下约 **52% 的击杀不掉任何东西**，期望每次击杀 0.59 个。收益因此是**方差**而不是**速率** —— 玩家不能按「每杀 N 只就有 M 瓶」来规划，只能按「现在这一片值不值得进去」来判断。

概率值是 `sim.ts` 里的 `DROP_CHANCE` 一组常量，随时可调。

**掉落的是一次性收益，条件是走过去。** 药剂躺在怪物死掉的地方，不在玩家脚下 —— 「走到哪」因此从纯防御问题（躲开攻击）变成了攻防一体的取舍（为了收益进入危险区，并在那里多停一会儿）。

| 参数 | 值 | 说明 |
|---|---|---|
| `pickupRadius` | 5 px | **药剂自己的**半径，同时也是画出来的视觉半径 |
| `playerRadius` | 9 px | 玩家的身体半径，同时也是画出来的视觉半径 |
| 拾取判定 | `playerRadius + pickupRadius` = **14 px** | 两个圆相触即算「踩上去了」（推导见 §8.4） |
| `itemLifetime` | 30 s | 之后消失 |
| `itemFlicker` | 10 s | 消失前最后 10 秒开始闪烁 |

一次掉多个时，它们按索引散布在死亡点周围一个约 11 px 的小圆上，避免完全重叠成一个；只掉一个时精确落在死亡点。

### 8.4 拾取

拾取是**自动**的（与自动攻击同理：需求第 1 条只给了 2 个控件，没有拾取键的位置）。玩家不需要按键，只要**经过**道具即触发。

**判定的是两个圆相触，不是玩家的圆心落进药剂里。** 玩家自己有 9 px 的身体，药剂 5 px，所以「看起来踩上去了」是圆心距 ≤ `playerRadius + pickupRadius` = **14 px**。这一条曾经写错过：判定只比了药剂自己的 5 px，于是 5–14 px 之间有一个**死区** —— 玩家在画面上整个人盖住药剂，规则却认为还没走到。而移动中的玩家**几乎总是**落在死区里：只有 8 个方向，玩家是**掠过**药剂而不是把圆心对准穿过去。结果就是必须停下来、来回蹭几下才捡得到，恰好把「走过去」这个动作的手感毁掉。实现上 `playerRadius` 由 `sim.ts` 拥有，`GameScene` 也引用同一个常量来画玩家和药剂，所以画面和判定不可能再分家。

判定用的是**本步移动前后两点构成的线段**到道具的距离，而不是终点距离。原因是：`dt` 被 clamp 到 `maxDt = 0.05`，慢帧一步能走 8 px，敏捷药剂叠起来还能更快 —— 只判终点会**穿过**道具而不拾取。有了线段判定，速度堆上去之后也不会漏捡。

**药剂不是密钥材料。** 掉落物**不进 `GameSnapshot`**，因此不占 `V` 的字节。它们通过改变 `maxHp / attackPower / attackSpeed / moveSpeed` 间接进入向量 —— `V` 是定长的（§3.4），加一个掉落物窗口会移动每个字节的归属，HUD 的归属提示会整体错位。

## 9. 运行 / 暂停 / 匹配流程

> 对应需求第 1、6 条。

### 9.1 状态机

```
   未选 puzzle ──► IDLE         ▶ 禁用，画布显示「请选择一个 puzzle」
        │ 选择 puzzle
        ▼
   READY ⇄ RUNNING              ▶ / ⏸ 手动切换
        │        │
        │        ├── 切到别的 tab ──► 自动暂停，运行意图复位
        │        │                    切回来保持暂停，必须手动点 ▶
        │        │
        │        └── hp 归零 ──► DEAD，存活时间定格，▶ 可重开
        │
        └── hash160 命中 ──► MATCHED，全部暂停 + 保存私钥
```

### 9.2 三条硬规则

1. **未选 puzzle 不能运行。** 没有 range 就没有字节布局（§3.1），`▶` 直接禁用。
2. **切走 tab 自动暂停。** 复用 `App.svelte` 已有的 `active` prop 协议。注意：`hidden` 属性**不会**触发 `document.visibilitychange`，所以 Phaser 自带的可见性处理在这里是失效的，必须由这条协议接管。
3. **切回来不自动恢复。** 这是与 Hex tab 的**关键差异**：Hex tab 选择继续后台跑（见 `App.svelte` 的注释），Game tab 必须**手动点 ▶ 继续**。实现上，`setActive(false)` 时要顺手把「运行意图」也复位成 `false`，这样切回来按钮就是 ▶。

### 9.3 暂停 = 停止搜索

暂停冻结仿真；仿真冻结则 `V` 恒定，于是**没有新密钥可以提交** —— 搜索自己就停了，没有任何东西需要被显式停掉。

这比旧实现（暂停时停掉密钥循环）更强：现在是**结构性**的，「暂停着还在后台扫」在 `V` 这一层就不可能发生，因为根本没有一个独立于仿真的时钟。

仍然有两条防线，只是职责变了：

- `syncStatus()` 依然是唯一决定 `setPaused()` 的地方，也是唯一决定「运行意图」的地方；
- 采样在**仿真真正走了一步之后**才可能发生（§9.4），并且只在意图是 `running` 时（READY 状态下画布也在渲染，但仿真没走，不产生密钥）。

### 9.4 密钥推进流程

**每当世界状态发生变化**（`V` 与上次提交的不同），走一遍：

1. 游戏状态 → `V` → `b-1` 个自由字节（§3.3）
2. 与上次提交的自由字节比较，相同则结束 —— 世界没变，没有新密钥
3. `randomTopByte(puzzle)` 取受 range 限制的高位字节
4. `puzzleKeyHex()` → 64 字符私钥 hex
5. 调 **`derive_group([keyHex])`**（`src/hex/api.ts`）
6. 命中 → 暂停 + 落盘 + `MatchBanner` + 标题行上的 ✅

触发点是场景的每一帧（`GameScene.update()` 末尾），所以推进速率的上限是帧率。**没有定时器，也没有速率常数** —— 世界变得多快，密钥就推进得多快。

> **同一时刻至多一个 `derive_group` 在途。** 在途期间到达的新状态不排队：等在途的那次落地后**重新看一眼当前世界**。排队的状态一定比当前状态旧，没有保留的价值。

> **两类边界，两种处理，区别是刻意的。** `generation` 只在**换局**时自增 —— 重开、换 puzzle、卸载。这三件事之后的世界和之前的世界没有关系，所以在途结果必须作废，否则一个上一局的密钥会画进这一局。
> **暂停、死亡、命中不作废在途结果。** 这三者都没有改变世界，只是让它停住：在途的那个密钥取自最后一个被 step 过的世界状态，而那恰好就是画布上冻结的那一帧。它在暂停后落地、被计入 `keysScanned` 并显示出来，是**一致**的，丢掉它才是浪费一次已经付过钱的 IPC。
> 暂停真正保证的是**不再发起新的提交**，这一点由 `canSample()` 在 `onFrame` 的入口处守住。实测：暂停后 3 秒内 0 个新密钥。

> 显示节流：密钥读数与字节条按固定间隔重绘，而 `keysScanned` 每个密钥都计数。两者的职责不同 —— 前者是给人看的，后者是这次运行真实花掉的成本。

> ⚠️ **必须用 `derive_group`，不能用 `derive_full`。**
> `derive_full`（`src-tauri/src/homepage.rs:618-627`）只做比对，**从不调用 `save_match`**，命中结果不会落盘。
> `derive_group`（`homepage.rs:640-672`）是唯一对「调用方已知私钥」执行持久化的命令，且在命中时自动写入 `{timestamp}.txt`。
> 这也正是 Hex tab group 模式使用的同一个命令。

## 10. UI

### 10.0 顶栏 = 一行

整条顶栏就是标题行：左边是读数，右边是 §10.1 的控件。

```
survive  efc98e13967c0a07…  1KKKK…KKKKK  ❌   [ 👤 manual │ 🤖 robot ]  [ #130 · 17 bytes ▾ ]  [ ⏸ ]
└ 标题 ┘ └─ 私钥非零部分 ─┘ └ 压缩地址 ┘ 命中  └── §14 的模式开关 ──┘  └── 需求第 1 条的 2 个控件 ──┘
```

**运行状态不再占一格。** 这里曾经有个 `idle / ready / paused / matched` 的文字标签。它和画布上的遮罩（`READY` / `PAUSED` / `GAME OVER`，即 §9.1 那几个状态的画法）说的是同一件事，而遮罩就画在玩家正在看的地方 —— 同一句话不必说两遍。状态机本身没有消失，它仍然驱动暂停协议（§9.4）与 `▶ / ⏸` 的可读性，只是不再打印给人看。

模式开关排在两个玩法控件**左侧**，因为它管的是「谁在玩」，而不是「玩什么」——离开玩法本身越远的东西越靠外，读起来才是「先决定谁玩，再决定玩哪一局，再决定跑不跑」。

控件用 `margin-left: auto` 顶到最右，与左侧读数分开——两者性质不同，一片留白比一个 gap 更能说明这件事。窗口变窄时整行 `flex-wrap` 换行，控件落到第二行，仍然靠右，不溢出。

左侧读数三项：

- **私钥的非零部分**：`puzzleKeyHex()` 在 range 之上全是 `00` 填充，展示完整 64 字符等于一堵零墙，把本局真正的产出挤到最右边。剥掉填充后剩下的就是玩家正在推动的那一段。点击复制完整 64 字符。
- **压缩地址**：点击复制。命中时转绿（`✅`），未命中为暗色（`❌`）。
- **命中图标**：`address_match`，与 `handleMatch()` 读的是同一个字段。

> 早期版本在底部复用 `AddrInfoPanel` 显示私钥 / xprv / 地址三张卡片。xprv 对本局没有意义（它由私钥唯一决定，不会随玩法变化），三张卡片的信息密度又远低于它占的位置，因此收进标题行。

### 10.1 控件（需求第 1 条的 2 个 + 1 个模式开关）

```
[ 👤 manual │ 🤖 robot ]   [ puzzle 下拉框 ▾ ]   [ ▶ / ⏸ ]        ← 位于 §10.0 的顶栏右端
```

- **下拉框**：列出全部 puzzle，显示 `#71 · 9 bytes`。选中后才允许运行。
- **按钮**：`▶` 运行 / `⏸` 暂停。未选 puzzle 时禁用；命中后锁定；死亡后按下 = 重开新局。
- **模式开关**（§14）：`👤 manual` / `🤖 robot`，两格的分段控件，命中后一并锁定。

**为什么是两个按钮而不是一个复选框。** 复选框说的是「你做过什么」（勾没了就不知道当初勾的是哪一项），分段控件说的是「你现在在哪」——而模式的全部意义就是那个当前态，它必须一眼可读。

**为什么它不算破坏需求第 1 条。** 需求第 1 条要的是「玩家不需要攻击键、不需要拾取键」，那条约束针对的是**玩法输入**：进场之后，除了方向键没有第二个键要按。模式开关在玩法之外——它决定这一局由谁驱动，而且在 `manual` 下与旧版逐帧等价。所以三个控件里有两个是需求原文的，第三个不参与游戏循环。

### 10.2 HUD（只读）

HUD 是**竞技场下方的一条**，不在标题行里：它报的是这一局累积出来的东西，看一眼就够，不该跟控件抢顶栏的位置。它与画布同属一个区块（`.game-arena`，间距 10px）—— `.game-main` 的 28px 是用来分隔区块的，不是用来分隔图注的。

```
存活 02:47.3   最佳 05:12.8   等级 7   经验 340/700   HP 84/170   击杀 63   keys 4,182
```

**经验**紧挨着等级：本次迭代之后，等级数字本身不再说明成长（升级只涨上限），进度条才是玩家真正在追的东西。

**掉落不再有读数。** 这里曾有一行 `掉落 ●12 ●7 ●5 ●2`，同时充当掉落物的**图例**：四个色点按 `heal / power / agility / vitality` 固定顺序排列，悬停给出文字说明。这一行连同图例一并删掉了。留下的后果是画布上的药剂只剩颜色可辨 —— `GameScene.readPalette()` 仍然从 `--loot-*` 变量取色（那几个变量因此保留），但场上没有任何地方再说明哪个颜色是什么。

`HP` 的上限显示为 `Math.round(maxHp)`：`maxHp` 在 sim 里是 `×1.05` 的连乘，浮点真值会带尾巴（`1.5 × 1.05 = 1.5750000000000002`）。**取整只发生在显示层** —— 在 sim 里取整会让复利每级漂移一点，且 `hp` 本来就因为回血是浮点的。

外加一行**字节归属提示**，把 §3.3 的可读性兑现成玩家看得见的信息：

```
byte0 ← player.dir    byte1 ← player.posX    byte2 ← player.posY    byte15 ← m[0].dir   …
```

（`V[0]` 回到 `player.dir` 之后，条子开头的四个归属全是玩家自己的实时状态，见 §3.4「为什么删掉了 tick」。）

这是「混合式映射」相对于「纯扩散」唯一但关键的回报：玩家能看到自己的操作在推动哪些字节。

字节条会**完整**展示 `b-1` 个自由字节（8–19 个）—— 它就是 Game tab 版的「grid」。归属说明只标前 4 个，避免 b 较大时糊成一片。

### 10.3 画布上的可见性规则

环形感知圈（`m_range`）是核心战术，但场上有一批怪物（§4.1：九区各 4 只起）—— **全部画出来会织成一张网，反而谁都看不清**。所以：

- **只画玩家可能踏入的那些圈**：`dist(player, monster) ≤ m_range + 60`。60 px 略大于玩家的 `attackRange`（55），于是「看得见的圈」= 「打得着的怪」= 「需要绕的怪」。
- **已锁定的圈更亮**（alpha 0.5 vs 0.22），一眼能分辨「它看见我了」和「我在它边缘」。

地图其余部分因此保持安静，九宫格的分区线才能真正读出来。**九个格子是同一种颜色、同一种线宽** —— 这条梯度曾经用三色（角落偏蓝 / 边中偏金 / 中心偏红）画出来，区域拉平之后它连同 SAFE / CONTESTED / DANGER 三个格子标签一起删掉了。玩家所在的那一格仍会被高亮，但那读的是**分区**（这本配额账现在记在谁头上），不是「你进了危险区」。

**地上的药剂必须一眼可辨种类，而且不能只靠颜色。** 场上最多同时躺着十几瓶，颜色在重叠时会失效，色觉差异也会让整张表作废。所以每种药剂除了色相（`--loot-*`）还有一个**独立的剪影**，沿用怪物那边已经确立的「一种原型一个形状」的语言：

| 药剂 | 剪影 |
|---|---|
| 回复 `heal` | 十字（两个 `fillRect`） |
| 强化 `power` | 正三角 |
| 敏捷 `agility` | 朝右的三角 |
| 生命 `vitality` | 圆环 |

**击杀处飘出 `+10` / `+20` / `+40`** —— 数字直接读 §6 表的经验列，和让玩家升级的是同一个字段（§8.2）。它留在怪物倒下的位置，而拾取药剂的那一下是从**玩家身上**炸开的：一个说「这里死了什么」，一个说「你拿到了什么」，两者在同一帧同时发生也不会被看混。

**弹体是这条「不只靠颜色」规则的一个例外，而例外有它的理由。** 子弹确实只靠颜色分敌我（`--accent` 绿 / 红，与两侧的单位配色一致）：它们只存在 0.1 秒、体积只有 2.5 px，而**方向本身就把信息说完了** —— 玩家的子弹飞向怪物，怪物的子弹飞向你。重叠与色觉差异在这里退化成可以忽略的代价。炸弹则必须多一个形状，因为它不是「一颗在飞的东西」而是「一个即将落在某处的圈」：

| 弹体 | 剪影 |
|---|---|
| 玩家的子弹 | 绿色的弹头 + 拖尾（`--accent`） |
| 怪物的子弹 | 红色的弹头 + 拖尾 |
| 炸弹 | 圆体 + 地面上**画在 `blast` 半径上的预警圈** |

预警圈是炸弹可躲的前提，而不是装饰（§15.3）：没有它，0.4 秒后凭空炸开的伤害会被读成渲染 bug。它同时也是「画出来的就是判定的」的一次兑现 —— 屏幕上那个圈就是判定用的那个圈，两者读同一个常量（§15.2）。

另外两条：

- **画出来的半径就是判定半径**（`pickupRadius` = 5 px，`playerRadius` = 9 px）。让「看起来踩上去了」和「真的捡到了」是同一条线，而不是靠玩家去猜一个隐藏判定区。注意判定涉及**两个**圆，所以门槛是两者之和（14 px）而不是药剂自己的半径 —— 只取后者会在两个半径之间留出一条视觉上已经踩上去、判定却不认的死区（§8.4 记了这次踩坑）。两个半径都由 `sim.ts` 拥有，`GameScene` 引用同一组常量去画，画面与判定因此不可能分家。
- **寿命最后 10 秒开始闪烁**（`itemFlicker`）。闪烁是「它快没了」的唯一提示 —— 没有它，药剂凭空消失会被读成渲染 bug。

### 10.4 操控

- **移动**：WASD / 方向键（8 方向）
- **攻击**：自动（见 §5.1）
- **拾取**：自动（见 §8.4）—— 同样是因为需求第 1 条只给了 2 个控件

## 13. 待定与后续可能

以下**不在**本次范围内，列出以备后续讨论：

- **难度基调：站桩存活从 92 s 塌到约 3.2 s（待用户拍板）。** 这是解除怪物拴区（§6.2）的直接后果 —— t=0 就有约 5 只怪罩住玩家，其中 3 只在邻区，因为感知范围是唯一的追猎边界（§4.1 记了这个代价）。**策略那几轮刻意不动它**：机器人策略的所有数字都是在那个世界里量出来的（§14.5 / §14.6），如果同时改难度，两边就无法归因。**九区拉平那一轮动了它，而且这是第一次有干净归因的难度改动**（`robot.ts` 一行没改，§14.5 的「＋九区拉平」列）：站桩存活 1.82 s → **2.43 s**（中心从 6 只 / 2.5s 变成 4 只 / 5.0s），但机器人中位存活 22.33 s → **14.83 s** —— **同一张图对站桩更宽、对会玩的人更狠**，因为四角从 2 只涨到 4 只，总数 30 → 36，而「角落稀薄」原本是一份隐含的缓冲。当前可用的旋钮至少有：**`senseRange`（唯一已有实测值的那个，见下）、§4.3 的密度升级曲线、§4.1 的每级 −0.1s 量级、以及「出生点是否给一小段无敌」。** `regionTargetCount` **不在这个列表里** —— 用户已明确「数量可以了，不用再调整」，它定在 4。

  **而这个数字还有第二张账单：一条命 0 击杀的概率 36% → 56%（§14.5）。** 它不是一个独立的缺陷，是同一个密度的另一面 —— `tests/game-tab.mjs` 那句「机器人不用键盘也能拿到一次击杀」等的就是**一条命里至少一次击杀**。**「＋引到的 1–4 只」那一轮把它量到底了（§14.5 的表），而量出来的结果把最省事的那条修法划掉了**：一条命**有过**击杀的只占 **40.6%**（39/96），首次击杀中位 12.87 s、最大 43.83 s，而单局时长中位只有 14.63 s —— 所以把 `timeout: 30000` 往上调，天花板就是 **40.6%**（60 s 窗口也一样），因为**一条命结束后不会自己再来一条**（死亡是停下、`▶` 手动重开）。**「超时不够长」是错的读法。** 于是可动的只剩两处，而它们不是同一件事：

  - **（a）改世界 —— 但现在有两个不同的旋钮，而它们不是一回事。** 第一个是 `regionTargetCount` 4 → 3（全场 27 只，低于旧的 30）。**用户已经就这个数给过明确指示：「数量可以了，不用再调整」**，所以它**不再是一个待选项**，记在这里只是为了把账留全。第二个是 **`senseRange`**，而它是一个**独立的旋钮**，用户没有就它说过话 —— 而它是「＋引到的 1–4 只」那一轮**唯一实测出大效果的杠杆**：只把追猎者的 `senseRange` 从 260 收到 140（96 颗种子，`SWEEP_OVERRIDE` 探针，`sim.ts` 未动），**击杀 80 → 330（4.1 倍）、机器人中位存活 14.83 → 18.20 s、均值 18.83 → 26.98 s、脱战 22.70 → 29.00 次/局**，同时「1–4 只」从 3.6% 的帧升到 59.2%。**换算到这张账单上：每局击杀 0.83 → 3.44，首次击杀中位 12.87 s，零击杀局应当从 59.4% 掉到接近零 —— 也就是说这一条同时治「打不死怪」和「测试红」。** 代价必须说清：它也让**站桩的人**更安全（idle 中位 2.43 → 3.37 s），所以**比值中位反而从 6.10× 掉到 5.26×** —— 这是一个**全面放松难度**的改动，不是一次精准的修复（`180` 那个中间档更差，且这个旋钮的响应**不单调**，见 §14.2）。**它是世界级改动，所以不由我单方面拍板。**
  - **（b）改断言的量** —— 让它跨几条命取一次击杀机会，而不是把「一条命里必须开张」当成需求。**（b）单独做等于把测试改绿然后留下一个「机器人在多数局里一只怪也打不死」的世界**，那正是 §14.6 教训六（量结局，不要量过程）的反面：量尺要换，但换量尺不能替代回答数字本身是不是要的。

  三件事要不要做、做哪几件（只做（b）、只做 `senseRange`、还是两件一起），待你拍板。
- **最佳存活时间的持久化**：目前只在会话内保留。若要跨会话，需要引入 `localStorage` 或一个 Tauri 存储命令。
- **命中历史**：目前一次命中即锁定本局（与 Hex tab 一致）。
- **音效**：`src/game/config.ts` 已配置 `noAudio: true`（BTC 扫描器不需要 AudioContext），若加入音效需一并调整。
- **手柄 / 触屏**：目前仅键盘。
- **数值平衡**：§11 全部为拍脑袋的初值，需要实际手玩后再调。本次新增的曲线里有三处已知的、**刻意没有先加护栏**的地方，留给手玩决定：
  - **强化药剂的复利是双份。** `attackPower ×1.05` 与 `attackSpeed ×1.05` 同时生效，等于 DPS `×1.1025` —— 高于怪物血量的 `×1.05/min`。玩家长线会跑赢怪物，除非掉落速率或怪物密度同步上调。这是需求原文（「攻击力 ×1.05，攻击速度 ×1.05」）的直接实现，未擅自加封顶。
  - **怪物的 `moveSpeed` 从不增长。** 越到后期，玩家越容易靠走位脱离接触 —— 难度全部由血量与密度承担。
  - **属性乘数无上限。** `keymap.ts` 的 `SCALE` 分母（`moveSpeed` 320 / `attackSpeed` 4 / `attackPower` 64）是定值，堆到一定程度后属性会**饱和**该分母，字节归属的可读性下降（数值不再有区分度）。需要时在这里加一个软上限。
- **密钥推进速率与 IPC 负担。** 现在每个变化的仿真步都提交一次，上限是帧率（§9.4）。`derive_group` 是**同步**命令，跑在主线程上，所以这条路径的代价会直接表现为掉帧。目前已经有在途合并（同一时刻至多一个在途），**如果实测发现负担过重**，下一步是把触发点挪到场景已有的 4 Hz 统计回调上 —— 那只是换一个观测节奏，仍然没有速率常数，设计主张（密钥 = 世界状态的函数）不变。

## 14. 机器人模式

一个自动玩的玩家。它跟人类看同一块屏幕、拿同一份信息，**不多也不少** —— 多出来的那一份必须靠走近去换（需求第 5 条）。

它存在的理由不止是「好玩」：§3.4 之后密钥是**世界状态的纯函数**，没有时钟、没有 tick 计数。所以一个停摆的机器人会产出停滞的世界，也就产出极少的密钥 —— 「它在动」这件事是功能性的，不是装饰。反过来，一个能自己活下去的机器人让这个 tab 可以无人值守地一直产密钥，而它活下去的每一秒都是真实推进的字节。

### 14.1 感知：需求第 4、5 条的分界线

| 信息 | 来源 | 是否公开 |
|---|---|---|
| 怪物位置 `posX` / `posY` / `dir` | 画在场上 | **公开**（需求 4） |
| 怪物感知半径 `senseRange`（`m_range`） | 那个虚线圈 | **公开**（需求 4） |
| 怪物种类 `kind` | 剪影 + 颜色（§10.3） | **公开** |
| 怪物血量条 `hpFrac` | 伤害条 | **公开** |
| 怪物所在区域 | 地板上的区域边界 | **公开**（可推导） |
| 药剂位置 / 种类 / 剩余寿命 | 地上的剪影 + 闪烁（§10.3） | **公开**（需求 4） |
| 飞行中的炸弹：落点 + `blast` | 画在落点上的预警圈（§10.3） | **公开** —— 圈画多久，机器人就看见多久（§15.6） |
| 飞行中的子弹 | 画在场上（§10.3） | **公开，但策略刻意不用**（§15.6：人类也躲不掉，用它就是偷偷放宽这条边界） |
| 玩家自己的属性 | 就是自己 | **公开** |
| 怪物 `attackPower` | —— | **只在圈内**（需求 5） |
| 怪物 `attackSpeed` | —— | **只在圈内** |
| 怪物 `attackRange` | —— | **只在圈内** |
| 怪物 `moveSpeed` | —— | **只在圈内** |

「只在圈内」是**逐帧重算**的，不是记住的：`perceive()` 每帧从 sim 重新投影，`stats` 非空**当且仅当**此刻 `hypot(dx, dy) ≤ senseRange`。走进圈就公开，走出圈就收回，不需要一张记忆表、不需要一个类。这也是 `decide()` 能是纯函数的原因 —— 视图是机器人关于世界的全部知识，而视图里没有上一帧。

**雾是模块边界，不是约定。** `robot.ts` 从不 import `MONSTER_ARCHETYPES`，`PerceivedMonster` 里也**没有**任何可以装隐藏属性的字段，所以这个作弊在类型层面就写不出来。注意 `MONSTER_ARCHETYPES` 在 `sim.ts` 里是公开的 —— 强制不在那边，在这里：在这个模块愿意看什么。

**为什么 `kind` 公开却不查表。** 种类确实画在屏幕上，人类看得见；但策略**刻意不**由它去查每种原型的数值。陌生怪物一律按同一个保守假设处理（见下），靠走近去修正 —— 那正是需求第 5 条要买到的东西。如果 `kind` 能直接推出属性，需求第 5 条就作废了。

### 14.2 策略

```
1. threats   : dps = attackPower × attackSpeed, reach = attackRange
               （没公开就用先验：hunter —— 9.6 dps / 26 px / 120 px·s⁻¹）
2. riskAt(x,y): 对每只怪物，按以下两条规则求和
3. 选目标     : 全场取 argmax(群大小 × CLUSTER_WEIGHT − 距离 / CLUSTER_DIST)，
               记下胜者所在那一群的**质心**作为一个点。
               这个点要**锁住**（见下），不每帧重选。
4. 意图 + 目标方向（首个命中者胜）
     heal  血 < 0.62 且 药比威胁更近            → 朝那瓶药
     flee  脱离闩锁已置位（见下）                → 背离「附近威胁的质心」，并带切向环绕（见下）
     loot  最好的药得分 ≥ 0.35                  → 朝那瓶药
     kite  有威胁在 FARM_RADIUS 内              → 站到「不在它 reach 内、但在自己射程内」的环上，带切向环绕
     roam  以上都不成立                          → 朝选中的目标
   （kite 与 roam 的目标默认是第 3 步选出的那个点；但 PACK_RADIUS 内的威胁数在
     1..PACK_MAX 之间时，目标改指**最近的威胁本身** —— 见下面「引到了 1–4 只」）
5. 在 9 个输入上取 argmax：
     W · dot(位移方向, 目标方向) − clamp(风险增量) − 墙体惩罚 + 可躲空间 + 粘滞
     W = GOAL[intent]
     风险增量的被减数是「所在世界与所去世界里更危险的那个」（见下）
     粘滞只奖励重复上一帧的**非静止**输入（见下）
     可躲空间按候选**方向**给分，不按位置给分（见下）
```

**目标锁定（本轮新增）。** `pickTarget` 选出的那只怪只是一个**指针**，真正被记住的是它**所在那一群的质心**——一个世界坐标点，连同上一次锁定时机器的位置（路线的起点）。锁定一直保持，直到满足两者之一：

- **已清空**：锁定点 `CLUSTER_RADIUS` 内没有任何怪物。这就是用户说的「直到把目标区域的怪物们击杀」。
  > **但这一条在机制上几乎不可能单独成立。** 怪死在**自己的 home 区**按等级对应的间隔重生（§4.2；1 级 5.0s，之后只会更短），所以一片被打空的区域几秒内就会回填，而锁定点又恰好是全场最密的地方。实测下来锁定**总是**被下面那条偏离判据解除的。
- **已偏离**（用户给的规则）：以**建锁时机器人所在位置**到锁定点连一条线段，长度记为 `d`；机器人当前位置到这条线段的垂距超过 **`d / 3`** 即视为偏离。阈值是**相对的**，随路线长度缩放 —— 目标远时容得下更大的横向绕行，贴近时收紧。**必须配一个下限**：`d` 很小时（锁就在脚下）`d/3` 会小于机器人自己绕圈的半径，正常风筝每帧都破锁、等于没有锁，所以下限取站位环 `desired` 本身。

锁的作用是让 `kite` 的站位环、`ignoring`、`roam` 的方向指向**一个固定的点**，而不是每帧在分数接近的候选之间翻。

**但要如实说清它的量级：这一节修的是「去哪」，不是「稳不稳」。** 机器人 72% 的帧在 `flee` 里，而 `flee` **不读** `target`（它读 `dangerCentre`），所以锁定对抖动几乎没有作用。实测印证了这一点：把 `OBJECTIVE_DEVIATION_FRAC` 在 1/4 · 1/3 · 1/2 上扫 96 颗种子，最差种子 1.25× / 1.25× / 1.26×、逃离率 45.8% / 46.0% / 45.8%、反向 21 / 20 / 26 次 —— **全在噪声内**。用户给的 1/3 因此原样保留，不是因为它被实测选出来，而是因为没有证据反对它。抖动的主修是下面的 `HYST`。

**「引到了 1–4 只就该风筝」这一轮：两条留下、两条否掉，而否掉的那两条和「前提不存在」这件事才是这一节的主要产出。** 用户报的是机器人**打不死怪**，并且给出了机制上的诊断：

> 「引怪后，你没有让 robot 去坚持风筝怪的机制。换句话说，引到了 1-4 只怪后，就该风筝了：绕圈子走位（躲避引来更多怪，确保优先击杀已经引到的怪），而不是到处转悠引来更多怪物，更不能直接冲向怪物撞过去。」

这句话拆开来是四条可分别落地的规则。**四条都实现了，一条一条单独量**（96 颗种子，同机同世界，只有 `robot.ts` 不同，基线的 6.10× / 14.83 s / 80 击杀）：

| 臂 | 规则 | 比值中位 | 机器人中位 | 击杀 | `flee` 帧 | `kite` 帧 |
|---|---|---|---|---|---|---|
| — | 基线 | 6.10× | 14.83 s | 80 | 73.6% | 25.8% |
| a | 引到 1–4 只时**不进入撤退闩锁**（「确保优先击杀」，坚持打） | 5.42× | 13.87 s | 73 | 72.4% | 27.0% |
| **b+d** | 引到 1–4 只时**目标换成最近的那只**（优先打已经引到的） **＋ roam 档也走站位环** | **6.27×** | **14.18 s** | **81** | **68.1%** | **31.7%** |
| c+d | 站位环的**环绕方向避开会拉到更多怪的一侧**（「躲避引来更多怪」）＋ roam 档同上 | 5.58× | 13.30 s | 85 | 72.1% | 27.2% |
| b+c+d | | 5.83× | 13.50 s | **46** | 70.5% | 29.3% |
| a+b+c+d | | 5.71× | 14.40 s | 56 | 68.5% | 31.3% |

> **这张表的臂名要照实读：除了基线与 `a`，每一臂都带着 `d`。** `d`（`roam` 档也走站位环，而不是直冲锁定点）在这一轮里**从来没有被单独量过** —— 它一直和 `b` / `c` 搭在一起。**所以「留下 `b` 和 `d`」这句话里，`d` 那一半是没有独立证据的**：它留下来是因为它所在的那一臂（`b+d`）是最好的一臂，而不是因为它自己被隔离出来证明过。**这是这一轮的一个已知缺口，写在这里而不是含糊过去**，因为 §14.6 教训三（共享旋钮的网格量的是两个机制的和）说的正是这种事 —— 只不过那一次是旋钮共享，这一次是臂共享。

- **留下的是 `b`（`d` 见上面那条注）。** 它是唯一一条两个轴都不亏的：比值 6.10× → **6.27×**、击杀 80 → **81**、中位 14.83 → 14.18 s（−0.65 s，在噪声内）、而 `kite` 帧 25.8% → **31.7%**、`flee` 帧 73.6% → **68.1%** —— **它是这一轮唯一一个「意图组成真的变了」的读数**，方向正是用户要的（少逃、多对峙）。**「优先击杀已经引到的怪」这条按原样保留，但它在账面上的价值是「一次平手」，不是「一次改善」。** 规则落在 `decide` 里：`committed = 1 ≤ (120 px 内的威胁数) ≤ PACK_MAX`，为真时 `target` 由「群质心／锁定点」改指**最近的威胁本身**。不需要新的查找：`committed` 成立时 `nearest.dist ≤ PACK_RADIUS` 是构造性的。
- **`a` 被否掉，理由是它不是「更坚持」，是「更早死」。** 击杀 80 → 73、机器人 14.83 → 13.87 s、比值 6.10× → 5.42×。机制上可预期：引到 1–4 只时压制撤退闩锁，等于取消了「挨打就退到 60 px」这条唯一的硬性脱身路径，而 §14.2 已经论证过**脱战只剩拉开距离一条路**。用户要的是「坚持风筝」，不是「站着挨打」—— 风筝的径向那半本来就在 `kite` 的站位环里，闩锁管的是另一件事。
- **`c` 被否掉，理由是它的前提在机制上不成立，而且它与 `b` 放在一起会互相破坏。** 「躲避引来更多怪」要能成立，得先有「引怪」这个**可以躲开的动作** —— 而模拟里的仇恨**不是一个被触发的状态，是一条逐帧重算的不等式**（`m.attacking = dist <= m.senseRange`，§14.1 / §6.1，**没有闩锁**）：任何一只怪只要落在它自己的 `senseRange` 内，**这一帧就在追你**，出了圈就立刻不追。所以并不存在「某一侧会**拉**到更多怪」这回事 —— 只有「某一侧**当下就在**更多怪的圈里」，而那件事 §14.2 的风险场**已经在全额计价**（风险项没有任何拴区项，§6.2）。**这一条不是「量值不够好」，是它想躲的那个因果对象不存在。** 更直接的是 `b+c+d` 这一臂：两条本来各自看着无害的规则**放在一起把击杀从 81 砸到 46**（`c+d` 单独的 85 也保不住）。原因看得见：`circling: heading consistency` 从 0.19 掉到 0.16 / 0.13，**逐帧重新推导绕行手性**会与 `b` 的「改朝最近的怪」互相打，站位环的方向每帧翻，环绕散成抖动。这一条与 §14.6 教训三（共享旋钮的网格量的是两个机制的和）是同一类错误的两个方向：那一次是**一个**旋钮养着两档，这一次是**两个**规则抢**一个**方向。
- **而这一轮最重要的读数是：这几条规则要作用的那件事，在今天的世界上几乎不出现。** 按模拟自己的仇恨判据（`dist <= m.senseRange`，§14.1）统计机器人在**每一帧**被多少只怪盯上，再按 1–4 / 5–8 / 9+ 分桶：**1–4 只只占全部帧的 3.6%，9+ 占 72.7%**（平均 9.67 只、峰值 21）。也就是说用户描述的那个状态 —— 「引到了 1–4 只」—— 是一个机器人**很少待在里面**的状态，所以为它写的规则自然什么都换不动。**换一个更宽松的读数**（120 px 内的「贴上来的」怪，复用 `CLUSTER_RADIUS`）确实是「引到了 1–4 只」的更贴近的读法，它占 **36.0%** 的帧；但**按严格读数设阈（3.6%）几乎从不触发，等于一段披着规则外衣的死代码**，而按宽松读数设阈虽然会触发、触发的却不是用户说的那个集合（36.0% 是「贴脸」而非「被引」）。**两个读数都不给它一个能工作的定义域** —— 这是否定这一整类规则的真实理由，不是「量值不够好」。**`PACK_RADIUS` 那条注释记的就是这个两难，而这一轮的实现选了会跑的那一个读数（120 px），代价是它的贡献停在一次平手。**
- **几何上的解释，也是这一轮最该记住的一句话：大群仇恨是这个世界的地形属性，不是策略的属性。** 一只追猎者的 `senseRange` 是 **260 px**，而场地是 960 × 540；一个 260 px 半径的圆占**地板面积的 41%**。所以**在没有任何聚集发生的前提下**，光靠面积就能推出机器人身旁常驻约 5 只盯上它的怪 —— 上限（36 只）与收敛（怪朝它走）只把这个数往上推。**「机器人被 9 只怪围着」不是它引怪引坏了，是这个半径相对这个场地本来就装得下这么多。** 下面这条探针把这句话从推理变成了测量。

**把「真正的杠杆是仇恨半径」这件事做成可测的，而不是断言的。** 上面那段推理如果只是推理，它就只是又一个说得通的故事（§14.6 教训一整段都在讲这种故事有多贵）。所以这一轮给 sweep 的 `SWEEP_OVERRIDE` 加了一个 `M.` 根，让它能改 `MONSTER_ARCHETYPES` 而不是 `ROBOT` —— **这是一次测量，不是一次世界改动**（`sim.ts` 没动）。96 颗种子，只动追猎者的 `senseRange`：

| 追猎者 `senseRange` | 盯上机器人的均值 | 1–4 只的帧 | 9+ 的帧 | 击杀 | 机器人中位 | 机器人均值 | 比值中位 | 脱战/局 |
|---|---|---|---|---|---|---|---|---|
| **260（现状）** | 9.67 | **3.6%** | **72.7%** | 80 | 14.83 s | 18.83 s | 6.10× | 22.70 |
| 180 | 6.00 | 32.5% | 18.4% | 82 | 13.60 s | 15.02 s | 3.88× | — |
| **140** | 4.49 | **59.2%** | 3.7% | **330** | **18.20 s** | **26.98 s** | 5.26× | **29.00** |

**把半径从 260 收到 140，击杀涨 4.1 倍（80 → 330），机器人自己的存活同时变长（中位 +23%、均值 +43%），脱战次数也涨（22.70 → 29.00）。** 而且**多出来的击杀几乎全部来自那个状态**：330 次里 1–4 只的桶贡献了绝大多数，该桶的击杀密度是 **3.1 次 / 千帧**，而基线全场是 1.5。用户说的「1–4 只就该风筝」在这个世界里**成了多数帧的状态（3.6% → 59.2%）**，而机器人**不需要新规则** —— 它原有的 `kite` 档直接把这个状态换成了击杀。**这同时证明了反过来的一半：风筝机制本身是好的，缺的是让它有机会上场的地形。**

> **这一格（`140`）的数字有一个必须自己说出来的读法陷阱。** 比值中位从 6.10× **掉到** 5.26×，看起来像变差了，而分子分母**两个都在涨**（机器人 14.83 → 18.20 s、idle 对照 2.43 → 3.37 s）—— 半径变小，连**站着不动的人**也活得更久（少挨枪）。这正是 §14.5「比值只在同一世界内可比」那条规矩的第三次兑现：**这里必须读绝对秒数，比值是误导的。** `180` 那一行则是另一个方向的意外：比值中位塌到 3.88× 而击杀一步没动（82），机器人中位反而比基线更短 —— **这个中间档比两端都差，我查不出机制，如实记在这里，不要把它读成一条曲线上的点。** 三行一起看：这个旋钮的响应**不单调**，所以「再收一点会更好」是一个没有依据的猜测。

**风险场。** 两条规则承载了整个策略：

- **没有拴区项了。** 这一条曾经是「一只怪物对它自己辖区之外的位置贡献为零」。拴区解除之后（§6.2）**每一只感知到的怪物、在每一个候选位置上，都全额计价**，风险场因此处处抬高。这是本轮最重要的一处世界变化，也是抖动之所以致命的原因：风险项的摆幅到处都是满的。边界不再是机器人手里的一步棋，**脱战只剩下拉开距离一条路**（§6.2 那 3.9 秒）。
- **接近度曲线。** `dps × CHASE × proximity`。`proximity` 在 `reach` 处为 1、在 `senseRange` 处为 0，进到 `reach` 以内则随距离缩小继续爬升（`1 + PROX × …`）。**必须是连续的、且对 `d` 单调的**：早期版本在 `reach` 以内给 `dps`、以外给 `dps × CHASE`，于是向内越过 `reach` 反而让风险**下降** `2.4 × dps` —— 风险场悄悄付钱让机器人踏进蛮牛的攻击范围。`kite` 的站位环把它盖住了，这正是它值得被删掉而不是被调参的原因。`FALLOFF` 取 0.4（小于 1，凸曲线）：线性斜坡会让「离蛮牛 50 px」看起来几乎免费，而它离挨打只有一步。
- **炸弹项**（§15.6）。飞行中的炸弹按 `damage × BOMB_WEIGHT × CHASE × proximity` 计价，位置取**落点**而不是弹体现在在哪，半径取 `blast + playerRadius`。它与怪物项有两处刻意的不同：**半径处硬截断**（圈外确实是零），**不看引信**（危险的是那个圈，不是还有多久落地 —— 那正好也是画面能读到的全部信息）。这一项只活在候选打分里，见下面两条「基准分」。

**风筝的站位环。** `desired = clamp(ourRange − STANDOFF_MARGIN, target.reach + BAND, ourRange − 2)` —— 既在目标 `reach` 之外、又在自己射程之内，因为只有玩家的攻击是自动的、怪物得走过来（§5.1），这个环就是全部战术。按当前数值 `ourRange − 4 = 51` 总是压过 `reach + 8`（最远的蛮牛 reach 才 34），所以下界是留给「怪物 reach 涨到接近玩家射程」那一天的兜底，不是现在生效的项 —— 而且它是把环推向**外侧**，也就是失败时安全的那一侧。修正量是**比例的**而不是一个符号：在环上径向项归零，于是机器人环绕而不是在「进」和「出」之间打摆子。

误差的归一化是**不对称的**，这一条承重，而且两侧的带宽各有各的道理：环外按「我们离**自己射程**还有多远」饱和，环内按目标自己的 `reach` 饱和。用单一半宽 30 时，径向项在蛮牛的 `reach` 处只有 0.567 —— 比 0.6 的切向项还弱，于是机器人一边挨打一边绕着怪物转圈，实测接触帧里只有约 27% 能把距离拉开。按 `reach` 饱和意味着「目标开始真正打到你」的那一刻退避正好满格，径向项（1.0）于是压过切向项（0.6），而它必须压过。切向偏置的方向由「哪边同时更靠近场地中心」定 —— 这是阻止一场风筝把自己螺旋进角落里死掉的东西。**这个「朝中心定向」的规则现在两档共用**（`kite` 用 `ORBIT`、`flee` 用 `FLEE_ORBIT`），而它在 `flee` 上是**逐次撤退锁一次**而不是逐帧重算：`kite` 的参照是单只怪的方位、很稳，`flee` 的参照是质心、会漂，而切向向量一旦相对中心方向转过 90° 符号就会翻 —— 那就是振动的另一种形态（见 `RobotState.orbitSign`）。

**环外的带宽原本是 `KITE_BAND` 30，那是同一个错误的另一面 —— 只是没人往那个方向量过。** 误差 30 意味着径向项要到环外 18 px（也就是离目标 69 px）才追平切向项 0.6。而玩家射程只有 55 px —— 于是**机器人会永远停在自己的射程之外绕圈，一次都不出手**：实测在一个不动的怪物身上，它稳在 58 px 处环绕，射程 55。改成按 `ourRange − desired`（即「我们还在自己射程之外」这一段的宽度，当前取值 4 px）饱和之后，整个接近过程中径向项都是满格，什么时候停由环决定、而不是由切向项决定。实测：接触帧 51369 → 40939（少了两成），拉开距离的比例 65% → 66%，而生存分布一格没动。`KITE_BAND` 因此成了一个死常数，已删除。

**风险是增量（`riskAt(next) − riskAt(here)`），不是绝对值。** 这条是承重的：机器人躲不掉的环境风险不应该让它瘫痪，所以只有**变化**可以操舵。改成给绝对风险打分，机器人一进密集场地就会原地冻死。

**而炸弹要活在增量里，就必须出现在「脚下」那一项 —— 于是这里有两个基准分，它们对炸弹的态度刻意不同。** `hereRisk` 服务于两个承诺门（撤退闩锁的进入与 `DISENGAGE`），它**排除**炸弹：一发落在脚下的炸弹在圆心能读出 `18 × 3 × 2` = 108，远在任何门槛之上，而它值得的反应是「挪两步」而不是「放弃整个区域」。`hereForScore` 服务于候选打分，它**包含**炸弹：基准分里没有那发炸弹的话，「从炸弹下面走开」会和「一动不动」打平，而平局按规则判给静止 —— 机器人会站在炸弹里等它落地。

**增量的第一个代价还在：参照点就是脚下，所以「不动」的增量恒为 0 —— 它是一个有特权的零**，每一次平局都判给它。

**第二个代价换了内容，而换成的这一条是本轮的关键发现。** 曾经的代价是拴区项造成的**空间阶跃**（跨过边界一次点亮 55 的风险，被 `RISK_CAP` 削平）。拴区没了，阶跃也没了 —— 但取而代之的是一个**处处都在**的问题：风险项的摆幅与目标项的摆幅不成比例。

**这个比例关系值得单独记下来，因为它是抖动这一整类缺陷的通用判据，比任何一次调参都重要：**

| 项 | 摆幅 |
|---|---|
| 目标项 `W · dot(…)` | `GOAL[intent]` 6 × \|goal\| ≈ 1.166 → **约 7.0** |
| 风险项 `clamp(Δ)` | ± `RISK_CAP` → **±12** |
| 抗抖动（总承诺） | 当时是 `HYST` **1.5** + `MOVE_MARGIN` **2** → **3.5**（= 风险摆幅的 29%） |

**角落计价那一项（`TRAP_WEIGHT`，见 §14.6 三）是这张表上的一个新形状：它乘在风险上，所以它改的不是摆幅的上限，而是摆幅到达上限的频率。** 角箱里最多 11 倍，于是 `clamp(Δ)` 在那里**必然**削平 —— 也就是说在角附近，风险项从「给方向定价」退化成「一律否决」。这是刻意要的（那一格的目的就是让角不可住），但它有一个必须记下来的后果：**角落附近的目标项完全失去了发言权**，机器人在那里只按风险场走。角落计价的全部收益与全部代价都发生在这一区域内，而它只有 70×70 px。

风险项的摆幅是目标项的 **1.7 倍**，而唯一的抗抖动项只有风险摆幅的 **29%**。40 px 的探针落在一个 5–7 只怪常驻（峰值 18）的风险场上时，相邻两个候选方向的分差经常接近整个 ±12；两只怪从相反方向拉扯时场上存在一个**鞍点**，而鞍点随怪移动，候选便在半数帧里从一侧翻到另一侧。测出来的结果就是：**每局 90 次方向反向、最长不间断直线跑只有 1.37 s**。而脱战需要 3.9 s（§6.2）—— 所以那不是「撤退得不好」，是**根本没有撤退，只在原地振动**。

**修法是抬高承诺，而不是压低风险项。** 这一条反直觉，值得记下为什么：压低风险项（`RISK_CAP` 12 → 8 → 6）在 96 颗种子上反而**更差**（中位 2.46× / 1.84×，都是负收益），因为风险项是机器人活下来的唯一原因。抬高承诺则直接对症：总承诺 3.5 → **8** 把反向从 90 次压到 **20 次**、最长直线跑从 1.37 s 抬到 **2.95 s**。代价是逃离率从 66.1% 掉到 46.0% —— 一个「认准方向」的机器人对贴到身上的怪反应得更少。生存中位和最差种子**都没有变差**（见 §14.6 的两个数字），所以这个交换是划算的，但它是一个交换，不是纯赚。

**那 46.0% 是当时的世界里的数，而这一轮的可躲空间项把它买回来了一大半 —— 回到 56.9%。** 值得把它记清楚，因为这**不是**「承诺调错了、后来调回来」：两者治的是同一个病的两端。承诺治的是**方向不稳**（反向 90 → 20，直线跑 1.37 s → 2.95 s），可躲空间治的是**位置不好**（33 px → 49 px 净空）。只调承诺时机器人学会了认准一个方向，而那个方向经常是沿着墙的；给它一份「往里去」的正收益之后，它认准的方向才变成值得走的那个。今天这两个数与承诺单独作用时的数不可比 —— 要比较就必须在同一世界里量，这也是 §14.5 记的规矩。

**「总承诺」这个词是这一轮量出来的，不是修辞。** 它当时由两个常数相加：`HYST`（奖励重复上一帧方向）与 `MOVE_MARGIN`（上一帧方向在打平时多得的余量）。两者都是**同一个分数单位下、给同一个候选的同一笔奖励**，所以机器人只感受到它们的和。实测把这一点钉死了：`HYST` 6 + `MOVE_MARGIN` 2 与 `HYST` 8 + 无 `MOVE_MARGIN`，在 96 颗种子上、八项统计上输出**逐字节相同**。于是 `MOVE_MARGIN` 被删掉，`HYST` 提到 8 独自承担全部承诺 —— 一个活儿两个旋钮，就是多了一个旋钮。**这类「两个常数其实是同一件事」的重复，本文件里已经出现过两次**（另一次是 §14.2 那条从未运行过的释放，见下），两次都是靠**输出逐字节相同**发现的，而不是靠读代码看出来的。

**「什么都不做」赢下这些竞标，曾经是用户那条报告的真正机制。** 当时的实测：723892 个「自己射程内没有怪物」的帧里 **72.4% 是静止的**，只有 14.6% 真的在靠近最近的怪物，而逐帧拆开那些静止帧的打分，**166863 / 166919 是被风险项挡下的**，其中 96% 的探测跨了区界，把中位数 4 只原本被拴住的怪物一次点亮。那一轮堵了三个出口：

- **被追的目标本身也在风险项里**（现在仍然是）：一个「朝它走过去」的候选要同时为「它在追我」付钱，而它正是唯一想靠近的东西。环已经是这只怪的安全契约，所以**接近期间把目标自己**从风险项剔除，其余每一只照常计价 —— 目标站在怪堆里时，仍然是怪堆把它拦下。
- **换辖区被当成了「走向危险」**（**已随拴区一起消失**）：`hereRisk` 在 A 区求和、`riskAt(next)` 在 B 区求和，跨一步等于把两个不同集合相减。修法是被减数取「所在世界」与「所去世界」中更危险的那个。拴区没了之后两个集合**恒等**，这整套被减数逻辑已删除。
- **选错了目标**（**已随拴区一起消失**）：`pickTarget` 曾先只在自己辖区内选，自己辖区空了才放眼全场。`pickTarget` 现在**不过滤辖区**。

那一轮的结果是静止帧 71.2% → 54.9%、击杀 7169 → 22504（3.1×）。**但拴区一解除，静止就换成了振动**：空闲帧低到 4.3%，可是反向 90 次/局、最长直线跑 1.37 s —— 机器人不站着了，改成在原地抖。修法是本节的 `HYST` 与 §6.2 的脱战机制凑到一起才成立的。

**`CHASE` 是唯一真正要紧的常数。** 它是「站在有东西追我的地方」和「走向我想要的东西」之间的汇率。太高 → 拒绝交战、饿死；太低 → 走进怪堆。48 颗种子上的实测：生存率随它单调上升到 3 左右后走平，此时中位数达到「原地不动」的约 7 倍，而且 —— 因为更大的风险场意味着**更多风筝而不是更少** —— 击杀数**上升**。这里其它每个常数在它旁边都是装饰。

**陌生怪物用 hunter 做先验，而且只有一个先验。** 这是整个雾设计里最承重的一个选择。需求第 5 条存在的意义是让「接触」**买到**东西，而只有当无知**真的变贵**时才会如此 —— 所以先验不能是平均值，更不能是最弱的那个。假设都是软柿子 → 它会一头撞进蛮牛；假设都是最坏的 → 它永远不交战、饿死。hunter 是中间那档，也最可能是正在朝你逼近的那只。

**脱离是一个闩锁，不是一条阈值。** 一只 hunter 在 `reach` 内把风险抬到 9.6，往外 30 px 就掉到 2.9。一个「在这个数开始逃、在那个数停止逃」的 bang-bang 控制器会每半秒掉一次头，永远走不到两百多像素外的任何安全地方 —— 实测就是这样死的，死在半路，一边抖一边死。所以 `RobotState` 里有一个 `retreating` 布尔：进入容易，退出要求风险**真的**消失。

**本轮把闩锁的两端都改成了局部的**，因为旧的两端都是「对**全场**怪物的**和**」取的阈值，而那些阈值随怪数一起漂：

- **进入**：`nearest.dist <= nearest.reach`（**接触** —— 怪真正打得到你的那一刻）**或** `hpFrac < FLEE_HP && nearest.dist <= DISENGAGE_RADIUS`。
- **退出**：`nearest.dist > FLEE_RELEASE_DIST`（60 px）**或** `hereRisk < KITE_SAFE_RISK`。

进 ≤26、出 >60，方向正确、在人群里可达，周期健康：在 51 px 的站位环上打 → 挨打就退到 60 → 回到环上。实测的形态正落在这个区间里：96 颗种子产生 294 次闩锁进入（约每局 3 次），中位时长 2.15 s，**98.7% 的 `flee` 帧落在 ≥0.5 s 的片段里** —— 上面警告的那种「每半秒掉一次头」的 chatter 没有回来。

第二条进入条件（残血 + `DISENGAGE_RADIUS`）守的是另一个真实陷阱：只看血量就逃的话，血在回满前一直低，于是一个残血、最近的怪却在 240 px 外**且没注意到它**的机器人会永远逃一个不存在的东西，而不是去捡药或回血。`KITE_MAX_RISK`（9）留在 `loot` 档守门 —— 「风险高过这个数就不绕路去捡强化药」—— 而且刻意**管不到 `heal`**：一瓶回复药对残血机器人不是可选项。**早退、常退**才是既活得久**又**拿分多的做法。

**改动前的闩锁是「一进不出」，而那是 bug 不是调参。** 旧的进入条件是 `hereRisk > PANIC`，而 `hereRisk` 是对**每一只**感知怪物的**求和**，所以它描述的等高线半径随在场怪数增长（2 只猎手 141 px、3 只 217 px、5 只 248 px）；退出的 `hereRisk < KITE_SAFE_RISK` 落在同一个随人数漂的半径上。场上常驻 5–7 只怪，于是机器人几乎每一帧都在等高线内，**没有任何固定距离能落在它外面** —— `FLEE_RELEASE_DIST` 调多大都没用。实测：96 颗种子一共只有 **102 次**闩锁进入，`flee` 占全部帧的 **96.1%**。那不是一段一段的撤退，是一整局不间断的撤退。

**另有一处真 bug，值得记下来因为它差点没被发现**：释放条件曾经写成 `if (threatened) … else if (…)`，所以它**只在没有受威胁的帧上才会执行** —— 而在真正需要释放的人群里，每一帧都受威胁。这条释放从未运行过。发现它靠的是一个异常：修完之后 sweep 的输出与修之前**逐字节相同**。改成一对方真正的迟滞之后就正常了。`PANIC` 这个常数随之删除。

**`heal` 排在 `flee` 上面，而且它差点是死代码。** 顺序的理由是：一个残血、脱战、又什么都不捡的机器人没有回头的路 —— 回血只有 1 hp/s，血量会一直低于脱离阈值，于是它逃到死，死在药旁边。但「去拿药」只在药比威胁**更近**时才对，所以那一档额外用距离守了一道。

而它一开始**根本没触发过**：拾取评分只跟踪了一个「场上最值钱的东西」，于是一瓶强化药剂可以轻松压过一瓶回复药，**悄悄否决**了残血机器人的取药行程。实测在 24 局种子里 `heal` 档命中 **0.0%** 的帧 —— 一条穿着规则外衣的死代码。修法是分开跟踪两个赢家：`best` 回答「场上最值钱的是什么」（`loot` 档的问题），`bestHeal` 回答「最近的药在哪」（`heal` 档的问题）。修完之后它**仍然**是 0.0%，但这次理由正当：血量分布显示机器人 74.1% 的帧在 90% 血以上，只有 3.1% 的帧低于 0.62 —— 而那几个帧里地上恰有回复药的概率是 0.01%。也就是说这一档不是接错了线，只是这个策略很少受伤。修法保留了，因为它移除的是一个真实存在的否决。

**`flee` 上一轮被收窄成纯局部脱离、避难区整个删掉；本轮把它的切向那半装了回来 —— 而这两件事并不矛盾。** 用户对这一档的要求是明确的：「flee 只做局部脱离」。曾经的目标是「径向分量 `FLEE_RADIAL = 1` ＋ 切向分量 `FLEE_ORBIT = 0.6`，切向负责把路线弯向**最安全的区域**」，上一轮两半都删了：

- **切向那半** 走的原因就是用户那句话：它一路把撤退导向**跨场地**的避难区，而那不是「局部脱离」。拴区解除之后「哪个区域最安全」也不再是任何东西的避难所 —— 它只是一个**此刻人少一点的地方**（§6.2）。
- **径向那半的参照点**换了。它原本是 `nearest`（逐帧 argmin），而 `nearest` 在人群里每秒换身份约十次，每次换名次都把逃离方向翻转最多 180° —— **那正是振动**。换成**附近威胁的加权质心**（`dangerCentre`，权重取 dps，半径复用 `DISENGAGE_RADIUS` 220）之后，两只怪交换名次时质心几乎不动，而 argmin 会瞬间翻向。

**用户第二次报同一个现象时（§14.6 三），删切向这件事被重新审了一遍，结论是它删错了对象。** 那句话禁止的是一个**跨场地的目的地**，而跨场地的从来只有避难区那**一个点**；绕着一个威胁转圈是相反的 —— 它是**局部受限**的机动。所以本轮把切向拿回来，但**不接任何区域**：方向改由「哪边同时更靠近场地中心」定，那不是「去哪儿」，只是两条切线之间的一次打破平局。参照点仍是 `dangerCentre`，也就是**比它当年拥有的那个参照严格更好**（当年取自 `nearest`）。径向本身仍是满格 1.0，只是切向被放大到 1.2 之后它占整步的比例降到 1/hypot(1, 1.2) = 64% —— 退避仍在真拉距离，方向弯了，向外的分量是「够用」而不是「最大」（这个取舍凭什么成立，见下表的实测与脱战次数那一段）。

**为什么切向在这一版战斗系统里是正解，而不只是好看（§7 / §15.1）。** 子弹射向玩家**开火那一刻所站的位置**，没有预判也没有追踪，所以有一个**飞行窗口**：从 51 px 的站位环射出是 0.182 s（280 px/s），玩家 160 px/s 在这段时间里走 **29.1 px**，而命中阈值是 `playerRadius 9 + bulletRadius 2.5 = 11.5 px`。
- **切向**移动 → 偏离火线 29.1 px > 11.5 px，**躲开**；
- **径向**退避 → 留在火线上，子弹以 280 − 160 = **120 px/s** 的净速度仍然追上，**照样命中**。

也就是说纯径向的 `flee` 恰好是**最差**的躲法（沿着火线后退），而「放风筝」在这个系统里是机制上的正解。用户凭手感给出的方向与机制一致。

**量出来的效果（96 颗种子，见 §14.5 / §14.6 三）：**

| `FLEE_ORBIT` | 贴墙帧（中位） | 净空 | 5–15 s | 15–30 s | 30 s+ | 中位存活 | 手性一致性 |
|---|---|---|---|---|---|---|---|
| 0.0（本轮对照＝纯径向） | 58.6% | 82 px | 63.5% | 75.8% | **100.0%** | 14.13 s | 0.11 |
| 0.6（拆分前的共享值） | 60.4% | 83 px | 66.9% | 67.4% | 64.4% | 13.60 s | 0.11 |
| 0.9 | 60.2% | 83 px | 64.8% | 64.8% | 63.4% | 16.68 s | 0.13 |
| **1.2（本轮落定）** | **57.9%** | **90 px** | **58.7%** | **61.4%** | 73.3% | 16.77 s | **0.17** |
| 1.5 | 56.5% | 91 px | 57.7% | 65.9% | 72.8% | 17.07 s | 0.14 |

**先说这一轮真正修好的那一件事：末端塌陷。** 对照臂（0.0）的贴墙比例随局时长**单调上升**到 30 s 后的 **100%**、净空从 98 px 一路掉到 **14 px** —— 这正是用户报的病，而且是终局性的：跑到最后它一定在墙上。1.2 之后这条曲线被压平，30 s 后停在 73.3% / 62 px。**这是本轮唯一一个「缺陷消失」级别的结果**，其余都是量的改善。

**而「兜圈子」本身只做到了一半，必须说清楚。** 手性一致性 `|Σdθ| / Σ|dθ|`（1.0 = 稳定单向环绕，0.0 = 来回抖）只从 0.11 抬到 **0.17**，最好的一档也没到 0.2。也就是说机器人**没有**进入一个持续的单向环绕轨道；它的收益来自切向那半把「墙棘轮」打断（贴墙时不再只剩下沿墙的一维滑动），而不是来自真的绕圈。1.5 那一档一致性反而掉回 0.14、反向涨到 22 次，是**过冲**而不是更多环绕 —— 所以 1.2 是拐点。

**环绕没能变成持续轨道，原因在 `flee` 与 `kite` 之间的振荡。** `flee` 在 220 px（`DISENGAGE_RADIUS`）放开、`kite` 把它拉回 51 px 的站位环，于是它在这两档之间来回换，一次撤退内根本转不满一圈。要拿到真正的环绕，下一根杠杆是给 `flee` 的**径向加饱和**（照 `kite` 的 `err`，把退避终止在一个环上）——**那正是用户没有选的方案 B**，本轮按计划不做，记在这里作为已验证的下一步。

**「更强」与「更弯」是两回事，这一轮把它们分开了。** 抬高环绕同时会抬高目标的**量值** `hypot(1, orbit)`（1.2 → 1.56 对 0.6 → 1.17，强 34%），而目标量值本身就是 `GOAL.flee` 管的事。用「量值相当」的两臂对照：`GOAL.flee` 8 + `FLEE_ORBIT` 0.6（6 × 1.562 ≈ 8 × 1.166）**什么都没买到** —— 贴墙 61.6%、净空 83 px、存活 14.52 s，全部不优于 0.6 基线；而 `GOAL.flee` 6 不动、只把 `FLEE_ORBIT` 抬到 1.2 就拿到 57.9% / 90 px / 16.77 s。**做功的是形状，不是量值。** 这也是为什么本轮把常数**拆开**而不是改共享的那个：拆分前那个「共享旋钮 1.2 大幅改善」的网格，其实主要是 `kite` 的功劳（见 §14.6 三）。

**还有一条静态推理被实测否掉了，值得留在这里。** `hypot(1, f)` 会分掉向外速度，所以 160/hypot(1, 0.9) = 119 px/s 已经低于猎手的 120 px/s，照 §14.5 那个「40 px/s 净差下约 3.9 s 脱战」的算法，0.9 以上应当**永远脱不了战**。实测相反：每局脱战次数随环绕**上升**（17.1 → 17.3 → 21.2 → 21.7），按存活秒数归一后基本持平。原因是这个 sim 里的怪物从来不做干净的直线追击 —— 它们按 `wanderSpeedScale` 走、按八方向吸附、追到 `attackRange × 0.7` 就停（§6.2），所以脱战由侧向几何决定，不由净直线增益决定。**静态模型记在这里，是为了让下一个人不要重新推一遍再照着它改。**


**墙。** 贴墙本身就该罚：它拿掉了风筝需要的退路，而角落是跑局结束的地方。惩罚按每轴平方，所以开阔地几乎免费、角落里压过一切 —— 它换掉的那个线性版本太弱，压不住一个朝外的目标方向。还有一个配套的「目标滑墙」：目标指向机器人**已经贴着**的那面墙时，把那个分量归零，否则每个服务它的候选都退化成原地不动，而原地不动风险增量为 0，于是稳赢所有要付代价的真动作。

**但墙这一项是「否决」，不是「操舵」—— 而用户在实机里看到的正是这个区别。** 他的报告是「机器人跑到了边界区域后，只会沿着边界移动，导致缺少躲避的空间」，量出来比听上去更极端：**85.3% 的帧落在离某条边 70 px 以内，到最近边的平均距离只有 33 px** —— 那比一次炸弹躲避需要的 41 px（`bombBlast` + `playerRadius`，§15.3）还小。它不是「漂到了墙边」，是**住在那里**。

机制上这不是因为罚得不够重：40 px 探针上这一项最多摆动 10 分（跨出墙带不扣、跨进去扣满），够重了。缺的是**拉**。罚项一旦还清就不再收费，而已经付过的罚不构成再迈一步的理由。本轮之前，分数里**没有任何一项**为「往里去」付钱：

- **朝外**这条路被 `flee` 的径向目标和墙带外的安全区一起推着，而滑墙又把朝外的目标分量归零 —— 朝外没有被罚的理由，只有被删的理由；
- **朝里**是怪物所在的方向，于是风险项**收费**；
- 剩下唯一既不挨罚也不收费的方向，就是**切向** —— 而那个残量**就是**「沿着边界移动」本身。

**`ROOM_WEIGHT` 就是补这份正收益的那一项**，而它的形状是承重的。它算两件事、取小者：**跑道**（沿候选方向的射线到边界的距离）与**侧向空间**（两个垂直方向到边界距离的**小**者）。取小者是关键 —— 贴着墙平行推进的机器人，有一个垂直方向正对着那面墙，所以侧向空间等于它离墙的距离，而「半个躲避不算躲避」。这就是为什么**沿着墙走**的得分**低于**往场地里走：在 33 px 处，平行推进的侧向空间是 33 px，而朝里的侧向空间是 270 px。按 `ROOM_REF` 饱和则保证它在开阔地**完全没有意见** —— 不加这个饱和，场地自己的长宽比（中心处长轴 480 px、短轴 270 px）会让每一个开阔地的决策悄悄变成对长轴的一票，那是没人要求过的转向。

实测（96 颗种子，`ROOM_WEIGHT` 0 → 4）：到最近边的平均距离 **33 → 49 px**、贴墙帧 **85.3% → 75.6%**、逃离率 **46.0% → 56.9%**，而且**打得更好了** —— 击杀 175 → 194，生存的每一个次序统计量都不低于基线。权重再往上抬，这份收益基本买完了（6 → 53 px / 55.8%，10 → 63 px / 57.1%），代价却开始出现：10 会把机器人从战斗里拉走（击杀掉到 138）、把承诺的直线跑压到 1.85 s，而 **8 是那个「最差种子比原地不动死得更快」的点（0.82×）**。被钉在墙上是要命的，**自由**也不是免费的。同理 `ROOM_REF` 也量过：放宽到 140（让它在 140 px 外就有意见）在它被造出来服务的每一项上都更差（49 → 46 px、56.9% → 53.4%），最差种子掉到 0.72×。

**而上面那个「抬到 10 就掉击杀」的代价，有一半不是这一项的错，是它在错误的帧上也在说话 —— 所以权重按意图分了两档（`ROOM_WEIGHT_FLEE`）。** 那个代价来自这一项与 `kite` 争执：`kite` **想要**待在离怪群 51 px 的站位环上，而「往里去」的正收益恰好要把它推开，两者在开阔地上互扯，于是机器人被从战斗里拉走。但用户报的那个缺陷不在这里 —— 它在 `flee`。**这一档是五个 rung 里唯一目标可以指向场外的**（kite 锚在站位环、loot 锚在掉落物、roam 锚在某只怪，而 `flee` 背离的是危险质心，那个方向可以刚好朝墙），它占了 70% 以上的帧、贴墙帧里更是 77.3%。所以分成「有异议的那一档」与「有缺陷的那一档」：

> **这句话在下一轮被精确化了一次，不是被推翻。** `flee` 的目标后来长出了一个**朝场地中心**的定向规则（见 §14.2 的环绕），但它**不是**一条场地参照：它只用来在两条切线之间**打破平局**（哪一侧同时更靠近中心），不构成一个可去的地点，也没有改变「背离危险质心」这个方向的量值。上面那句「唯一目标可以指向场外」因此仍然成立 —— 一个背离场内的向量仍然可以指向场外，环绕只是让它在指向场外时**开始转弯**。

96 颗种子（中央出生）上的网格，`4` 那一档等于分档失效（`ROOM_WEIGHT_FLEE === ROOM_WEIGHT`）：

| `ROOM_WEIGHT_FLEE` | 贴墙帧（逐种子中位） | 净空 | 中位存活 | 最差种子 |
|---|---|---|---|---|
| 4（不分档） | 63.9% | 77 px | 15.57 s | 2.82× |
| **6** | **58.6%** | **82 px** | 14.13 s | 2.10× |
| 8 | 57.0% | 85 px | 13.23 s | 2.10× |

**过了 6 就在平掉**（3 px 换 0.9 s），所以 6 是拐点。而**这笔买卖的规模只有 32 颗种子那个网格说的一半**（那一版给 8 读出 53.5% / 86 px）—— 小样本骗人的两种方式这一轮都撞上了，记在 §14.6（三）。

**对角线不再更快，归一化本身就是一处修复。** `stepSim` 曾经用 `(dx, dy) × moveSpeed × dt` 移动玩家、**不做归一化**，而怪物沿单位向量走 —— 于是斜向实测 226.3 px/s 对正交 160.0 px/s，人类按住两个键就白拿 41%。那不是「手感」，是 `moveSpeed` 这个数在斜向上根本不成立；用户报的「移动跟瞬移一样，明显不符合它的 moveSpeed」就是它。现在按 `Math.hypot` 归一化，八个方向实测都是 160.0 px/s。机器人这边配着一处旧缺陷：候选的探测步长曾经直接取 `(c.dx, c.dy) × step`，于是斜向探 56 px 而正交只探 40 px，跨边界的概率高得多 —— 而跨边界会让风险项饱和，于是**每一个斜向候选都被否决**，实测 172991 个移动帧里斜向被选中 **0.0%**。现在探测步长同样归一化。

**粘滞只奖励「重复上一帧的移动」，静止被排除在外。** 那个奖励的存在意义是压住两个**相反方向**之间的反复横跳，而那是只有移动中的机器人才有的问题；静止不是那两个方向之一，也不缺这份帮助 —— 严格 `>` 的平局规则本来就把所有真正无差别的帧判给它。如果它把静止也算进去，就会赢下它本不该参与的竞标：`lastDx` / `lastDy` 的初值 `(0, 0)` **恰好就是静止那个候选**，于是从每一局的第 0 帧起静止白拿这一整份承诺分，每次停顿又把它赚回来一次。

**而这个奖励的大小是承重的，本轮把总承诺从 3.5 抬到 8 —— 这是抖动的主修**（理由与实测见上表那一段）。抬高它的代价是逃离率（66.1% → 46.0%），而它换来的是反向从 90 次降到 20 次、最长直线跑从 1.37 s 抬到 2.95 s。往上还会继续改善稳定性（总承诺 10 → 反向 11 次），但 **10 就开始破最差种子**（0.92×，比原地不动死得更快），所以 8 是拐点，是按**最差种子**选的、不是按均值选的。

**曾经还有一个同类的承诺项 `MOVE_MARGIN`，现在删了 —— 因为它和 `HYST` 是同一件事。** 它的定义是「保住上一帧方向所需的分差」，听起来是个独立的旋钮（一个奖励**重复**，一个惩罚**改变**），但在这一份打分里两者是同一个算术：给上一帧方向多加 2 分，与要求新方向多赢 2 分，落在同一个比较上。实测证实：`HYST` 6 + `MOVE_MARGIN` 2 与 `HYST` 8 + 无 `MOVE_MARGIN`，96 颗种子、八项统计**逐字节相同**。所以承诺量只有**一个**数，8；`MOVE_MARGIN` 的存在只会让「调 `HYST`」这个动作的效果被另一个常数分摊掉，读代码的人算不出机器人的真实承诺是多少。

**`RobotState` 里没有记忆，只有决心。** 需求第 5 条的公开机制仍然逐帧重算、从不记住 —— `perceive()` 是纯的，视图就是机器人关于世界的全部知识，视图里**没有上一帧**。这里存的全是策略**对自己决定的记忆**，是另一回事：

| 字段 | 是什么 |
|---|---|
| `retreating` | 撤退闩锁（上面那个布尔） |
| `orbitSign` | 一次撤退**朝哪一侧绕**（`+1` / `-1`），在闩锁置位的那一帧定一次、之后保持到闩锁释放。`kite` 每帧重推符号是对的（单目标的 `u` 稳定），`flee` 不行：它的参照是 `dangerCentre`，而质心会漂，撤退方向相对中心方向转过 90° 之后切向的符号会翻 —— 那就是抖动的另一种形态 |
| `lastDx` / `lastDy` | 粘滞要奖励的那个方向 |
| `objectiveX` / `objectiveY` | 目标锁的点（**世界坐标**，不是「某只怪」的引用 —— 怪是会死的，点是稳的） |
| `originX` / `originY` | 建锁时机器人所在位置，偏离判据那条线段的起点 |
| `locked` | 有没有锁 |

**从「一个布尔加一对方向」长到了这些，而每一格都对应一次被实测逼出来的承诺。** 三条都是同一个道理：策略需要一个比「这一帧的分数」更长的视野，因为**这一帧的分数在这张风险场上是抖的** —— 风险项的摆幅是目标项的 1.7 倍。锁是「去哪」的承诺，闩锁是「撤还是打」的承诺，粘滞是「朝哪走」的承诺。代价是 `decide` 不再是无状态的，所以「同视图 + 全新 state 给出同一走法」这条契约仍然成立（§14.5 测它），但「同一局逐帧重放」现在**依赖 state 被正确地带着走**，测试里也钉住了这一点。

> 计划里写的签名是 `decide(view)`，实现是 `decide(view, state)` —— 那个闩锁需要一个落脚处。`perceive()` 仍然是纯的、无状态的。

### 14.3 模式与重置语义

```
[ 👤 manual │ 🤖 robot ]        ← §10.1 的三号控件，命中后禁用
```

- **切换即重开。** `setMode()` 先把模式推给场景（这样重建出来的场地就是新模式下的场地），再走**既有的** `restart()` 重置路径：新的 sim、`generation++`、全部本局计数器归零（存活 / 等级 / 经验 / 击杀 / 掉落 / 密钥数），然后 `running = false` —— **总是停在 READY**，`▶` 是一个必须被做出的动作。
- 复用 `restart()` 而不是重抄一遍重置，是为了让「切模式」和「死后重开」这两条路不可能走岔。
- `bestSurvival` **不**清零 —— 和死后重开一样，最好成绩是跨局的。
- 命中后开关一并锁定（与下拉框、`▶` 同一套规则）。
- 场景未就绪时选的模式不会丢：`onReady` 会把当前模式重新推一次。
- **`manual` 下与旧版逐帧等价。** 机器人只占输入源那一个插槽：`readInput()` 在 `robotMode` 时走上 `decide()`，否则一个字符都不变。

### 14.4 HUD 读数

```
auto kite · known 2/5
```

意图 + 「已经拿到几只怪物的数值」。渲染**只在机器人模式下**，因为手动模式下它恒为空。

**画布上没有雾。** 用户明确要求机器人的知识不要画到场上，所以 `GameScene.drawFrame()` 除了一句 READY 提示文案之外没有改动。代价是 `known n/m` 成了观察「看到」与「知道」之差的唯一窗口 —— 这也是它值得占一格 HUD 的原因。

### 14.5 模块与测试

见 §11 的数值表和 §12 的模块 / 测试表。要单独点出的是 `robot.ts` 的形状：两个纯函数加一张调参表，与 `sim.ts` / `keymap.ts` 同构 —— 无 Phaser、无 DOM、无时钟、无随机。所以一颗种子能钉住整条轨迹，一个测试不需要浏览器就能复现一局，而雾是可审计的（它的边界就是类型边界）。

**实测（96 颗种子，`i × 1013 + 7`，`dt` = 1/60，上限 10 分钟）：** 中位 **6.10×**，机器人中位绝对存活 **14.83 s**，idle 对照 **2.43 s**。总计 **80** 次击杀，空闲帧 **0.7%**，接触帧逃离率 **59.1%**，每局脱战 **22.70** 次。到最近边的平均距离 **103 px**，贴墙帧 **52.0%**（逐种子中位）。**死亡点**：到最近边的中位距离 **16 px**、**67.7% 死在贴墙带里**、**2.1% 死在角里**。

**这四个世界必须放在一起看，因为它们量的是三个不同的东西，而比值在它们之间不可比。**

**角落计价那一轮带进来的新通道：死亡点。** 此前所有关于墙的统计量都是**帧的占比**，而一个机器人可以在 59% 的人生里贴着墙、却一次都没被堵死过 —— 用户报的是**结局**（「跑到角落里被怪物堵死」），所以那一轮开始量结局，四个数：死亡点到最近边的距离、是否落在贴墙带（70 px）内、是否在角里（两个轴都在带内）、以及**追猎者的角覆盖** `1 − |追猎者单位向量均值|`（**1.0 = 被围死，0.0 = 全在一侧**）。这条通道是那一轮唯一直接回答用户那句话的量，也是它把前两轮的判断整个翻过来的原因 —— 见下。

> † 这两格的绝对秒数取自 **32 颗种子**的一次运行：绝对秒数通道是**＋可躲空间那一轮才加进 sweep 的**，上面那几列当时没有这个输出，不能回头补。32 与 96 两个样本上的比值不可比，所以这一列与第五列之间的绝对秒数**只当作数量级的对照**，不要当精确对比。

**更早几轮加的两条通道，数字更新到「＋九区拉平」那一轮：**

- **手性**（`circling:` 四行）。按帧取玩家相对 `dangerCentre` 的方位角，报逐帧有符号增量的平均 `|dθ|`/秒，以及一致性 `|Σdθ| / Σ|dθ|`（**1.0 = 稳定单向环绕，0.0 = 来回抖**）。一致性必须**逐种子算完再聚合**，不能把所有种子的帧混在一起 —— 每一局可能朝不同方向绕，混起来会把两个干净的环绕抵消成 0。角落计价那一轮实测 **0.15**（方位）与 **0.16**（无参照的朝向转角），环绕速度 16 deg/s，参照存在的帧占 **100.0%**。**这个绝对值是低的，而且那一轮没有改善**：它证明机器人有单向偏置，但不证明它在绕圈 —— 见 §14.2 关于振荡的说明。**那一轮也没打算改善它**：角落计价动的是风险场的形状，不是环绕的预算。**本列（九区拉平）它反而退了一点：0.15 → 0.12（方位）、0.22 → 0.19（朝向），转角速度 16 → 19 deg/s** —— 这一列动的是世界，环绕预算一分没加，退的这一截只能记在地形账上。
- **脱战次数**（`aggro breaks`）。`escape rate in contact` 问的是「在接触中，这一帧距离有没有被拉开」，是个逐帧问题；而**脱离仇恨是另一个机制**，它要的是把距离净拉开到 `senseRange` 之外。旧的指标看不见它，而环绕恰好花的就是这份预算。角落计价那一轮实测 **26.30 次/局**（2525 次，更早一轮 21.71）—— **角落计价同时抬高了它**，与击杀 115 → 168 同向：机器人更少待在角里，就有更多时候在能拉开距离的地方。**而「＋九区拉平」把它推回去了：26.30 → 22.70 次/局，与击杀 168 → 80 同向** —— 同一支机器人在一张处处都有怪的图上，能拉开距离的窗口更少了。**这一条当年是被加进来否掉一个静态推理的**：见 §14.2 最后一段。

**本轮（＋引到的 1–4 只，§14.2）加进来的新通道：按「盯上机器人的怪有几只」给帧和击杀分桶（`pack`）。** 这条通道存在的理由很直接：用户给的规则是**按数量条件**说的（「引到了 1-4 只怪后」），而在这条通道之前，这份记录里**没有任何一个量能回答「机器人有多少时间待在那个状态里」** —— §4.1 的 `regionTargetCount`、§6.2 的跨区仇恨、§14.2 的 `FARM_RADIUS` 全是别的量。它报两组读数，因为「引到了几只」有两种读法，而两种都要报才看得出问题：

- **`pack aware`** —— 用**模拟自己的仇恨判据**（`dist <= m.senseRange`，§14.1 公开的就是这个）。这是「它在打我」的精确读法，也正是 `m.attacking` 的那一条。实测 1–4 只占 **3.6%** 的帧、5–8 占 23.7%、9+ 占 **72.7%**。
- **`pack close`** —— 用 **120 px**（复用 `CLUSTER_RADIUS`，也是 `PACK_RADIUS` 的取值）。这是「贴上来了」的读法，比仇恨判据窄得多。实测 1–4 只占 **36.0%** 的帧。
- **两者必须并排看，因为中间那个差就是这一轮的结论**：一只追猎者的 `senseRange` 是 260 px 而场地是 960 × 540，**一个 260 px 半径的圆占地板面积的 41%** —— 所以 `aware` 那个读数天然偏大，而它偏大的**原因不是机器人引怪引坏了，是半径相对场地本来就这么大**（§14.2 的探针把这句话变成了测量）。**`aware` 是「谁在盯我」，`close` 是「谁在我脸上」；用户说的「引到 1–4 只」两种读法都讲得通，而它们在量上差了一个数量级（3.6% vs 36.0%）。**
- **这一轮还新增了「击杀落在哪个桶」**（`kills/1k frames` = 该桶的击杀数 ÷ 该桶的帧数 × 1000），因为只报帧的占比会把「待得久」当成「打得好」。**而这个数给出的结果自相矛盾，所以它的价值是「划掉一个想当然的假设」，不是「给出一条结论」。** 基线（96 颗种子，全场 80 次击杀 / 约 108.6 千帧 = **0.74 次/千帧**）：

  | 读数 | 1–4 只 | 5–8 只 | 9+ 只 | 相对全场 |
  |---|---|---|---|---|
  | `pack aware` | **1.5** | 0.6 | 0.7 | 小群 = 全场的 **2.0 倍** |
  | `pack close` | 0.9 | 0.4 | **0.9** | 小群 ≈ 全场（1.2 倍），**9+ 也不差** |

  **两个读数给出相反的方向**：按「谁在盯我」算，小群是效率最高的那桶（1.5 vs 全场 0.74）；按「谁在我脸上」算，小群并不突出，而 9+ 那桶同样高（0.9）。**也就是说「怪少就杀得快」这件事，取决于你用什么标准数「怪少」，而这两把尺子都是这一轮自己定义的。** 结论只能记到「这个假设**没有被**证实」，不能记成「被否掉」—— 上面那句「否掉一个想当然的假设」如果写成「小群效率更低」就是**读过头**了。真要回答它，需要的是**逐只怪**的归属（这只怪是被谁、在它被引到第几秒杀掉的），而不是**逐帧**的分桶；帧的分桶只能近似，因为一帧里那只怪不一定已经死了。**这条留给下一次，本轮不做。**

**本轮（＋引到的 1–4 只）的账：一次平手，理由是这条规则的前提在今天的世界上几乎不出现。** 这一轮与「九区拉平」那一列相反，动的是**策略**（`robot.ts`），世界一分没动，所以同机同批种子直接可比。

- **买到的**：`kite` 帧 25.8% → **31.7%**、`flee` 帧 73.6% → **68.1%**（**唯一一个方向明确的读数** —— 机器人真的少逃了一点、多对峙了一点，正是用户要的那件事）、贴墙帧 52.0% → **48.1%**、击杀 80 → **81**、比值中位 6.10× → **6.27×**、到最近边距离 103 → **107 px**、死在角里 2.1% → **1.0%**。
- **付掉的**：机器人绝对存活中位 14.83 → **14.18 s**（−0.65 s，噪声内）、直线跑 2.82 → **2.72 s**、空闲帧 0.7% → **0.9%**、脱战 22.70 → **21.82 次/局**、死在贴墙带 67.7% → **68.8%**。**没有一格是显著变差的，也没有一格是显著变好的** —— 这就是「平手」在这里的意思：两轴各动了一点点，且都小于噪声。
- **死亡方式那两个数这一轮不能读，必须写出来当一条警告。** 死亡点到最近边的中位距离在**同一世界内跨臂**从 16 px（基线）跳到 63 px，而**均值几乎没动（68 → 66 px）**：这是分布形状变了（贴死在墙根的那一簇没了），不是整体挪了，**中位在这里不稳，均值才是可信的那个**。而**追猎者角覆盖在臂与臂之间从 0.00 摆到 0.39**（基线 0.01、本轮 `b+d` 0.02、`c+d` 一臂 **0.39**、`a` 一臂 **0.37**、`b+c+d` 与 `a+b+c+d` 都是 0.00），与各臂的表现**毫无对应关系**。**结论：这一轮的臂间差异小于这两个通道的臂间抖动，它们现在还不足以支撑任何判断** —— 记在这里，是为了下一个人不要拿它们去论证什么。
- **而这一轮真正的产出不在表里，是一个被证否的诊断**：用户说机器人打不死怪是因为没有坚持风筝，而实测说**风筝机制是好的，缺的是让它上场的地形**（§14.2 的半径探针：`senseRange` 260 → 140 让 1–4 只从 3.6% 升到 59.2% 的帧、击杀 80 → 330）。**这一列的数字之所以这么平，正是因为它试图修的那件事本身是别的旋钮的事。**

**上一列那个 7.96× 里，大部分不是机器人的功劳，是分母塌了；而这一列的 12.46× 是干净的。** 上一轮机器人自己的中位存活从 9.92 s 涨到 14.13 s（1.42×），而 idle 对照从 3.62 s 塌到 1.82 s（0.50×）—— 两件事乘起来才是 7.96× / 2.45× ≈ 3.2× 的来源。**此后分母两步没动**（idle 中位 1.82 s 与上一轮逐位相同），所以 7.96× → 10.01× → 12.46× 全部来自分子：14.13 s → 16.77 s → 22.33 s。这正是「比值只在同一世界内可比」那条规矩的第二次兑现 —— 同一次改动里分母不动，比值才第一次可以当分子读。idle 从 3.62 s 塌到 1.82 s 的原因仍在记录中：出生点挪到场地正中之后，**站着不动的人** t=0 就被 10.2 只怪罩住（当时的角落是 5.6 只）。**这一整段都是旧地图上的测量**：那时九区还分档，场地正中是最密的一格；§4.1 拉平九区之后，「中心开局比角落开局更危险」这个对比本身已经不存在了 —— **已重测：idle 中位 1.82 s → 2.43 s**（中心从 6 只 / 2.5s 变成 4 只 / 5.0s），而这条反向的变化正是本表「＋九区拉平」那一列里分母变大的原因。

**两个方向相反的变化仍然在，而角落计价那一轮的账比它前面一轮清楚。** 承诺那一轮：最差种子 0.95× → 1.25×、击杀 143 → 175、反向 90 → 20，代价是中位从 3.48× 掉到 2.48×、逃离率从 66.1% 掉到 46.0%（承诺就是「不理会每一次触碰」）。可躲空间项落地那一轮：逃离率买回到 56.9%，中位不付代价，代价落在方向稳定性上（反向 20 → 27、直线跑 2.95 s → 2.33 s）。中央出生那一轮把两件事一起做，方向稳定性和逃离率第一次同时站到承诺之前的水平或更好（反向 13、直线跑 3.13 s、逃离率 58.5%），代价是击杀 194 → 74。**角落计价那一轮把这份账又推进了一步，而代价明确地落在同一个地方：**

- **买到的**：净空 82 → **90 px**、贴墙 63.1% → **59.0%**、逃离率 58.5% → **60.3%**、击杀 74 → **115**、直线跑 3.13 s → **3.52 s**、存活 14.13 s → **16.77 s**、最差种子 2.10× → 1.98×（**唯一变差的一格**）。而 §14.2 那张表的最后一列说明真正被修的是**末端塌陷**：30 s 后的贴墙比例从 100% 降到 73.3%、净空从 14 px 回到 62 px。
- **付掉的**：反向 13 → **18 次/局**。这是**可预期的代价，不是意外** —— 环绕就是让方向持续转弯，而「反向」这个统计量数的正是方向变化（它把每一次转向记一次）。直线跑反而变长（3.13 → 3.52 s），说明代价不是「抖」，而是「转」。**这两个数从此要一起读**：只报反向会把环绕当成抖动，只报环绕会把抖动当成环绕 —— 所以那一轮才加了手性一致性那一行，它同时在两个轴上看方向。

**角落计价那一轮的账，是这份记录里第一次「买到的东西正是用户报的那句话」。**

- **买到的**：**死在角里 41.7% → 1.0%**（这一格是那一轮存在的理由）、存活 16.77 s → **22.33 s**、比值 10.01× → **12.46×**、击杀 115 → **168**、脱战 21.71 → **26.30 次/局**、最差种子 1.98× → **2.16×** ‡、30 s 后的净空 62 → **73 px**、30 s 后的贴墙 73.3% → **65.9%**。**击杀与脱战同时上升这一点值得单独看**：它不是「躲得更好了」，而是「更少待在角里，就有更多时候在能打也能跑的地方」—— 一个只会逃的改动会把击杀压下去，这个没有。
- **付掉的**：反向 18 → **26 次/局**、直线跑 3.52 s → **3.39 s** ‡、净空 90 → **87 px**、贴墙 59.0% → **58.5%**（后两项基本未动）。代价仍然落在方向稳定性上，与前一轮同一处 —— 角落计价让机器人在角附近更早转向。
- **没买到的，而这一条要写在最显眼处**：**贴墙帧一步没动**（59.0% → 58.5%）。那一轮**不治**「总是往边界跑」，只治「死在角里」。这两件事在前两轮被当成一件事，而实测说它们是两件 —— 见 §14.6 三。（**九区拉平这一列把贴墙帧从 58.5% 推到 52.0% —— 但那是密度与幸存者偏差的副产品，不是「往边界跑」被治好了**，见下。）

**本轮（九区拉平 ＋ 等级刷新，§4.1）的账，是这份表里第一次可以整列归因的一次：`robot.ts` 一行没改。** 这一轮动的是世界 —— 九区参数拉平、刷新间隔改由玩家等级驱动、§4.3 去掉 `×0.9`。**策略那几列都同时动了策略，比值与绝对值都只能在列内比较；这一列的差值是纯地形效应。** 为了让这句话站得住，本轮先在**同一台机器、同一批种子**上把旧世界重跑了一遍作为对照臂（`git stash` 前后各一次），而不是拿文档里的旧数字直接比。

- **买到的**：净空 87 → **103 px**、贴墙帧 58.5% → **52.0%**、死在贴墙带 82.3% → **67.7%**、死在角里 1.0% → 2.1%（几乎未动）。**前两格是这份表里净空与贴墙的历史最好值**，而它们不是策略挣来的 —— 是地图不再提供「最密的一格」的结果。
  **但这份改善里有一部分是幸存者偏差，必须自己说出来。** 活得短就等于少经历末端塌陷那一段，而末端塌陷恰恰是贴墙最重的时段（§14.6 三）。分桶对照（新 / 旧）：0-5s 净空 121 / 105 px、5-15s 86 / 85 px、15-30s **92 / 74 px**、30s+ 77 / 73 px；贴墙份额 40.1 / 48.6、56.8 / 57.9、54.8 / 65.3、60.5 / 65.9。**前两桶基本只是「开局没被围」的差别，真正的差额落在 15-30s 那一桶** —— 而那一桶也是样本被截短得最少的一桶。所以这一格的方向可信，量值里混着一份分母效应，不要当纯粹的净空改善读。
- **付掉的**：中位存活 22.33 → **14.83 s**（−34%）、比值 12.46× → **6.10×**、击杀 168 → **80**、接触帧 16.5% → **23.9%**、脱战 26.30 → **22.70 次/局**、直线跑 3.55 → **2.82 s**（均值；两值同源于本轮那次重跑，中位 2.73 s、最好 6.00 s；表内那一列的记值是 3.39 s，见 ‡）、方向一致性 0.15 → **0.12**（方位）/ 0.22 → **0.19**（朝向）、死亡点到最近边的中位距离 37 → **16 px**（**死的时候贴着墙**，哪怕死在墙边的比例降了）。反向 26 → 24 次/局，基本未动。
  **这一列的分母反向动了，而这次它是替地图说话。** idle 对照从 1.82 s 涨到 **2.43 s**（+34%）—— 场地正中不再是全图最密的一格（旧：6 只 / 2.5s；新：4 只 / 5.0s）。**12.46× → 6.10× 这个塌陷里，分子降 34%、分母升 34%，两股力同向。** §14.5 那条「比值只在同一世界内可比」的规矩这次兑现得更彻底：**跨世界连分母的方向都会翻**，所以本列同样只能读绝对秒数。
- **机制一句话：每格的刷新都更松了，整张图却更挤了。** 每区间隔 2.5–6.0s 统一到 5.0s、中心目标数 6 → 4，这两件都是**放松**；但总数从 30 涨到 36（四角 2 → 4 是主要来源），而怪物**跨区仇恨**（§4.2）让「角落稀薄」这件事一直是可依赖的缓冲 —— **它是这份表里所有存活数字的一个隐含前提，此前从未被单独写出来过，而它现在没了。** 放松赢了每一格，输给了总数。
- **等级那条曲线在机器人的一局里没有接上电，这一列可以直接证明。** 机器人中位存活 14.83 s，而 §4.1 的公式要升到 11 级（约 240 次击杀）才把间隔压到 4.0s；本列**全程 80 次击杀**，也就是说整局的刷新间隔都停在 5.0s 的初值上，**等级规则贡献了 0**：地图变难的部分全部来自密度，一点不来自这条新梯度。**新梯度是真的、可测的、也是这一轮唯一的设计意图，但它在机器人这个时间尺度上等于没接上电** —— 这正是 §4.1 里如实记下的那条代价在实测上的样子。
- **最差种子 1.98× → 1.01×（旧值取自本轮同机的重跑；表内那一列的记值是 2.16× ‡），这一格要写在最显眼处。** 96 颗种子里有一颗，机器人只比站桩多活 **1%**。而 `tests/game-sim.mjs` 守这一条的断言用的是 **12 颗种子**：那 12 颗里最差 **2.42×**、中位 5.31×，两条都过。**测试不薄，薄的是 96 颗的尾巴** —— 这条断言从此是在一个它看不见的分布上过的。这是 §14.6 教训二的反面用法：小样本当年让一颗种子**冒充**了一个机制，这一次它让一颗种子**看不见**一个机制。

- **零击杀局：36% → 56%（96 颗种子，逐种子击杀数）。** 这是「＋九区拉平」那一轮唯一新增的量，而它把一个**既有的测试缺陷**顶到了台面上：`tests/game-tab.mjs` 里那句 `the robot scores a kill with no keyboard input at all` 等的是**一条命里至少一次击杀**，而一条命 0 击杀的概率是 **56%** —— 这条断言在那之后的世界里大约**三次里红两次**（实测 3 次跑 2 次红）。**它在九区拉平之前也已经不可靠**（旧世界 36%，实测 3 次跑 1 次红；那时它靠 64% 的通过率混过去），所以这是一条**先于那一轮存在、被那一轮放大的**缺陷。

  **「＋引到的 1–4 只」这一轮把它量清楚了，而量出来的结果否掉了最省事的那种修法。** 给 96 颗种子逐颗记「第一次击杀发生在第几秒」，以及**这条命到底有没有过一次击杀**：

  按这条分布算，**把断言里的 `timeout: 30000` 往上调是没用的**：10 / 15 / 20 / 30 / 45 / 60 秒的窗口分别只覆盖 17.7% / 22.9% / 30.2% / **36.5%** / 40.6% / 40.6% —— **天花板就是 40.6%**，因为**一条命结束后不会自己再来一条**（`state.svelte.ts` 的死亡是停下、`▶` 手动重开），所以 30 s 的窗口实际覆盖的就是**一条中位 14.63 s 的命**，之后它在等一个不会到来的重开。**「超时不够长」是错的读法；正确的读法是这条断言要求的那个性质，在这个世界里 59.4% 的情况下不存在。** 修法与取舍见 §13。

  **而「全套测试到底红在哪」要单独说清，否则这一条会被读成「测试整体坏了」。** 同一份代码连跑，其中一次全套 **278 条断言全绿**；红的那些次全部停在 307 行那一句，即上面这个零击杀门槛。**所以这一轮没有别的断言被打坏** —— 278 这个数也是这份记录里第一次写下来的全套规模。

  **另有一处与本节无关、但同一批运行里观察到的偶发失败，如实记一笔（只见到 1 次 / 3 次运行）。** `[6] A stale failure cannot kill the run that replaced it` 那一段里，`#btn-run` 会以 `disabled` 状态被点到而超时 —— 而 `#btn-run` 禁用只有两种情形（没选谜题、命中后锁定），时序上对得上它自己那段注释预言过的症状「the new run comes up frozen behind an inert ▶」。**最可能的原因是这段测试自己的时序**：它用 `waitForTimeout(60)` 等采样器把 `__FAIL_NEXT__` 那个陷阱捡起来（注释写的是「at most one frame」），而 60 ms 在负载下不足一帧，于是陷阱被后一次 derive（恰好是跨边界那次）消费掉。**它属于 `fix/game-run-boundary-leaks` 那条分支的题目，不属于本轮的机器人改动** —— 本轮的改动只在 `robot.ts`，而 `[6]` 跑在手动模式下。**记在这里是为了不让它被下一轮的账盖掉，不是本轮去修它。**

### 14.6 三条曾记录的缺陷：一条已修，一条残留，一条是本节最后落的

这两条曾被认为来自同一个根因 —— **探测视界与实际步长的比例**（`PROBE_S = 0.25` 让每个候选都在约 40 px 之外被评判，而机器人一帧实际只走约 2.8 px）。**这个归因对第一条是错的，而错了整整一轮。** 第二条才是它的真实作用域。

**（一）静止（原「边界僵持」）：已修。根因不是探测视界，是拴区。** 机器人会在满血、离任何墙都有 140 px 的地方**站着不动**，一分不得。上一轮把根因定位到了正确的地方 —— 拴区项在空间上是一个**阶跃**：跨过边界会一次点亮好几只怪物，实测阶跃约 55，而没有一个目标权重能到那个量级；在 `RISK_CAP = 12` 之上风险项从「操舵」变成「否决」，而原地不动的增量恰好是 0，于是它永远赢 —— **但结论写成了「要真正治好它就得改探测视界」，而那是另一个东西。** 实测反驳了它：拴区一解除（§6.2），在**没有任何策略改动**的情况下空闲帧从 55.9% 掉到 5.2%；本轮策略改完是 **4.3%**。探测视界从头到尾没动过。

**这一轮之前堵的三轮口，堵的全是症状，值得作为一条教训留下来。** `KITE_CONTACT_WEIGHT`、粘滞排除静止、以及 §14.2 记的那三个出口（目标剔除、跨区被减数、`pickTarget` 只选本区），每一个都让数字好看了一点（空闲帧 77% → 71% → 54.9%），但没有一个碰到阶跃本身。**而其中 `KITE_CONTACT_WEIGHT` 在拴区解除后变成了一段永不执行的死代码** —— 它守的判据（目标已在 `reach` 内）恰好也是撤退闩锁的进入判据，闩锁先一步把那些帧全部接走了。它和本节下面那条一起，构成了同一种失败模式：**一个常数或分支的职责已经被别的东西接管，而它还在原地以旧的理由被记录着。**

**（二）探测 / 步长震荡：大幅减轻，残留仍在，但残留的性质变了。** 机器人会在相隔约 6 px 的两个位置之间来回，净位移为零。机制仍然是 40 px 的探测对上 2.8 px 的实际步长：当两个探测端点的风险差得够狠时，反向的收益盖过承诺奖励。**承诺修完的量级：反向 90 → 20 次/局，最长不间断直线跑 1.37 s → 2.95 s**（中位 2.58 s，最好 7.02 s）。**补上可躲空间项之后，反向回到 27 次、最长直线跑回到 2.33 s** —— 那一项在墙边与承诺奖励争夺同一个方向，赢得多了，方向就换得勤（这个交换的账记在 §14.5）。

**而这一轮结束时，这两项**同时**回到了承诺之前的水准之上：反向 **13 次/局**（承诺时 20，可躲空间项单独作用时 27）、最长直线跑 **3.13 s**（承诺时 2.95 s，单独作用时 2.33 s）。** 这是把两件事**一起**做才有的结果：出生点挪出角落减少了机器人在墙边与承诺奖励抢方向的机会，而撤退档的可躲空间权重把「往里去」的正收益补在该补的那一档上。也就是说 27 次 / 2.33 s 那个代价**从来不是可躲空间项的必要代价，是它在错误的帧上也在说话**—— 这一点在 §14.2 的 `ROOM_WEIGHT_FLEE` 上有 96 颗种子的网格为证。

**而这里有一条反直觉的实测结果，值得单独记下来：直线跑变短了，逃离率反而从 46.0% 涨到 56.9%。** 也就是说**「最长不间断直线跑」不是逃离的充分统计量**。它作为指标成立的前提，是那些直线跑发生在**跑得开**的地方 —— 而在墙边，一段同样长的直线跑净收益接近于零：脱战要的是净间距（§6.2 的 160 px），沿着墙跑只会撞到角落，届时方向必须重置、收益清零。给它 16 px 净空之后，短一点的片段也能真的拉开距离。**「追猎者需要 3.9 s 不中断的直线跑」这句话本身没错，但它是对着 640 px 跑道那个特定几何说的，不能拿来当所有情况下逃离能力的天花板。**

> 上一版记的「`HYST` 调大反而**加长**这些片段（最坏连续帧数 3 → 8 时从 747 涨到 1817）」**在拴区世界里量的，在这里不复现**：最长直线跑在 3.5 → 8 → 10 上单调上升。那时的「最坏片段」是拴区阶跃造成的另一种现象，被错误地归到了本缺陷名下 —— 与上面那条错误归因是同一件事的两面。

**炸弹没有治好它，这是一次落空的期望 —— 而它在新世界里比上一版记的更彻底。** §15.4 把重装者的炸弹设计成反站桩工具，理由是「落点画在地上 + 0.4 秒引信」对一个静止的人是确凿的惩罚，而这条缺陷恰好就是静止。拴区世界里实测就已经否掉了它：`BOMB_WEIGHT` 取 **0 / 1 / 20** 三组跑同一套 96 颗种子，中位倍数三组都是 6.49×、都是 96/96 跑满，只有极小的分布差异（空闲帧 55.7% / 55.9% / 56.0%，击杀 23020 / 23002 / 23096）。**本轮重测，连那点差异也没有了：0 与 20 的完整 sweep 输出逐字节相同**，唯一的差别是打印覆盖值的那一行。权重从「完全不躲炸弹」拉到 20 倍，一格都不动。

> **但这一条与上面那两条死代码不是同一回事，分寸要留住。** `KITE_CONTACT_WEIGHT` 与 `MOVE_MARGIN` 能删，是因为有**机制上的证明**：前者守的判据与撤退闩锁的进入条件逐字相同，闩锁先接走了那些帧；后者与 `HYST` 是同一个算术。`BOMB_WEIGHT` 只有**聚合输出相同**这一条证据 —— 那可以说明它在这 96 颗种子上没有改变任何决定，但**不能说明它不可达**：炸弹项可能只是很少成为某一帧的胜负手。所以它**保留**，且以「正确性」而非「修法」的身份保留 —— 人类能读懂预警圈并走开，忽略它的机器人玩的是另一个更瞎的游戏（§14.1）。**删一个常数需要机制，不是需要相关性。**

**结论翻了面。** 上一版写「生存对比是压倒性的，96/96 颗种子都跑满上限」—— 这一条**已不成立**：0/96 跑满上限，而这个指标在无拴区世界里恒为 0，与策略无关（§14.5）。但「机器人大部分时间在玩」这句上一版**部分收回**的话，现在可以**收回那句收回**：空闲帧 2.8%，机器人不再站着不动，击杀 194（拴区解除未改策略时是 143）。**它现在是真的在打**；而它仍然活得比拴区世界短，那个代价属于难度基调，不在这里的账上（§13）。

**这一轮最后落下的教训是：一个罚项不会自动变成一份方向感。** 用户看到的是「贴着边界走」，缺的是躲避空间，而分数里**已经有**一个专门罚贴墙的项、罚得也不算轻 —— 它的问题是只会**收费**、不会**吸引**，而它收费的方向恰好被 `flee` 的径向目标和滑墙一起删掉了。剩下那个即不挨罚也不收费的方向就是切向，于是机器人沿着边界走。**修法不是把罚加重，是补上那份正收益**（§14.2 的 `ROOM_WEIGHT`）。这条与本节前面那条「删一个常数需要机制，不是需要相关性」是一对：**加一个项同样需要机制 —— 需要说得出它在补哪个方向上缺失的收益，而不是说得出它让哪个数字变好了。**

**（三）「总是往角落里跑」：先量后判，三层，而最像元凶的那一层不是。** 用户第二次报的现象是「robot 为什么总是倾向于往角落里或者边界上跑」。第一直觉是**出生点** —— 当时的出生点在左上角那一格。直觉错了一半，所以先量：（**这段分析量于两处改动之前**：出生点已挪到场地正中，九宫格也已按 §4.1 拉平。下面这些数字与「角落 / 中心」的对比都属于旧地图。**「越活越贴墙」这条结论已在新地图上重测，方向成立**：贴墙份额按时段 40.1% → 56.8% → 54.8% → 60.5%（0-5 / 5-15 / 15-30 / 30s+，§14.5 的「＋九区拉平」列），仍然是**单调上升**的；但「左上的两个角占 45% 的帧」这类具体量值属于旧地图，不再有意义。）

- **不是启动假象。** 贴墙比例按局内时间分桶是 79.7% → 72.3% → 76.1% → **100%**（0-5 / 5-15 / 15-30 / 30s+），平均净空 44 → 57 → 51 → **24 px**。它**越活越贴墙**，不是开局没走开。t≥10s 之后，左上的两个角占了全部帧的 **45%**，而它们只占 8% 的地面。
- **贴墙时它在往外走。** 贴墙且移动的帧里，**向外 28.1% / 切向 55.9% / 向内 16.0%**，平均径向分量 **+0.18**（开阔地 −0.01）。而 `flee` 在贴墙帧里占 **77.3%**，开阔地里只占 66.2% —— **它贴墙是因为它在撤**。
- **滑墙是清白的。** 最像元凶的是 `decision` 顶部那段把朝外分量清零的滑墙钳制，但删掉它每一项都**更糟**（净空 49 → 31 px、向外 28.1% → 33.0%、贴墙 76.6% → 80.9%）。它是**保护**，不是病因，已回退。

机制因此是三层的，且只有前两层是病因：**（a）** `flee` 是五个 rung 里**唯一**目标不含任何场地参照的 —— kite 锚在站位环、loot 锚在掉落物、roam 锚在某只怪，只有 `flee` 的目标是「背离危险质心的纯径向」，它可以指向场外；**（b）** 滑墙把「向外」投影成「沿墙」，一维滑动的终点是角；到角之后**脱战所需的约 640 px 跑道永远凑不出**（§14.2），于是脱不了战、还在危险里、继续 `flee` —— 一个自锁环；**（c）** 出生点只是**先手距离**：挪到场地正中，净空 49 → 77 px、贴墙 75.6% → 63.9%、中位存活 9.9 → 15.6 s，但**两臂的贴墙比例都随时间上升**（中心开局 51.8% → 69.6% → 80.4% → 74.1%）。**从场地正中央出发，它照样一路走到边上。** 挪出生点是把起点从陷阱里挪出来，不是把陷阱拆掉。

> **这一轮的记账教训有两条，都关于「这个数字是怎么来的」。**
>
> **一、分母会跟着世界一起动。** 出生点一挪，比值中位数从 2.33× 跳到 **9.80×**，看着像翻了四倍 —— 而 idle 对照的中位绝对秒数同时从 3.62 s 塌到 **1.85 s**（场地正中比角落对站桩的人危险得多），机器人自己的秒数只从 9.92 s 涨到 17.55 s。**9.8× 里只有 1.8× 是机器人的。** 所以 sweep 现在两臂都打绝对秒数：比值不能单独用这件事（§14.5 早就写着）必须有输出可以查，不能只写在文档里。
>
> **二、样本小的时候，一个种子就能冒充一个机制。** 32 颗种子的网格上，`ROOM_WEIGHT_FLEE=8` 那一臂读出贴墙 51.1%（对 4 的 76.6%）—— 一个漂亮的断崖。而同臂的击杀是 **334**（其余各臂都在 50 上下）、总帧数是 58427（其余约 24000）：**一颗活得特别久的种子把按帧加权的统计量整个抬走了。** 逐种子的中位数说那一格是 **73.0%**，不是 51.1%。于是 sweep 现在**同时**报按帧加权与逐种子中位数两个数（前者回答「一局里它怎么过」，后者回答「策略有没有变」），而 96 颗种子上那笔买卖的规模只有 32 颗种子说的**一半**。

**这一轮的结局：机制（b）那个自锁环被拆掉了，但拆掉它的不是当初诊断出的那根杠杆 —— 而下面三条记账教训，全部是关于「功劳被记到了谁头上」。**

用户第二次报同一现象时给出的方向是「**增加兜圈子效果**（这是放风筝杀怪的精髓）」。诊断复述过来就是上面那三层，而修法落在**（a）与（b）的连接处**：`flee` 的**径向**（当初被收窄时唯一留下的那半）保持满格 1.0，把它的**切向**那半装回来。理由是径向的**形状**问题而非尺寸问题 —— 一个永不归零、背离一点的目标在有界场地里是梯度流，唯一的吸引子是边界，而滑墙把残量投影成一维滑动、终点是角。切向那半不改变它离得多远，只改变它弯向哪边。96 颗种子对照纯径向：**30 s 后的贴墙比例 100% → 73.3%、净空 14 → 62 px**，全局净空 82 → 90 px、贴墙 63.1% → 59.0%、中位存活 14.13 → 16.77 s。**末端塌陷这个缺陷级的结果是本轮唯一一个「消失」而不是「变小」的东西**，其余都是量的改善。

**而「兜圈子」本身只做到了一半，这一点不能靠「修好了」三个字盖过去。** 本轮为此专门加了手性一致性这个量（`|Σdθ| / Σ|dθ|`，1.0 = 稳定单向环绕）：它只从 **0.11 抬到 0.17**。也就是说机器人**没有**进入持续的单向环绕轨道 —— 收益来自切向那半把墙棘轮打断，而不是来自真的绕圈。原因是 `flee` 与 `kite` 在 51–220 px 之间来回换档，一次撤退内转不满一圈；要拿到真环绕，下一根杠杆是给 `flee` 的径向加饱和（照 `kite` 的 `err`）—— 那正是用户当轮**没有选**的方案 B，本轮按计划记录了但不做。**「加了一个机制」与「这个机制按设计运转了」是两句话，这一条是它们的差价。**

> **三、一个常数被两档共用时，网格会把功劳记在错的那一档上。** 最初那个网格扫的是**共享**的 `ORBIT`，读数很惊人（贴墙 63.1% → 47.5%、净空 82 → 96 px），而我把它归给了 `flee`，并据此写了一整段理由。拆分之后才看清：`ORBIT=1.2` **只动 `kite`** 是 **48.7% / 93 px**，**只动 `flee`** 是 **57.9% / 90 px** —— 那个大改善**主要是 `kite` 的**，`flee` 只贡献了剩下的一小截。而 `kite` 的值被一条**有实测依据的**不变量压住（目标挨打时径向必须压过切向，§14.2），所以那个「惊人的网格」实际上在推销一个**本来就上不去**的值。**共享旋钮的网格量的是两个机制的**和**，而「和」在调参时从来不是可分的** —— 拆分不是为了给两档不同的数，是为了让网格能归因；两档最后确实要了不同的数（0.6 / 1.2）只是这条的副产品。
>
> **四、改形状会同时改强度，而强度是另一个常数的事。** 抬高环绕同时抬高目标的**量值** `hypot(1, orbit)`，1.2 相对 0.6 是 1.56 对 1.17 —— **强 34%**，而「目标该多强」是 `GOAL.flee` 管的。所以那一格改善里可能一分钱都不来自「弯」，全部来自「更用力」。用**量值相当**的两臂分开：`GOAL.flee` 8 + `FLEE_ORBIT` 0.6（6 × 1.562 ≈ 8 × 1.166）对照 `GOAL.flee` 6 + `FLEE_ORBIT` 1.2。前者**什么都没买到**（贴墙 61.6%、净空 83 px、存活 14.52 s，全部不优于基线），后者拿到 57.9% / 90 px / 16.77 s。**做功的是形状。** 教训是可操作的：一个乘法形式的参数（`GOAL × hypot(1, orbit)`）里动了其中一项，就必须有另一个臂把乘积**配平**，否则量的是乘积。
>
> **五、静态推理要被实测否掉一次才算数，而否掉它的通道得先存在。** 切向会分掉向外速度：160/hypot(1, 0.9) = 119 px/s 已低于猎手的 120 px/s，照 §14.5 那个「160 px 净收益 ÷ 40 px/s 净差 ≈ 3.9 s」的算法，0.9 以上**永远脱不了战**。这个推理几乎让我把值停在 0.6。**但 sweep 里没有任何一行能看见脱战** —— `escape rate in contact` 量的是「接触中这一帧距离有没有拉开」，是逐帧问题，与「把距离净拉开到 `senseRange` 之外」不是一回事。于是本轮加了 `aggro breaks` 这一行，实测**每局脱战次数随环绕上升**（17.1 → 17.3 → 21.2 → 21.7），按存活秒数归一后持平。原因是这个 sim 的怪物**从来不做干净的直线追击**（`wanderSpeedScale`、八方向吸附、追到 `attackRange × 0.7` 就停，§6.2），脱战由侧向几何决定。**那个静态模型是错的，而它错得很有说服力** —— 这正是它值得被写下来的理由：这条通道是**为了否掉一个我自己已经算完的结论**才加的，如果先写文档再补测量，它会以「已论证的风险」的身份留下来并永久压住 0.9 以上的所有值。
>
> **五条合起来是一句话：这一轮没有一个数字是照原样信下来的。** 功劳被拆开过（三），乘积被配平过（四），机制被新通道否过（五），小样本被中位数复核过（二），分母被单独打过（一）。而留下的**负数**有两个，都不许藏：**手性 0.17 说明环绕没有变成持续轨道**，**反向 18 次/局高于上一轮的 13**（那是转弯本身的代价，与直线跑 3.13 → 3.52 s 一起读才完整）。

**（三）续：用户第三次报同一现象。这一轮先换掉量尺，然后结论翻了面。**（本节下面这一段叙述的是表里**「＋角落计价」那一轮**，不是最新一列；读法见 §14.5 开头那条。）

用户的第三句话是「仍然会跑到角落里被怪物堵死……运行了两次，都是很快就到了边界，然后是角落，被堵死，整个不超过 20 秒」。前两轮优化的都是**贴墙帧占比**，而用户报的是**死亡的方式与地点** —— 不是一个量，且一个机器人完全可以在 59% 的人生里贴着墙、一次都没被堵死过。**所以这一轮的第一件事不是改代码，是加通道**（§14.5 的「死亡点」四行）。它一落地，用户的话就被证实了一半：

- **死在贴墙带里 81.3%**，死亡点到最近边的中位距离 **37 px**；
- **死在角里 41.7%** —— 用户说的「角落」是真的，而且在四个角只占 8% 地面的情况下。

**但「被怪物堵死」这半句没有成立。** 死亡时刻的追猎者角覆盖中位只有 **0.62**：他们不全在一侧，可也没有围死，一条逃逸通道还在。而在 **40 个真正的失败帧**（贴边 ≤40 px 且正在沿墙滑动）上做消融，给出了这一轮最重要的一个数：**把 `WALL_WEIGHT` 归零，0/40 的走法会变；把可躲空间项归零，0/40；而把风险场的上限归零，27/40。** 也就是说 —— **前面两轮写来把机器人挡在墙外的那两项，在任何一帧失败画面上都没有被咨询过。** 在决定的是风险场。

**而风险场把它送去墙边，是它的定义直接推出来的。** `riskAt` 是对附近怪物的求和，所以风险的最低点就在**怪最少的地方**；而在场地边缘怪物全在一侧，于是**边界成了整个风险场里局部最安全的地面**。这就是「总是倾向于往角落里或者边界上跑」的机制，而它不是任何**目标形状**盖得过去的：前两轮改的全是目标（环绕、手性、弧形），而目标项（±7）本来就在风险项（±12）的阴影里。**修法只能落在风险场本身。**

**依据是一次按暴露量（而不是按结局）的测量**：每秒暴露受到的伤害，按到最近边的距离分桶，**并控制住 150 px 内的怪物数量** —— 因为不控制的话，墙带看起来致命 2.5 倍，而其中大部分只是「它旁边恰好站着谁」：

| 150 px 内的怪物数 | 边 ≤70 px | 70–240 px | >240 px | 各带占的时间 |
|---|---|---|---|---|
| 0 | 0.00 | 0.00 | — | 1.5% / 0.2% / 0.0% |
| 1 | 1.22 | 1.02 | — | 3.8% / 0.5% / 0.0% |
| 2 | 1.72 | 3.65 | — | 5.4% / 1.2% / 0.0% |
| 3 | 2.72 | 6.18 | 0.00 | 4.3% / 1.1% / 0.2% |
| 4–5 | 4.24 | 2.30 | 0.00 | 5.1% / 1.9% / 0.2% |
| **6+** | **7.87** | **5.03** | **4.63** | **38.3% / 30.9% / 5.5%** |

最后一行是机器人真正生活的地方（**75% 的人生**是 6 只以上怪在 150 px 内），在那里墙带是**同威胁密度下**中场区的 **1.56 倍**。而第一行是说明「这是一个**交互项**」的对照：旁边没怪时，角落是**免费**的（各带都是 0.00 dmg/s）。**所以它是 `riskAt` 的乘数，而不是旁边的一个罚项** —— 一个平摊的罚项会给一个零成本的空角落定价。伤害的来源也不冷门：**这 48 局里 98.0% 的伤害是子弹**（接触 1.0%、炸弹 1.1%），而子弹打的是玩家**当时站的地方**，所以同样一只怪，在你有一半方向是墙的时候更容易打中。这正是人类读作「别被逼到角落」的那个几何 —— 所以给它定价**不需要机器人拥有人类没有的信息**：它仍然从不建模子弹，它只知道自己的余地更小。

**这张表本身是混淆的，而正是这个混淆决定了常数的形状 —— 这是本轮唯一一次真正的翻车。**

- **第一种形状：给整条墙带定价**（`1 + TRAP_WEIGHT × (push_x + push_y)`）。它**完美地做到了用户要求的事**：贴墙帧 56.6% → **12.0%**，死在角里 **0%**。而它**亏 16% 中位存活**（16.77 → 14.05 s），**每秒受到的伤害反而涨 32%**（7.46 → 9.82）。

  | `TRAP_WEIGHT`（墙带式） | 中位存活 | P10 | 贴墙帧 | 每秒伤害 |
  |---|---|---|---|---|
  | 0 | 16.77 s | 6.17 s | 56.6% | 7.46 |
  | 0.25 | 14.68 s | 4.95 s | 43.3% | 9.83 |
  | 0.5 | 13.55 s | 4.52 s | 23.0% | 10.78 |
  | 1 | 14.05 s | 4.52 s | 12.0% | 9.82 |
  | 2 | 12.40 s | 4.60 s | 8.6% | 10.90 |

  **这不是调参问题：五档代价几乎一样**（都是约 −5 s），响应是**阈值而不是梯度**。**边界对这台机器人是承重地面，从它身上拿走的每一分都用血来付。**

- **第二种形状：只给角落定价**（`2 × TRAP_WEIGHT × push_x × push_y`，**乘积**，所以单面墙一分不罚）。用户对**位置**的直觉是对的，对**原因**的直觉是错的：角落确实是最差的地面，但修法是**不要在里面扎营**，而不是**不要用墙**。

  | `TRAP_WEIGHT`（角落式） | 中位存活（训练 / 留出） | P10（训练 / 留出） | 每秒伤害（训练 / 留出） | 配对 胜/负（训练 · 留出） |
  |---|---|---|---|---|
  | 0 | 16.77 / 19.60 s | 6.17 / 6.78 s | 7.46 / 6.75 | — |
  | 2 | 22.88 / 22.15 s | 8.83 / 7.55 s | 6.14 / 6.43 | 48/30 · 35/37 |
  | **5** | **22.33 / 22.93 s** | **8.83 / 9.28 s** | **6.20 / 6.05** | **54/25 · 46/33** |
  | 8 | — / 22.58 s | — / 8.12 s | — / 6.17 | — · 43/36 |
  | 12 | — / 21.80 s | — / 8.12 s | — / 6.32 | — · 38/39 |

**样本上的诚实交代：** 训练种子上中位 +33%，而**另取 96 颗（offset 300）只有 +13~17%**，配对 46/33。所以「中位存活」是较弱的那条主张。**在两组种子上都成立**的是**最差十分位涨约 40%**（6.2 → 8.8 s，6.8 → 9.3 s）与**每秒伤害降 10–15%** —— 而 P10 恰好就是用户那句话的量（「两次都很快就死」）。5 是两组上同时最好或并列最好的一格；8 与 12 在留出集上单调变差，所以它是**峰值而不是平台**。

**本轮留下的负数，两条，都不许藏：**

- **贴墙帧一步没动**（59.0% → 58.5%）。**这一轮不治「总是往边界跑」**，只治「死在角里」。这两件事在前两轮被当成一件，而实测说它们是两件。
- **反向 18 → 26 次/局**，代价照旧落在方向稳定性上（直线跑 3.52 → 3.39 s）。

**而这一轮真正的产出是一句诊断，不是一句修法：** 「跑到边界」与「死」在这台机器人身上**不是同一件事** —— 边界是它的避难所，而杀死它的是**火力**。子弹在机器人的模型里是**被有意排除**的（§14.1 记着理由：280 px/s 的弹丸穿过猎手 26 px 射程只要 0.09 s，能躲的机器人玩的是人类玩不到的游戏）。所以要让**边界本身**变得不可住，杠杆在**世界**（是什么让边缘成了避难所），不在这个文件里的任何一个权重。

> **六、量结局，不要量过程 —— 而过程指标最危险的地方是它可以长期好看。** 「贴墙帧占比」连续三轮都是这个话题的主指标，而它**度量不了**用户报的任何一件事：机器人可以 59% 的时间贴墙而从不被堵死，也可以 12% 的时间贴墙而死得更快（墙带式那五档就是后者）。**换掉量尺这件事本身比这一轮任何一个常数都重要** —— 前两轮之所以「好点有限」，一半原因是我一直在把用户的那句话翻译成一个我能算的量，而不是去算他那句话里的量。
>
> **七、条件化的那个变量，往往正是要证的东西。** 上面那张暴露量表条件在**旧策略**的位置上，而策略决定「在哪些状态下访问哪些位置」。于是「在墙带的每秒伤害」被读成了「住在墙带会有多危险」，而后者是**错的**：墙带式那五档直接量了这件事，结果是住在开阔地**受伤害更多**。**凡是「按位置分桶」的统计量，只要这个策略自己会选择位置，它就在拿相关性冒充因果** —— 而「位置」在机器人身上恰恰是最被策略摆布的那个变量。
>
> **八、一次测量的形状（阈值还是梯度）决定哪个常数是答案。** 墙带式那五档**看起来**像一个可以调的旋钮，实际是一条**阈值**：0.25 与 2 的代价几乎相同，中间没有可交易的空间。如果我只看 0 / 0.5 / 1 三档并按「取最小的有效值」选，会得到 0.25，而它与 2 一样贵 —— 却会以「更保守、代价更小」的身份被写进文档。**网格的取值必须跨过响应的形状，而不只是跨过一个区间。**

**「加了一个机制」与「这个机制按设计运转了」是两句话，这一条是它们的差价。**

## 15. 弹道与爆炸（bullet / bomb）

> 本轮新增。战斗在此之前是**瞬间命中**（hit-scan）：冷却归零、目标在射程内，就在同一次函数调用里扣血。现在两边都发射**看得见的弹体**，伤害在弹体到达时结算 —— 这不是纯视觉改动，见 15.1。

弹体形状跟着原型走，沿用 §6 已经确立的「一种原型一种剪影」的语言：

| 发射者 | 弹体 | 速度 | 剩余射程 | 备注 |
|---|---|---|---|---|
| 玩家 | 子弹 | 520 px/s | 110 px | 直线、单体 |
| 游荡者 | 子弹 | 280 px/s | 110 px | 同上 |
| 追猎者 | 子弹 | 280 px/s | 110 px | 同上 |
| 重装者 | 炸弹 | `距离 / 引信` | —— | 落到**投掷瞬间**玩家所站的位置，引信 0.4 s 归零即爆 |

子弹与炸弹共用一张 `s.projectiles` 数组和一个 `kind` 判别字段：一个循环、一趟绘制、一次 diff 扫描，而不是两套几乎相同的代码。`kind` 为 `bomb` 时 `blast` 是爆炸半径（32 px）、`fuse` 是剩余引信；为 `bullet` 时两者恒为 0，`range` 是剩余射程。

**为什么玩家和怪物的子弹速度不同（520 / 280）。** 玩家的攻击是自动的（§5.1）：他无法瞄准，也就无法补偿一次打空，而打空是纯损失。怪物打空则相反 —— 那是玩家自己的走位在兑现。所以这个不对称是刻意的，不是疏漏。`bulletRange` 取 110 px（玩家射程的 2 倍）是为了让「朝外逃跑的目标」仍然追得上，同时让流弹死在它自己那个区域里，而不是穿过整个场地打到陌生人。

### 15.1 伤害在命中时结算，于是多了第二个躲避窗口

§7 主张「躲避是空间性的，不是数值赌博」。真实弹道是这条主张的**加强**而不是背离：原本只有一个窗口（在冷却走完之前走出 `m_attackRange`），现在多了一个**飞行途中的窗口** —— 目标在弹体到达之前走开，这一枪就是空的。三个瞄准决定都是这条规则的推论：

- **不做追踪弹。** 追踪会悄悄把 hit-scan 的「必中」还回来，躲避也就没得躲了。
- **不做提前量。** 开火时瞄准的是目标**此刻**的位置，不是预测位置。「目标走开就打空」是这条规则的语义本身；加了提前量，能躲开的动作就只剩下「反向走」。
- **瞄准是连续的。** 速度向量是浮点（`vx` / `vy`）而不是 8 方向 `Dir`：到最近怪物的连线几乎从不是一个罗盘方向，整数化会把 55 px 的一枪变成最多偏 21 px —— 比一只怪物的身体还宽。

### 15.2 画出来的就是判定的

沿用 §10.3 已经为半径立下的规则：

- 子弹的**身体**半径 `bulletRadius = 2.5`，同时也是画出来那条亮线的粗细。命中是「两个圆相触」（§8.4 的同一套写法），所以门槛是 `bulletRadius + 目标半径` —— 对玩家是 11.5 px，对三种怪物分别是 8.5 / 9.5 / 13.5 px。
- 炸弹的**预警圈**画在 `blast = 32` 上，与爆炸判定用的是同一个常量（判定再加 `playerRadius`）。

**判定取的是本步移动前后两点构成的线段，不是终点** —— 和 §8.4 的拾取同一个理由，而且这里更严重：`dt` 被 clamp 到 `maxDt = 0.05`，玩家的子弹一步走 `520 × 0.05` = **26 px**，比任何一种怪物的身体都宽，只判终点会让子弹在两帧之间**穿过**一只怪。反过来，怪物的子弹一步只走 14 px，小于「两圆相触」的 11.5 px 门槛两侧的余量，所以它**不可能**穿透玩家 —— 那一侧的线段判定是形式上的对称，不是修复。

### 15.3 炸弹的躲避规则（这组数值是这么定的）

炸弹落在投掷瞬间玩家所站的位置上，引信固定 `bombFuse = 0.4` 秒，所以它的**速度由距离推导**（`距离 / 引信`）而不是一个固定值。保持恒定的是**预警时间** —— 这也是重装者的弹体被做成最慢的那一个的原因：预警时间恒定，而只有一个慢速攻击者才需要预警。

于是躲避可以写成一个不等式，整组数值都是它的推论：

```
站桩的人需要走出的距离   bombBlast + playerRadius = 32 + 9 = 41 px
扔出后立刻开跑能得到的位移   moveSpeed × bombFuse = 160 × 0.4 = 64 px
```

余量 23 px。而 `dt` 被 clamp 到 `maxDt = 0.05`，20 fps 下一步就是 `160 × 0.05` = **8 px** 的位移 —— 所以**余量必须大于一步**，否则「迟疑一帧就等于没躲」，「躲避窗口」只对已经在跑的人开放，那就不是躲避。

这条不等式是本轮实测**改过一次数值**的原因。原定 `bombFuse = 0.3`：`160 × 0.3` = 48 px 对 41 px，余量 7 px **小于一步** —— 实测确认它确实是假的，在 `maxDt` 下扔出后迟疑一步的玩家最后离落点 40 px，仍然吃到全额伤害。改成 0.4 之后同一组实测：`maxDt` 下迟疑两步仍能走掉、第三步（0.15 s）才吃到伤害；60 fps 下能容忍八步（约 0.13 s）。也就是说炸弹从「必须恰好在这一帧起跑」变成了一个有真实余量的窗口。

### 15.4 炸弹是反站桩工具

重装者的 `m_range` 只有 110 px 而攻击力 18（§6.1），它的圈可以绕开 —— 但只要你**站在**它附近，炸弹就会落到你脚下。设计意图是让它成为 §14.6 那条缺陷的对症药：机器人最严重的毛病是**静止**（55.9% 的帧一动不动），而子弹的飞行只有 0.05–0.1 秒量级，人类来不及反应；炸弹不一样，预警圈画在那里、落点固定、0.4 秒足够读完并走开。它是场上唯一一个**人类和机器人都看得见、也都躲得开**的机制。

**实测：药没有生效，这个期望落空了。** 把 `BOMB_WEIGHT` 拆成 **0 / 1 / 20** 三个对照组跑同一套 96 颗种子（§14.5）。拴区世界里三组的中位倍数都是 6.49×、都是 96/96 跑满、最差都是 3.56×，只有极小的分布差异（空闲帧 55.7% / 55.9% / 56.0%，击杀 23020 / 23002 / 23096）。**拴区解除后重测，连那点差异都没有了：0 与 20 的完整 sweep 输出逐字节相同。** 权重从「完全不躲炸弹」一路调到 20 倍，一格都不动。

**它治错了地方，而这一点现在比当时更清楚。** 当时归因于「静止的根因是拴区阶跃，而机器人静止的那些帧里附近通常根本没有炸弹」—— 那个归因是对的，而拴区阶跃本身随后就随拴区一起消失了（§6.2），静止也随之从 55.9% 掉到 4.3%（§14.6）。**也就是说这条机制在它想治的缺陷已经不存在之后，依然一格都不动** —— 那说明它对机器人行为的实际影响力本来就接近零，与缺陷在不在无关。所以它按**正确性**留下：人类看得见也会躲，忽略它的机器人玩的是另一个更瞎的游戏（§14.1），它不该按修法记账。详见 §14.6。

**不做友伤。** 炸弹只伤玩家。§6 的 AI 和 §14.2 的风险模型都建立在「怪物只伤害玩家」之上，一次会减少场上怪物数量的爆炸是没人预料到的平衡改动。

### 15.5 弹体不是密钥材料

`ProjectileStats` **刻意不进 `GameSnapshot`**，因此不占 `V` 的字节 —— 与药剂（§8.4）同构的理由：飞行中的弹体不是密钥材料，它只通过移动 `V` 已经携带的玩家 / 怪物属性间接影响密钥；而 `V` 定长承载不动一个新窗口（§3.4），加进去会让每个字节的归属随开火抖动。

**弹道路径不消耗任何随机抽样。** 瞄准是确定性的（开火瞬间的目标位置），所以 `s.rng` 的流不会因为多了一次射击而错位 —— 与 `rollDrops` 刻意固定抽样次数（§8.3）是同一条契约。`tests/game-sim.mjs` 里有一条断言专门守着它（「firing spends no randomness at all」：同一个 rng 在「开火」与「不开火」两次运行里被抽样的次数必须完全相等），另有一条守着「同种子逐帧重放弹体的 id / 种类 / 位置」。

### 15.6 机器人只躲炸弹，不躲子弹

`RobotView` 多了一项 `hazards`：只有**飞行中的炸弹**，取它的落点（`bombLanding`）和 `blast + playerRadius` 作为半径，在风险场里按 `damage × BOMB_WEIGHT × CHASE × proximity` 计价。它与怪物项有三处刻意的不同：**没有拴区项**（这一条写在拴区还在的时候；现在整个风险场都没有拴区项了，§6.2），**在半径处硬截断**（圈外一分钱不算，因为爆炸确实只炸圈内），以及**引信不参与**（危险的是那个圈，而不是还有多久落地 —— 这恰好也是画面上能读到的信息）。

三条理由：

1. **子弹不进风险场是诚实，而不是偷懒。** 0.05–0.1 秒的飞行快于人类反应时间；让机器人躲一个人类躲不掉的东西，就是在偷偷放宽 §14.1 的边界。
2. **炸弹的可见性不多于画面。** 预警圈画多久，机器人就看见多久 —— 两者读的是同一个条件（弹体还在飞），圈消失的那一刻它也忘了。
3. **它计入「脚下」的基准分，但不计入承诺门。** 这一条是实测调出来的：`hereRisk`（当时是 `PANIC` / `DISENGAGE` 两个承诺门用的那个）**排除**炸弹，否则一发落在脚下的炸弹在圆心读出 `18 × 3 × 2` = 108（圈边 54），越过当时的 `PANIC` 44，触发整区撤退 —— 对一个「走两步就没事」的东西反应过度；而 `hereForScore`（候选打分用的基准）**包含**它，否则「从炸弹下面走开」会和一个不动的人打平，而平局按规则判给静止。

`BOMB_WEIGHT` 实测是**完全不敏感**的：0 / 1 / 20 三组的完整 sweep 输出逐字节相同（§14.6 有完整数字）。留在 1 的理由是它按炸弹自己的伤害计价 —— 一个能自圆其说的默认值，而不是一个调出来的值。机器的行为不依赖它，正是因为这个量在机器人的活动分布里很少非零。

> **与 §14.2 那条「切向躲子弹」不矛盾，两句话说的是不同的东西。** §14.2 用子弹的飞行几何论证的是**运动学**：切向位移能在 0.182 s 的飞行窗口里偏离火线 29.1 px，超过 11.5 px 的命中阈值，所以环绕**顺带**比直线后退更能活下来。但那是**几何的后果，不是策略的知识** —— 机器人**并不知道**子弹存在，它的分数里没有子弹项（本节三条理由），它不会因为看见子弹而转弯。**一个不瞄准子弹的策略，仍然可以站在一个让子弹打不中的地方**：环绕是为「绕着威胁转」买的，躲子弹是它碰巧赚到的。把这两件事混起来，就会写出一个「因为要躲子弹所以转弯」的理由 —— 那是给机器人安了一个它没有的传感器，也就越过了 §14.1 的边界。
