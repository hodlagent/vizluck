# vizluck · Game tab 玩法设计文档

> 状态：已实现。本文档是**契约** —— `src/game/` 下的代码注释按 §编号引用它，因此**只增不删、不重排编号**。
> 适用范围：`src/tabs/Game.svelte` 及其下的 `src/game/`
> 相关模块：`src/hex/`（密钥构造与命中流程全部复用）

## 0. 一句话概括

**把「搜索」变成「生存」。** 玩家在一个遍布怪物的 3×3 竞技场里躲避、击杀、成长；玩家自身的状态**就是**密钥材料，世界的每一次变化都对应一个新密钥 —— 静止的世界不产生密钥。

---

## 1. 为什么要做这个

Hex tab 是一个「暴力搜索实验室」：盯着一排字节滚动，看 hash160 刷过去。它把彩票式的等待做得很透明，但玩家除了按 Random / Auto 之外**没有任何介入手段** —— 搜索是个黑箱，玩家是旁观者。

Game tab 是同一件事的另一种讲法。目标不是让搜索变快（不可能），而是：

1. **把等待变成有意义的操作** —— 有决策、有风险、有成长曲线；
2. **产生真正无偏的密钥采样** —— 这正是彩票所需要的；
3. **让「命中」这件事有叙事** —— 命中时玩家是在一场自己打出来的局里撞上的，而不是盯着屏幕等出来的。

### 1.1 必须写在最前面的诚实声明

**这个玩法不会「搜出」puzzle。**

`b ≥ 9`（真实数据集里 `b` 取 9..20）意味着一个 puzzle 的区间至少有 `2^72` 个密钥。任何玩法、任何存活时长、任何操作水平都不可能穷尽它。这一点 Hex tab 的 auto 模式同样成立 —— 它跑一整年也扫不完 puzzle #71 的一个零头。

所以请**不要**把 Game tab 理解成「通过玩来解开 puzzle」，也不要据此去评估它的数值平衡。它是一个**把长期无反馈的等待过程游戏化的外壳**，命中是极小概率的彩票事件，而不是可攻略的目标。

## 2. 核心循环

```
   击杀怪物 ──► 获得经验 ──► 升级 ──► 生命上限 ×1.05 ──► 容错变高
        │
        └──► 掉落药剂 ──► 走过去捡起 ──► 攻击力/攻速/移速 ×1.05 ──► 杀得更快
                              │                                     │
                              └─────────────────────────────────────┘

   上述每一步都会改写 V（§3.4），而 V 就是密钥。
   换句话说：**世界的每次变化都是一个新密钥。**

   与此同时：怪物按 n 秒刷新（§4.2）并随时间变强
   （§4.3 密度、§4.4 血量），躲避攻击（走位）贯穿始终。
```

一句话：**怪物是搜索的燃料 —— 但烧的是状态，不是速率。**

**杀怪给两样东西，它们的兑现方式完全不同：** 经验直接入账（只要杀就有，且立刻进 `V[10]`），战斗力则要先**走到怪物倒下的地方**把药剂捡起来（§8.3）。所以「打得动 → 杀得快 → 但站得越久越危险」这个循环里，多了一个空间决策：**什么时候离开安全位置去捡收益。**

**密钥推进不是奖励，是已发生事实的记录。** 游戏不发放「扫描速度」这样的资源（§8.1），所以这里没有速率可以权衡：杀怪之所以推动搜索，是因为杀怪改变了世界 —— 经验、击杀数、怪物集合、走位、拾取后的属性 —— 而这些都是 `V` 的组成部分。

## 3. 密钥映射

> 对应需求第 2、6 条。这是整个设计的核心，也是唯一需要精确到字节的部分。

### 3.1 字节布局

`b = puzzle.hex_bytes_len`（真实数据集为 9..20）。32 字节私钥的排布沿用 `src/hex/range.ts` 已有的语义：

```
   [ 32-b 个 0x00 填充 ] [ 受 range 限制的字节 ] [ b-1 个自由字节 ]
         恒为 0x00          [start_top, end_top]      0x00 – 0xFF
```

以 puzzle #71（`b = 9`，range `[2^70, 2^71)`）为例：

```
 00 ×23  |  0x40 .. 0x7f  | bb bb bb bb bb bb bb bb
   ↑              ↑                      ↑
 填充，恒为 0   受 range 限制        游戏状态唯一的输出口
```

三个部分的归属：

| 部分 | 字节数 | 取值 | 由谁决定 |
|---|---|---|---|
| 填充 | `32 - b` | 恒 `0x00` | 无（游戏不碰） |
| 受 range 限制的字节 | 1 | `[start_top, end_top]` | `randomTopByte(puzzle)`，复用 hex tab 的实现 |
| **自由字节** | `b - 1` | `0x00 – 0xFF` | **游戏状态** |

`end_top === 0` 的上溢情形由 `src/hex/range.ts` 的 `topByteBounds()` 处理，游戏侧不需要关心。

### 3.2 复用：游戏就是一个「由玩法驱动的 grid」

因为自由字节是全范围的，游戏只需要产出 `b-1` 个字节，然后原样喂给已有的构造函数：

```ts
// src/hex/range.ts —— 与 hex tab group 模式完全同一条路径
puzzleKeyHex(puzzle, randomTopByte(puzzle), gameBaseBytes)
```

**零新代码**：密钥构造、range 校验、私有密钥十六进制格式化全部复用。

这个类比很准确：

| | Hex tab | Game tab |
|---|---|---|
| grid 的格子数 | `b - 1` | `b - 1` |
| 格子由谁驱动 | Random 按钮 / hover 循环 / auto 模式 | 走位 / 战斗 / 升级 / 拾取药剂 |
| 高位字节 | `randomTopByte()` | `randomTopByte()`（同左） |

### 3.3 每个自由字节的取值

```
byte[j] = ( owner(V, j) + diffuse(V, j) ) & 0xFF        j = 0 .. b-2
```

| 分量 | 定义 | 作用 |
|---|---|---|
| `owner(V, j)` | `V[j]`，定长状态向量的第 j 项 | **可读性 + 玩家能动性**。字节 j 有固定归属，HUD 能显示「byte 3 ← player.posX」，玩家的操作直接推动它 |
| `diffuse(V, j)` | `expand(fold(V))` 的第 j 个字节 | **均匀覆盖 + 状态完整性**。把全场状态（含每一只怪物）折叠扩散到所有字节 |

**`V` 是仿真状态的纯函数，公式里没有时钟也没有计数器。** 所以同一个 `V` 一定产出同一串自由字节 —— 「世界没变」就等于「没有新密钥」，这不是优化，是这套映射的定义（§3.4 结尾、§9.4）。

#### 为什么必须混合

**纯直接映射不可行**：`player.dir` 只有 8 个取值。若某个字节直接等于它，那个字节就永远只覆盖 `0..255` 中的 8 个值 —— 浪费掉 96% 的范围。方向、区域编号、怪物原型这类低基数属性都有同样的问题。

**纯扩散又丢掉了可读性**：玩家无法感知自己的操作影响了什么，游戏就退化成一个「有怪物陪伴的随机数生成器」。

叠加之后的数学性质：`owner` 是有界的任意项，`diffuse` 是均匀项，**模 256 下均匀项加任意项仍然是均匀的**。所以 `byte[j]` 的整体分布由 `diffuse` 主导，覆盖率得到保证；同时 `owner` 保留了「哪个属性影响哪个字节」的可读性和玩家的直接操控感。

#### `fold` / `expand` 的具体选择

- `fold`：FNV-1a 32 位，以 **`puzzle 编号`** 为初始种子，逐字节吞掉整个 `V`。
- `expand`：splitmix32 PRNG，用 `fold` 的结果作种子，按需吐出字节。

> ⚠️ **`V` 里不包含 puzzle 编号，但 `fold` 的种子必须异或上它。** 否则切换到另一个 puzzle 时会产出完全相同的密钥串。

### 3.4 状态向量 V（定长，`|V| = 63`）

**定长是关键设计约束。** 怪物数量每时每刻都在变；如果 `V` 长度可变，那么某只怪物一死，它后面所有字节的归属就会整体错位，HUD 上的归属提示会疯狂乱跳，玩家会觉得「字节在乱变」。

因此固定布局，空槽位补 `0`：

```
V[0]       = player.dir             // 0..7
V[1]       = q(player.posX)
V[2]       = q(player.posY)
V[3]       = q(player.hp / maxHp)
V[4]       = q(player.attackPower)  // 只有强化药剂会改变它（§8.2）
V[5]       = q(player.moveSpeed)
V[6]       = q(player.attackSpeed)
V[7]       = q(player.attackRange)
V[8]       = q(player.hpSpeed)
V[9]       = q(player.level)
V[10]      = q(xp / xpForNext(level))
V[11]      = region.index           // 玩家所在区域 0..8
V[12]      = q(region.targetCount)  // 该区域的目标怪物数（场景数据）
V[13]      = q(region.respawnSec)   // 该区域的刷新间隔（场景数据）
V[14]      = q(kills)
─────────── 以下 8 只怪物 × 6 项 = 48 ───────────
V[15+6i+0] = m.dir
V[15+6i+1] = q(m.posX)
V[15+6i+2] = q(m.posY)
V[15+6i+3] = q(m.hp / m.maxHp)
V[15+6i+4] = q(dist(player, m))
V[15+6i+5] = m.attacking ? 1 : 0
```

`q()` 是量化到 `0..255` 的整数（位置按竞技场尺寸归一化，比率按百分比，绝对值按各自量程缩放后 clamp）。

`V[10]` 用 `xp / xpForNext(level)` 而不是固定除数：`xp` 会一直涨到 `100 × level` 才归零，任何常数都会很快饱和。这和 `V[3]` 用 `maxHp` 归一化是同一个形状 —— 分母是活的，所以这个字节**始终铺满整个 `0..255`**，不会随着等级升高而挤在某一端。（`sim.ts` 的 `while (s.xp >= xpForNext(s.level))` 保证了 `xp < xpForNext`，所以 `q()` 的上界恰好用满；`xpForNext(level) = 100 × level ≥ 100`，也不存在除零。）

#### 为什么删掉了 tick

`V[0]` 曾经是一个 tick 计数器，存在的唯一理由是「玩家站在空角落里不动时密钥也要动」。**这个前提是错的**：密钥是**世界状态**的函数（§3.3），而 tick 是时间 —— 它用时间伪造了一个「状态变了」的假象，代价是整个映射里混进一个和玩法无关的量，还让「世界不变则密钥不变」这条性质不再成立。

删掉之后 `V[0]` 回到 `player.dir`，而**静止的世界也不会永久静止**：§4.3 的难度升级每 30 秒改写一次 `region.targetCount` / `respawnSeconds`，两者都在 `V` 里；怪物自己也在游荡。

> ⚠️ 「世界不变则密钥不变」这句话说的是**自由字节**（`b-1` 个低位字节），不是最终密钥：高位字节仍然来自 `randomTopByte()`（§3.1），每次调用都是新的 CSPRNG 取样（`src/hex/range.ts`）。实现之所以比较 `V` / 自由字节而不是比较密钥，正是因为密钥每次都不同（§9.4）。

#### 怪物窗口 = 8

只取**离玩家最近的 8 只**怪物填入 `V`，排序键为 `(距离, spawnId)` —— 加 `spawnId` 是为了在距离相同时保证**确定性**，否则同一帧内排序结果不稳定，密钥会抖。

这个窗口设计让「靠近怪物」这件事本身改变密钥：**贴脸战斗和躲在角落的采样路径完全不同**，与「怪物是燃料」的核心循环一致。

#### 低基数属性的处理

`player.dir`（8 值）这类属性，即使作为 `owner` 也只贡献 8 个值；它们对密钥的**主要贡献来自 `fold`**（进入种子），`owner` 只是让玩家在 HUD 上看得见它。

#### 不进 `V` 的东西

**药剂（§8.4）与弹体（§15）都不进 `V`。** 它们不是密钥材料 —— 只通过改变 `V` 已经携带的玩家 / 怪物属性间接影响密钥 —— 而 `V` 定长承载不动新窗口：加一个「场上的掉落物」或「飞行中的弹体」窗口，会让每个字节的归属随一次击杀、一次开火而整体位移，HUD 的归属提示会跟着抖。

## 4. 场景与区域

> 对应需求第 4 条。

场景 `w × h`（= `GAME_WIDTH × GAME_HEIGHT` = 960 × 540）划分为 **3×3 = 9 个区域**，每个区域的**目标怪物数**与**刷新间隔**相互独立。

### 4.1 风险/收益的空间梯度

| 区域 | 位置 | 目标怪物数 | 刷新间隔 | 主要怪物 |
|---|---|---|---|---|
| 4 个角落 | 四角 | 2 | 6.0 s | 游荡者 |
| 4 个边中 | 四边 | 4 | 4.0 s | 游荡者 / 追猎者 |
| 1 个中心 | 中央 | 6 | 2.5 s | 重装者 / 追猎者 |

**地图本身就是一个风险旋钮，而旋钮控制的是「状态变化量」：**

- **角落 = 低产出的地方。** 刷新最慢、怪最少，所以**状态变得最慢**：2 只游荡者，血不掉、经验不涨、击杀数不动，`V` 因而长时间持平 —— 待在这里就是「活着但不搜索」。
   > **但它不再安全。** 区域只划分刷新、不划分移动（§6.2），追猎者的 `m_range` 比一个区域还大，所以在角落出生的玩家 t=0 就会被邻区的怪罩住。角落的「安逸」来自**怪少**，不来自**墙**。
- **中心 = 收益区。** 密度最高、刷新最快、高危原型最集中，**状态持续变化**：有杀、有伤、有升级、有拾取，`V` 每一帧都在改写 —— 也是死得最快的地方。

  > 注意：**药剂的掉落概率与区域无关**（§8.3 是一张全局表）。中心之所以药剂多，只是因为**那里有的杀**，不是因为每一只掉得更好。收益完全来自「单位时间的击杀数」，而这一点恰好也是死亡率的来源。

于是「走到哪」成为玩家的核心决策，而**移动本身又会直接改变密钥字节**（`player.posX/posY` 在 `V` 里）。空间决策与搜索推进在这里是同一件事。

### 4.2 刷新规则

每只怪物被击杀后，按**它所属区域**的刷新间隔、在**该区域内**的随机位置重生。各区域节奏完全独立 —— 这就是「每个区域的怪物数量和刷新速度是独立的」。

### 4.3 全局难度升级

每存活 **30 秒**，所有区域：目标怪物数 `+1`、刷新间隔 `×0.9`（各有上限/下限封顶）。

这让任何一局最终都会结束 —— 存活时间因此成为一个有意义的分数。没有这个升级，高手可以无限期地待在角落，分数失去区分度。

### 4.4 怪物血量按分钟复利升级

> 对应**迭代二**需求第 1 条（怪物的升级）。下文同：§8.2 对应迭代二需求第 2 条，§8.3 / §8.4 对应第 3 条。

每存活 **60 秒**，怪物血量乘数 `×1.05`（复利），即第 N 分钟结束时的乘数为 `1.05^N`。

实现上**不新增计时器字段**，直接从存活时间推导：

```
monsterHpMul(time) = monsterHpGrowth ** floor(time / monsterHpEvery)
```

`spawnMonster()` 在生成时把 `arch.hp × monsterHpMul(s.time)` 同时写进 `hp` 和 `maxHp`。

**只作用于新刷新的怪物，已存在的怪物不追溯。** 这不是偷懒，是有意的：

- 区域刷新间隔只有 2.5–6 秒，一分钟内场上怪物基本换过一轮，追溯与否的效果差异很小；
- 而给一只**正在挨打**的怪物凭空加血，读起来是「打不动了」的 bug，不是难度。血条凭空变长是最容易被误解成故障的反馈。

§4.3 抬的是**密度与节奏**（更多、更快刷新的怪），§4.4 抬的是**单只怪的分量**。两条曲线叠加，才让「苟在角落」的边际收益随时间真正归零。

## 5. 玩家

> 对应需求第 3 条。

| 属性 | 初始值 | 说明 |
|---|---|---|
| `dir` | 由输入决定 | **8 方向**，与需求一致 |
| `moveSpeed` | 160 px/s | 走位速度，躲攻击靠它 |
| `attackSpeed` | 1.5 次/s | **自动攻击**的冷却 |
| `attackPower` | 8 | 每次攻击伤害 |
| `attackRange` | 55 px | 自动攻击的索敌半径 |
| `hp` | 100 | 归零即本局结束。上限见 `maxHp`，两者**不是一回事** |
| `maxHp` | 100 | **唯一的成长轴**：升级与生命药剂各自 `×1.05`（§8.2 / §8.3）。抬高上限**不回血** |
| `hpSpeed` | 1.0 /s | 脱战 3 秒后开始回血 |
| `posX, posY` | 角落区域中心出生 | 不得越出场景边界 |

### 5.1 为什么攻击是自动的

需求第 1 条规定 UI 里没有战斗键的位置：**下拉框** 和 **暂停/运行按钮**，加上 §14 的模式开关——后者不进游戏循环，见 §10.1。没有攻击键的位置。

所以攻击设计为**对 `attackRange` 内最近的怪物自动出手**。这个选择有三个好处：

1. 符合 2 控件的 UI 约束；
2. 玩家只需要专注走位，操作门槛低、反馈直接；
3. `attackPower / attackSpeed / attackRange` 从「按钮」变成**可被感知、可成长的属性** —— 也正好让它们作为密钥材料有意义。

### 5.2 脱战回血

最后一次受伤后 **3 秒**开始按 `hpSpeed` 回复。

这是「脱离接触」这个决策的收益来源：**只要真的跑出所有感知圈，血就回来了。** 但它的搭档在 §6.2 之后换了人 —— 曾经的节奏是「中心冒险 → 受伤 → 撤回角落回血 → 再冲进去」，靠的是角落既低产出又安全；现在**角落不再安全**（§4.1），回血只与「多久没挨打」有关，与站在哪里无关。所以撤退的方向不再是「回角落」，而是**任何一条能跑出感知圈的路**，而跑出去需要的那 ~3.9 秒不中断直线见 §6.2。

## 6. 怪物

> 对应需求第 5 条。

三种原型，字段全部来自需求 5：

> 下表是 `m_hp` 的**基准值**。实际生成时还要乘以 §4.4 的时间乘数 `monsterHpMul(time)`，`hp` 与 `maxHp` 同时取该结果。

| 原型 | `m_hp` | `m_moveSpeed` | `m_attackPower` | `m_attackSpeed` | `m_attackRange` | `m_range`（感知） | 经验 | 半径 | 弹体（§15） |
|---|---|---|---|---|---|---|---|---|---|
| **游荡者** | 20 | 50 | 5 | 0.8 /s | 22 px | 140 px | 10 | 6 px | 子弹 |
| **追猎者** | 35 | 120 | 8 | 1.2 /s | 26 px | 260 px | 20 | 7 px | 子弹 |
| **重装者** | 90 | 40 | 18 | 0.6 /s | 34 px | 110 px | 40 | 11 px | 炸弹 |

`m_dir` 同样是 8 方向，始终朝向自己的移动方向 / 朝向目标。

**身体半径**（6 / 7 / 11 px）由 `sim.ts` 拥有，而不是留在渲染层：它既是剪影的绘制半径，也是 §15 弹体命中判定的门槛（`半径 + bulletRadius`）—— 也就是 §10.3 那条「画出来的就是判定的」在多了一个消费者之后的写法。

### 6.1 行为

```
if dist(player) <= m_range:              # 感知到就锁定
    m_dir = 朝向玩家（8 方向取整）
    朝玩家移动（移动范围只夹在场地边界内，见 §6.2）
    if dist(player) <= m_attackRange and 攻击冷却就绪:
        发射按原型决定的弹体（§15），伤害随弹体飞
        攻击冷却 = 1 / m_attackSpeed
else:                                   # 未感知
    在自己的 home 区域内随机游荡
```

**注意两行的夹取范围是不同的，这是 §6.2 的改动。** 游荡仍然夹在自己的 home 区内（那是刷新配额的账本，不是移动边界），而**追击可以跨出 home 区直到场地边缘** —— 感知范围是唯一的追猎边界。打断追击的只有一件事：玩家跑出 `m_range`。

**冷却计的是「出手」，不是「命中」。** 冷却在弹体生成的那一刻重置，与 hit-scan 时代完全一致 —— 变的是伤害的到达时间，不是出手的节奏。所以 §6 这张表里 `m_attackSpeed` 的含义一个字都没变。

**感知范围 `m_range` 是设计里最有意思的一个字段。**

- **重装者**感知只有 110 px，但攻击力 18（游荡者的 3.6 倍）。它「看不见」远处的你 —— **只要不进它的圈就绝对安全**。
- **追猎者**感知 260 px，在整个区域内几乎全程锁定，是强制位移压力 —— 逼你在边中/中心区域持续移动，而不是站桩输出。

于是走位从「跑开」升级为**绕开视野圈**：玩家需要读怪物的感知半径，规划一条不触发高危怪物的路线。这是躲避玩法的技术深度所在。

### 6.2 区域划分刷新，不划分移动

**怪物可以离开它的 home 区域** —— 游荡会走遍全场，追击也会（§6.1 的两个条件）。唯一的边界是**场地边缘**：`wander` 与追击位置都夹在 `arenaPad` = 14 px 的内缩矩形里，撞到就镜像方向。

九宫格因此退回它本来的身份：**刷新分区 + 刷新配额账本**（`countInRegion` 按 home 计数，§4.2）。它不划分怪物的活动范围，也不划分战斗。

**这条规则是刻意反转的，反转的代价必须写在这里。** 曾经的版本是「怪物被拴在自己区域内」，理由是让 §4 的区域梯度成立 —— 若允许跨区追击，角落这个「安全区」就不存在了。反转的直接后果就是如此：

- **角落不再安全。** 玩家的角落出生点在 t=0 就会被 5 只怪罩住，其中 3 只在邻区；追猎者的 `m_range` 260 px 远超一个区域的尺寸（边中只有 320 × 180）。§4.1 的梯度因此不再是「安全 / 危险」的梯度，而是**刷新密度和击杀率**的梯度。
- **脱战变成一件要练的事，而不是走回边界。** 仇恨现在只看 `m_range`（§6.1），所以断仇恨的唯一办法是**拉开距离**。实测三种原型：游荡者（50 px/s）0.3 s、重装者（40 px/s）0.1 s，而**追猎者（120 px/s）需要约 3.9 s 不间断的直线跑**（= 160 px 间距 ÷ 40 px/s 的净接近差，需要约 640 px 跑道；场地 960 × 540）。一旦在墙上转身，收益全部归零。
- 这条 3.9 s 的门槛**正是** §14.2 要机器人「锁定方向」的原因：一个每几帧翻一次方向的机器人永远凑不出这 3.9 s，对它而言脱战机制等于不存在。
- **已知的、用户尚未拍板的代价**：站桩存活从 92 s 塌到约 3.2 s。这是「角落不再安全」的直接后果，属于难度基调问题，与机器人策略分开处理。

反过来，这条规则也**没有**制造「站在区域外无伤刷怪」的漏洞：玩家的 `attackRange` 只有 55 px，想够到怪物就要贴上去，而那时怪物的 `m_attackRange`（22–34 px）同样够得到你。贴上去蹭怪仍然要付血价。

## 7. 战斗

| 方向 | 触发条件 | 节奏 | 伤害到达 |
|---|---|---|---|
| 玩家 → 怪物 | 目标在 `attackRange` 内，取**最近**的一只 | 按 `attackSpeed` 冷却 | 弹体命中时（§15） |
| 怪物 → 玩家 | 目标在 `m_attackRange` 内 | 按 `m_attackSpeed` 冷却 | 弹体命中 / 炸弹爆炸时（§15） |

**躲避是空间性的，不是数值赌博。** 这条主张有两个窗口，而不是一个：

1. **冷却窗口。** 玩家只要在冷却走完之前走出 `m_attackRange`，这次出手就不成立。
2. **飞行窗口**（§15）。出手成立之后，伤害还要飞一段才到 —— 目标在弹体到达之前离开那条线，这一枪就是空的。炸弹把第二个窗口放大成肉眼可见的一档：落点圈画在地上，0.4 秒的引信足够走开（§15.3）。

**死亡**：`hp <= 0` → 本局结束，存活时间定格。弹体随之冻结 —— `stepSim` 在 `!alive` 时直接返回，所以死在一发炸弹落地之前的话，它会停在半空中。

## 8. 成长与资源

### 8.1 算力（hashpower）—— 已移除

> 这一节保留编号，因为它记录的是一次**删除**：代码注释按 §编号引用本文档，重排编号会让别处的引用失效。

**曾经是什么。** 一个 0..100 的资源：击杀 +1/+2/+4，自然衰减 3/s，再线性映射到密钥采样速率 `2 + 18 × (hashpower / 100)`，即 2~20 keys/s。它是「击杀 → 搜索」的唯一换算通道，被称为「整个玩法的支点」。

**为什么删掉。** 它假设「采样速率」是玩家可以用玩法买到的东西 —— 但密钥是世界状态的函数（§3.3 / §3.4），所以「每秒采多少个」根本不是一个游戏能控制的量：它是**世界自身的变化速率**，上限是帧率（每个仿真步至多一次提交，§9.4）。把一个不由游戏决定的量当成资源来发放，只会让数值平衡去调一个假旋钮。

**随之而来的三处改动：**

1. `V` 里原本放 hashpower 的那个槽位现在放 `xp`（§3.4）；
2. §4.1 的区域梯度改用「状态变化量」重新解释 —— 角落与中心的差别没有消失，只是不再用扫描速率来描述；
3. §10.2 的 HUD 少了「算力」和「采样 keys/s」两个读数。

**活下来的是什么。** 杀怪依然推动搜索 —— 通过经验、击杀数、怪物集合、走位、以及拾取后的属性，全部都在 `V` 里 —— 而不是通过一个读表节奏。

### 8.2 等级：只涨生命力

> 对应迭代二需求第 2 条。经验值系统本身在迭代一就已存在（`xpForNext(level) = 100 × level`），本次改的是**升级的内容**。

击杀获得经验（游荡者 10 / 追猎者 20 / 重装者 40，见 §6 表；与 §8.3 的药剂掉落无关）。升到第 N 级需要 `100 × N` 经验。每次升级：

```
maxHp *= 1.05        （hp 不变）
```

**升级不再提供攻击力/攻速/移速。** 上一版那六项加法加成已经删除，原因只有一个：如果升级本身就涨战斗力，药剂就只是「慢一点的升级」，掉落系统失去存在理由。现在分工是干净的：

| 轨道 | 提供 |
|---|---|
| 等级（经验） | **血量上限** —— 容错空间 |
| 药剂（掉落） | **战斗力与机动** —— 攻击力 / 攻速 / 移速 |

两条轨道的来源也不同：经验来自「击杀数量」，药剂来自「击杀位置」—— 后者要求你走过去，见 §8.3。

抬高上限时**当前 `hp` 不动**（`50/100` → `50/105`），与生命药剂语义完全一致：上限是容量，不是补给。

因为**所有属性都在 `V` 向量里**，升级会改变密钥字节 —— 玩家变强这件事本身就在移动采样位置。这是「玩家的状态就是密钥材料」这句话的具体兑现。

经验的另一处可见性：击杀位置会飘出 `+10` / `+20` / `+40` 的数字（§10.3），读的正是 §6 表的经验列，所以它不可能和真正让玩家升级的规则不一致。

### 8.3 掉落与药剂

> 对应迭代二需求第 3 条。

怪物死亡时，在**死亡点**掉落药剂。四种药剂**各自独立掷骰**，所以一次击杀可能什么都不掉，也可能同时掉多个。

| 药剂 | 概率 | 效果 |
|---|---|---|
| 回复药剂 `heal` | 22% | `hp = min(maxHp, hp + 0.30 × maxHp)` —— **封顶不回溢** |
| 强化药剂 `power` | 14% | `attackPower ×1.05` **且** `attackSpeed ×1.05` |
| 敏捷药剂 `agility` | 14% | `moveSpeed ×1.05` |
| 生命药剂 `vitality` | 9% | `maxHp ×1.05`，`hp` 不变 |

**「独立判定，且不保证掉落」是刻意的。** 加权单抽表（总和 100%）会让每次击杀都必然有产出，击杀变成稳定的收入流；独立判定下约 **52% 的击杀不掉任何东西**，期望每次击杀 0.59 个。收益因此是**方差**而不是**速率** —— 玩家不能按「每杀 N 只就有 M 瓶」来规划，只能按「现在这一片值不值得进去」来判断。

概率值是 `sim.ts` 里的 `DROP_CHANCE` 一组常量，随时可调。

**掉落的是一次性收益，条件是走过去。** 药剂躺在怪物死掉的地方，不在玩家脚下 —— 「走到哪」因此从纯防御问题（躲开攻击）变成了攻防一体的取舍（为了收益进入危险区，并在那里多停一会儿）。

| 参数 | 值 | 说明 |
|---|---|---|
| `pickupRadius` | 5 px | **药剂自己的**半径，同时也是画出来的视觉半径 |
| `playerRadius` | 9 px | 玩家的身体半径，同时也是画出来的视觉半径 |
| 拾取判定 | `playerRadius + pickupRadius` = **14 px** | 两个圆相触即算「踩上去了」（推导见 §8.4） |
| `itemLifetime` | 30 s | 之后消失 |
| `itemFlicker` | 10 s | 消失前最后 10 秒开始闪烁 |

一次掉多个时，它们按索引散布在死亡点周围一个约 11 px 的小圆上，避免完全重叠成一个；只掉一个时精确落在死亡点。

### 8.4 拾取

拾取是**自动**的（与自动攻击同理：需求第 1 条只给了 2 个控件，没有拾取键的位置）。玩家不需要按键，只要**经过**道具即触发。

**判定的是两个圆相触，不是玩家的圆心落进药剂里。** 玩家自己有 9 px 的身体，药剂 5 px，所以「看起来踩上去了」是圆心距 ≤ `playerRadius + pickupRadius` = **14 px**。这一条曾经写错过：判定只比了药剂自己的 5 px，于是 5–14 px 之间有一个**死区** —— 玩家在画面上整个人盖住药剂，规则却认为还没走到。而移动中的玩家**几乎总是**落在死区里：只有 8 个方向，玩家是**掠过**药剂而不是把圆心对准穿过去。结果就是必须停下来、来回蹭几下才捡得到，恰好把「走过去」这个动作的手感毁掉。实现上 `playerRadius` 由 `sim.ts` 拥有，`GameScene` 也引用同一个常量来画玩家和药剂，所以画面和判定不可能再分家。

判定用的是**本步移动前后两点构成的线段**到道具的距离，而不是终点距离。原因是：`dt` 被 clamp 到 `maxDt = 0.05`，慢帧一步能走 8 px，敏捷药剂叠起来还能更快 —— 只判终点会**穿过**道具而不拾取。有了线段判定，速度堆上去之后也不会漏捡。

**药剂不是密钥材料。** 掉落物**不进 `GameSnapshot`**，因此不占 `V` 的字节。它们通过改变 `maxHp / attackPower / attackSpeed / moveSpeed` 间接进入向量 —— `V` 是定长的（§3.4），加一个掉落物窗口会移动每个字节的归属，HUD 的归属提示会整体错位。

## 9. 运行 / 暂停 / 匹配流程

> 对应需求第 1、6 条。

### 9.1 状态机

```
   未选 puzzle ──► IDLE         ▶ 禁用，画布显示「请选择一个 puzzle」
        │ 选择 puzzle
        ▼
   READY ⇄ RUNNING              ▶ / ⏸ 手动切换
        │        │
        │        ├── 切到别的 tab ──► 自动暂停，运行意图复位
        │        │                    切回来保持暂停，必须手动点 ▶
        │        │
        │        └── hp 归零 ──► DEAD，存活时间定格，▶ 可重开
        │
        └── hash160 命中 ──► MATCHED，全部暂停 + 保存私钥
```

### 9.2 三条硬规则

1. **未选 puzzle 不能运行。** 没有 range 就没有字节布局（§3.1），`▶` 直接禁用。
2. **切走 tab 自动暂停。** 复用 `App.svelte` 已有的 `active` prop 协议。注意：`hidden` 属性**不会**触发 `document.visibilitychange`，所以 Phaser 自带的可见性处理在这里是失效的，必须由这条协议接管。
3. **切回来不自动恢复。** 这是与 Hex tab 的**关键差异**：Hex tab 选择继续后台跑（见 `App.svelte` 的注释），Game tab 必须**手动点 ▶ 继续**。实现上，`setActive(false)` 时要顺手把「运行意图」也复位成 `false`，这样切回来按钮就是 ▶。

### 9.3 暂停 = 停止搜索

暂停冻结仿真；仿真冻结则 `V` 恒定，于是**没有新密钥可以提交** —— 搜索自己就停了，没有任何东西需要被显式停掉。

这比旧实现（暂停时停掉密钥循环）更强：现在是**结构性**的，「暂停着还在后台扫」在 `V` 这一层就不可能发生，因为根本没有一个独立于仿真的时钟。

仍然有两条防线，只是职责变了：

- `syncStatus()` 依然是唯一决定 `setPaused()` 的地方，也是唯一决定「运行意图」的地方；
- 采样在**仿真真正走了一步之后**才可能发生（§9.4），并且只在意图是 `running` 时（READY 状态下画布也在渲染，但仿真没走，不产生密钥）。

### 9.4 密钥推进流程

**每当世界状态发生变化**（`V` 与上次提交的不同），走一遍：

1. 游戏状态 → `V` → `b-1` 个自由字节（§3.3）
2. 与上次提交的自由字节比较，相同则结束 —— 世界没变，没有新密钥
3. `randomTopByte(puzzle)` 取受 range 限制的高位字节
4. `puzzleKeyHex()` → 64 字符私钥 hex
5. 调 **`derive_group([keyHex])`**（`src/hex/api.ts`）
6. 命中 → 暂停 + 落盘 + `MatchBanner` + 标题行上的 ✅

触发点是场景的每一帧（`GameScene.update()` 末尾），所以推进速率的上限是帧率。**没有定时器，也没有速率常数** —— 世界变得多快，密钥就推进得多快。

> **同一时刻至多一个 `derive_group` 在途。** 在途期间到达的新状态不排队：等在途的那次落地后**重新看一眼当前世界**。排队的状态一定比当前状态旧，没有保留的价值。

> **两类边界，两种处理，区别是刻意的。** `generation` 只在**换局**时自增 —— 重开、换 puzzle、卸载。这三件事之后的世界和之前的世界没有关系，所以在途结果必须作废，否则一个上一局的密钥会画进这一局。
> **暂停、死亡、命中不作废在途结果。** 这三者都没有改变世界，只是让它停住：在途的那个密钥取自最后一个被 step 过的世界状态，而那恰好就是画布上冻结的那一帧。它在暂停后落地、被计入 `keysScanned` 并显示出来，是**一致**的，丢掉它才是浪费一次已经付过钱的 IPC。
> 暂停真正保证的是**不再发起新的提交**，这一点由 `canSample()` 在 `onFrame` 的入口处守住。实测：暂停后 3 秒内 0 个新密钥。

> 显示节流：密钥读数与字节条按固定间隔重绘，而 `keysScanned` 每个密钥都计数。两者的职责不同 —— 前者是给人看的，后者是这次运行真实花掉的成本。

> ⚠️ **必须用 `derive_group`，不能用 `derive_full`。**
> `derive_full`（`src-tauri/src/homepage.rs:618-627`）只做比对，**从不调用 `save_match`**，命中结果不会落盘。
> `derive_group`（`homepage.rs:640-672`）是唯一对「调用方已知私钥」执行持久化的命令，且在命中时自动写入 `{timestamp}.txt`。
> 这也正是 Hex tab group 模式使用的同一个命令。

```
└ 标题 ┘ └─ 私钥非零部分 ─┘ └ 压缩地址 ┘ 命中  └── §14 的模式开关 ──┘  └── 需求第 1 条的 2 个控件 ──┘
```

**运行状态不再占一格。** 这里曾经有个 `idle / ready / paused / matched` 的文字标签。它和画布上的遮罩（`READY` / `PAUSED` / `GAME OVER`，即 §9.1 那几个状态的画法）说的是同一件事，而遮罩就画在玩家正在看的地方 —— 同一句话不必说两遍。状态机本身没有消失，它仍然驱动暂停协议（§9.4）与 `▶ / ⏸` 的可读性，只是不再打印给人看。

模式开关排在两个玩法控件**左侧**，因为它管的是「谁在玩」，而不是「玩什么」——离开玩法本身越远的东西越靠外，读起来才是「先决定谁玩，再决定玩哪一局，再决定跑不跑」。

控件用 `margin-left: auto` 顶到最右，与左侧读数分开——两者性质不同，一片留白比一个 gap 更能说明这件事。窗口变窄时整行 `flex-wrap` 换行，控件落到第二行，仍然靠右，不溢出。

左侧读数三项：

- **私钥的非零部分**：`puzzleKeyHex()` 在 range 之上全是 `00` 填充，展示完整 64 字符等于一堵零墙，把本局真正的产出挤到最右边。剥掉填充后剩下的就是玩家正在推动的那一段。点击复制完整 64 字符。
- **压缩地址**：点击复制。命中时转绿（`✅`），未命中为暗色（`❌`）。
- **命中图标**：`address_match`，与 `handleMatch()` 读的是同一个字段。

> 早期版本在底部复用 `AddrInfoPanel` 显示私钥 / xprv / 地址三张卡片。xprv 对本局没有意义（它由私钥唯一决定，不会随玩法变化），三张卡片的信息密度又远低于它占的位置，因此收进标题行。

### 10.1 控件（需求第 1 条的 2 个 + 1 个模式开关）

```
[ 👤 manual │ 🤖 robot ]   [ puzzle 下拉框 ▾ ]   [ ▶ / ⏸ ]        ← 位于 §10.0 的顶栏右端
```

- **下拉框**：列出全部 puzzle，显示 `#71 · 9 bytes`。选中后才允许运行。
- **按钮**：`▶` 运行 / `⏸` 暂停。未选 puzzle 时禁用；命中后锁定；死亡后按下 = 重开新局。
- **模式开关**（§14）：`👤 manual` / `🤖 robot`，两格的分段控件，命中后一并锁定。

**为什么是两个按钮而不是一个复选框。** 复选框说的是「你做过什么」（勾没了就不知道当初勾的是哪一项），分段控件说的是「你现在在哪」——而模式的全部意义就是那个当前态，它必须一眼可读。

**为什么它不算破坏需求第 1 条。** 需求第 1 条要的是「玩家不需要攻击键、不需要拾取键」，那条约束针对的是**玩法输入**：进场之后，除了方向键没有第二个键要按。模式开关在玩法之外——它决定这一局由谁驱动，而且在 `manual` 下与旧版逐帧等价。所以三个控件里有两个是需求原文的，第三个不参与游戏循环。

### 10.2 HUD（只读）

HUD 是**竞技场下方的一条**，不在标题行里：它报的是这一局累积出来的东西，看一眼就够，不该跟控件抢顶栏的位置。它与画布同属一个区块（`.game-arena`，间距 10px）—— `.game-main` 的 28px 是用来分隔区块的，不是用来分隔图注的。

```
存活 02:47.3   最佳 05:12.8   等级 7   经验 340/700   HP 84/170   击杀 63   keys 4,182
```

**经验**紧挨着等级：本次迭代之后，等级数字本身不再说明成长（升级只涨上限），进度条才是玩家真正在追的东西。

**掉落不再有读数。** 这里曾有一行 `掉落 ●12 ●7 ●5 ●2`，同时充当掉落物的**图例**：四个色点按 `heal / power / agility / vitality` 固定顺序排列，悬停给出文字说明。这一行连同图例一并删掉了。留下的后果是画布上的药剂只剩颜色可辨 —— `GameScene.readPalette()` 仍然从 `--loot-*` 变量取色（那几个变量因此保留），但场上没有任何地方再说明哪个颜色是什么。

`HP` 的上限显示为 `Math.round(maxHp)`：`maxHp` 在 sim 里是 `×1.05` 的连乘，浮点真值会带尾巴（`1.5 × 1.05 = 1.5750000000000002`）。**取整只发生在显示层** —— 在 sim 里取整会让复利每级漂移一点，且 `hp` 本来就因为回血是浮点的。

外加一行**字节归属提示**，把 §3.3 的可读性兑现成玩家看得见的信息：

```
byte0 ← player.dir    byte1 ← player.posX    byte2 ← player.posY    byte15 ← m[0].dir   …
```

（`V[0]` 回到 `player.dir` 之后，条子开头的四个归属全是玩家自己的实时状态，见 §3.4「为什么删掉了 tick」。）

这是「混合式映射」相对于「纯扩散」唯一但关键的回报：玩家能看到自己的操作在推动哪些字节。

字节条会**完整**展示 `b-1` 个自由字节（8–19 个）—— 它就是 Game tab 版的「grid」。归属说明只标前 4 个，避免 b 较大时糊成一片。

### 10.3 画布上的可见性规则

环形感知圈（`m_range`）是核心战术，但场上有约 30 只怪物 —— **全部画出来会织成一张网，反而谁都看不清**。所以：

- **只画玩家可能踏入的那些圈**：`dist(player, monster) ≤ m_range + 60`。60 px 略大于玩家的 `attackRange`（55），于是「看得见的圈」= 「打得着的怪」= 「需要绕的怪」。
- **已锁定的圈更亮**（alpha 0.5 vs 0.22），一眼能分辨「它看见我了」和「我在它边缘」。

地图其余部分因此保持安静，区域色调（角落偏蓝 / 边中偏金 / 中心偏红）才能真正读出来。

**地上的药剂必须一眼可辨种类，而且不能只靠颜色。** 场上最多同时躺着十几瓶，颜色在重叠时会失效，色觉差异也会让整张表作废。所以每种药剂除了色相（`--loot-*`）还有一个**独立的剪影**，沿用怪物那边已经确立的「一种原型一个形状」的语言：

| 药剂 | 剪影 |
|---|---|
| 回复 `heal` | 十字（两个 `fillRect`） |
| 强化 `power` | 正三角 |
| 敏捷 `agility` | 朝右的三角 |
| 生命 `vitality` | 圆环 |

**击杀处飘出 `+10` / `+20` / `+40`** —— 数字直接读 §6 表的经验列，和让玩家升级的是同一个字段（§8.2）。它留在怪物倒下的位置，而拾取药剂的那一下是从**玩家身上**炸开的：一个说「这里死了什么」，一个说「你拿到了什么」，两者在同一帧同时发生也不会被看混。

**弹体是这条「不只靠颜色」规则的一个例外，而例外有它的理由。** 子弹确实只靠颜色分敌我（`--accent` 绿 / 红，与两侧的单位配色一致）：它们只存在 0.1 秒、体积只有 2.5 px，而**方向本身就把信息说完了** —— 玩家的子弹飞向怪物，怪物的子弹飞向你。重叠与色觉差异在这里退化成可以忽略的代价。炸弹则必须多一个形状，因为它不是「一颗在飞的东西」而是「一个即将落在某处的圈」：

| 弹体 | 剪影 |
|---|---|
| 玩家的子弹 | 绿色的弹头 + 拖尾（`--accent`） |
| 怪物的子弹 | 红色的弹头 + 拖尾 |
| 炸弹 | 圆体 + 地面上**画在 `blast` 半径上的预警圈** |

预警圈是炸弹可躲的前提，而不是装饰（§15.3）：没有它，0.4 秒后凭空炸开的伤害会被读成渲染 bug。它同时也是「画出来的就是判定的」的一次兑现 —— 屏幕上那个圈就是判定用的那个圈，两者读同一个常量（§15.2）。

另外两条：

- **画出来的半径就是判定半径**（`pickupRadius` = 5 px，`playerRadius` = 9 px）。让「看起来踩上去了」和「真的捡到了」是同一条线，而不是靠玩家去猜一个隐藏判定区。注意判定涉及**两个**圆，所以门槛是两者之和（14 px）而不是药剂自己的半径 —— 只取后者会在两个半径之间留出一条视觉上已经踩上去、判定却不认的死区（§8.4 记了这次踩坑）。两个半径都由 `sim.ts` 拥有，`GameScene` 引用同一组常量去画，画面与判定因此不可能分家。
- **寿命最后 10 秒开始闪烁**（`itemFlicker`）。闪烁是「它快没了」的唯一提示 —— 没有它，药剂凭空消失会被读成渲染 bug。

- **攻击**：自动（见 §5.1）
- **拾取**：自动（见 §8.4）—— 同样是因为需求第 1 条只给了 2 个控件

以下**不在**本次范围内，列出以备后续讨论：

- **难度基调：站桩存活从 92 s 塌到约 3.2 s（待用户拍板）。** 这是解除怪物拴区（§6.2）的直接后果 —— t=0 就有约 5 只怪罩住玩家，其中 3 只在邻区，因为感知范围是唯一的追猎边界（§4.1 记了这个代价）。**本轮刻意不动它**：机器人策略的所有数字都是在这个世界里量出来的（§14.5 / §14.6），如果同时改难度，两边就无法归因。等策略定稿后单独提。可用的旋钮至少有：初始怪数、`senseRange`、§4.3 的密度升级曲线、以及「出生点是否给一小段无敌」。
- **最佳存活时间的持久化**：目前只在会话内保留。若要跨会话，需要引入 `localStorage` 或一个 Tauri 存储命令。
- **命中历史**：目前一次命中即锁定本局（与 Hex tab 一致）。
- **音效**：`src/game/config.ts` 已配置 `noAudio: true`（BTC 扫描器不需要 AudioContext），若加入音效需一并调整。
- **手柄 / 触屏**：目前仅键盘。
- **数值平衡**：§11 全部为拍脑袋的初值，需要实际手玩后再调。本次新增的曲线里有三处已知的、**刻意没有先加护栏**的地方，留给手玩决定：
  - **强化药剂的复利是双份。** `attackPower ×1.05` 与 `attackSpeed ×1.05` 同时生效，等于 DPS `×1.1025` —— 高于怪物血量的 `×1.05/min`。玩家长线会跑赢怪物，除非掉落速率或怪物密度同步上调。这是需求原文（「攻击力 ×1.05，攻击速度 ×1.05」）的直接实现，未擅自加封顶。
  - **怪物的 `moveSpeed` 从不增长。** 越到后期，玩家越容易靠走位脱离接触 —— 难度全部由血量与密度承担。
  - **属性乘数无上限。** `keymap.ts` 的 `SCALE` 分母（`moveSpeed` 320 / `attackSpeed` 4 / `attackPower` 64）是定值，堆到一定程度后属性会**饱和**该分母，字节归属的可读性下降（数值不再有区分度）。需要时在这里加一个软上限。
- **密钥推进速率与 IPC 负担。** 现在每个变化的仿真步都提交一次，上限是帧率（§9.4）。`derive_group` 是**同步**命令，跑在主线程上，所以这条路径的代价会直接表现为掉帧。目前已经有在途合并（同一时刻至多一个在途），**如果实测发现负担过重**，下一步是把触发点挪到场景已有的 4 Hz 统计回调上 —— 那只是换一个观测节奏，仍然没有速率常数，设计主张（密钥 = 世界状态的函数）不变。

## 14. 机器人模式

一个自动玩的玩家。它跟人类看同一块屏幕、拿同一份信息，**不多也不少** —— 多出来的那一份必须靠走近去换（需求第 5 条）。

它存在的理由不止是「好玩」：§3.4 之后密钥是**世界状态的纯函数**，没有时钟、没有 tick 计数。所以一个停摆的机器人会产出停滞的世界，也就产出极少的密钥 —— 「它在动」这件事是功能性的，不是装饰。反过来，一个能自己活下去的机器人让这个 tab 可以无人值守地一直产密钥，而它活下去的每一秒都是真实推进的字节。

### 14.1 感知：需求第 4、5 条的分界线

| 信息 | 来源 | 是否公开 |
|---|---|---|
| 怪物位置 `posX` / `posY` / `dir` | 画在场上 | **公开**（需求 4） |
| 怪物感知半径 `senseRange`（`m_range`） | 那个虚线圈 | **公开**（需求 4） |
| 怪物种类 `kind` | 剪影 + 颜色（§10.3） | **公开** |
| 怪物血量条 `hpFrac` | 伤害条 | **公开** |
| 怪物所在区域 | 地板上的区域边界 | **公开**（可推导） |
| 药剂位置 / 种类 / 剩余寿命 | 地上的剪影 + 闪烁（§10.3） | **公开**（需求 4） |
| 飞行中的炸弹：落点 + `blast` | 画在落点上的预警圈（§10.3） | **公开** —— 圈画多久，机器人就看见多久（§15.6） |
| 飞行中的子弹 | 画在场上（§10.3） | **公开，但策略刻意不用**（§15.6：人类也躲不掉，用它就是偷偷放宽这条边界） |
| 玩家自己的属性 | 就是自己 | **公开** |
| 怪物 `attackPower` | —— | **只在圈内**（需求 5） |
| 怪物 `attackSpeed` | —— | **只在圈内** |
| 怪物 `attackRange` | —— | **只在圈内** |
| 怪物 `moveSpeed` | —— | **只在圈内** |

「只在圈内」是**逐帧重算**的，不是记住的：`perceive()` 每帧从 sim 重新投影，`stats` 非空**当且仅当**此刻 `hypot(dx, dy) ≤ senseRange`。走进圈就公开，走出圈就收回，不需要一张记忆表、不需要一个类。这也是 `decide()` 能是纯函数的原因 —— 视图是机器人关于世界的全部知识，而视图里没有上一帧。

**雾是模块边界，不是约定。** `robot.ts` 从不 import `MONSTER_ARCHETYPES`，`PerceivedMonster` 里也**没有**任何可以装隐藏属性的字段，所以这个作弊在类型层面就写不出来。注意 `MONSTER_ARCHETYPES` 在 `sim.ts` 里是公开的 —— 强制不在那边，在这里：在这个模块愿意看什么。

**为什么 `kind` 公开却不查表。** 种类确实画在屏幕上，人类看得见；但策略**刻意不**由它去查每种原型的数值。陌生怪物一律按同一个保守假设处理（见下），靠走近去修正 —— 那正是需求第 5 条要买到的东西。如果 `kind` 能直接推出属性，需求第 5 条就作废了。

### 14.2 策略

```
1. threats   : dps = attackPower × attackSpeed, reach = attackRange
               （没公开就用先验：hunter —— 9.6 dps / 26 px / 120 px·s⁻¹）
2. riskAt(x,y): 对每只怪物，按以下两条规则求和
3. 选目标     : 全场取 argmax(群大小 × CLUSTER_WEIGHT − 距离 / CLUSTER_DIST)，
               记下胜者所在那一群的**质心**作为一个点。
               这个点要**锁住**（见下），不每帧重选。
4. 意图 + 目标方向（首个命中者胜）
     heal  血 < 0.62 且 药比威胁更近            → 朝那瓶药
     flee  脱离闩锁已置位（见下）                → 纯粹背离「附近威胁的质心」
     loot  最好的药得分 ≥ 0.35                  → 朝那瓶药
     kite  有威胁在 FARM_RADIUS 内              → 站到「不在它 reach 内、但在自己射程内」的环上，带切向环绕
     roam  以上都不成立                          → 朝选中的目标
5. 在 9 个输入上取 argmax：
     W · dot(位移方向, 目标方向) − clamp(风险增量) − 墙体惩罚 + 粘滞
     W = GOAL[intent]
     风险增量的被减数是「所在世界与所去世界里更危险的那个」（见下）
     粘滞只奖励重复上一帧的**非静止**输入（见下）
```

**目标锁定（本轮新增）。** `pickTarget` 选出的那只怪只是一个**指针**，真正被记住的是它**所在那一群的质心**——一个世界坐标点，连同上一次锁定时机器的位置（路线的起点）。锁定一直保持，直到满足两者之一：

- **已清空**：锁定点 `CLUSTER_RADIUS` 内没有任何怪物。这就是用户说的「直到把目标区域的怪物们击杀」。
  > **但这一条在机制上几乎不可能单独成立。** 怪死在**自己的 home 区**按 2.5–6 s 的时钟重生（§4.2），所以一片被打空的区域几秒内就会回填，而锁定点又恰好是全场最密的地方。实测下来锁定**总是**被下面那条偏离判据解除的。
- **已偏离**（用户给的规则）：以**建锁时机器人所在位置**到锁定点连一条线段，长度记为 `d`；机器人当前位置到这条线段的垂距超过 **`d / 3`** 即视为偏离。阈值是**相对的**，随路线长度缩放 —— 目标远时容得下更大的横向绕行，贴近时收紧。**必须配一个下限**：`d` 很小时（锁就在脚下）`d/3` 会小于机器人自己绕圈的半径，正常风筝每帧都破锁、等于没有锁，所以下限取站位环 `desired` 本身。

锁的作用是让 `kite` 的站位环、`ignoring`、`roam` 的方向指向**一个固定的点**，而不是每帧在分数接近的候选之间翻。

**但要如实说清它的量级：这一节修的是「去哪」，不是「稳不稳」。** 机器人 72% 的帧在 `flee` 里，而 `flee` **不读** `target`（它读 `dangerCentre`），所以锁定对抖动几乎没有作用。实测印证了这一点：把 `OBJECTIVE_DEVIATION_FRAC` 在 1/4 · 1/3 · 1/2 上扫 96 颗种子，最差种子 1.25× / 1.25× / 1.26×、逃离率 45.8% / 46.0% / 45.8%、反向 21 / 20 / 26 次 —— **全在噪声内**。用户给的 1/3 因此原样保留，不是因为它被实测选出来，而是因为没有证据反对它。抖动的主修是下面的 `HYST`。

**风险场。** 两条规则承载了整个策略：

- **没有拴区项了。** 这一条曾经是「一只怪物对它自己辖区之外的位置贡献为零」。拴区解除之后（§6.2）**每一只感知到的怪物、在每一个候选位置上，都全额计价**，风险场因此处处抬高。这是本轮最重要的一处世界变化，也是抖动之所以致命的原因：风险项的摆幅到处都是满的。边界不再是机器人手里的一步棋，**脱战只剩下拉开距离一条路**（§6.2 那 3.9 秒）。
- **接近度曲线。** `dps × CHASE × proximity`。`proximity` 在 `reach` 处为 1、在 `senseRange` 处为 0，进到 `reach` 以内则随距离缩小继续爬升（`1 + PROX × …`）。**必须是连续的、且对 `d` 单调的**：早期版本在 `reach` 以内给 `dps`、以外给 `dps × CHASE`，于是向内越过 `reach` 反而让风险**下降** `2.4 × dps` —— 风险场悄悄付钱让机器人踏进蛮牛的攻击范围。`kite` 的站位环把它盖住了，这正是它值得被删掉而不是被调参的原因。`FALLOFF` 取 0.4（小于 1，凸曲线）：线性斜坡会让「离蛮牛 50 px」看起来几乎免费，而它离挨打只有一步。
- **炸弹项**（§15.6）。飞行中的炸弹按 `damage × BOMB_WEIGHT × CHASE × proximity` 计价，位置取**落点**而不是弹体现在在哪，半径取 `blast + playerRadius`。它与怪物项有两处刻意的不同：**半径处硬截断**（圈外确实是零），**不看引信**（危险的是那个圈，不是还有多久落地 —— 那正好也是画面能读到的全部信息）。这一项只活在候选打分里，见下面两条「基准分」。

**风筝的站位环。** `desired = clamp(ourRange − STANDOFF_MARGIN, target.reach + BAND, ourRange − 2)` —— 既在目标 `reach` 之外、又在自己射程之内，因为只有玩家的攻击是自动的、怪物得走过来（§5.1），这个环就是全部战术。按当前数值 `ourRange − 4 = 51` 总是压过 `reach + 8`（最远的蛮牛 reach 才 34），所以下界是留给「怪物 reach 涨到接近玩家射程」那一天的兜底，不是现在生效的项 —— 而且它是把环推向**外侧**，也就是失败时安全的那一侧。修正量是**比例的**而不是一个符号：在环上径向项归零，于是机器人环绕而不是在「进」和「出」之间打摆子。

误差的归一化是**不对称的**，这一条承重，而且两侧的带宽各有各的道理：环外按「我们离**自己射程**还有多远」饱和，环内按目标自己的 `reach` 饱和。用单一半宽 30 时，径向项在蛮牛的 `reach` 处只有 0.567 —— 比 0.6 的切向项还弱，于是机器人一边挨打一边绕着怪物转圈，实测接触帧里只有约 27% 能把距离拉开。按 `reach` 饱和意味着「目标开始真正打到你」的那一刻退避正好满格，径向项（1.0）于是压过切向项（0.6），而它必须压过。切向偏置的方向由「哪边同时更靠近场地中心」定 —— 这是阻止一场风筝把自己螺旋进角落里死掉的东西。

**环外的带宽原本是 `KITE_BAND` 30，那是同一个错误的另一面 —— 只是没人往那个方向量过。** 误差 30 意味着径向项要到环外 18 px（也就是离目标 69 px）才追平切向项 0.6。而玩家射程只有 55 px —— 于是**机器人会永远停在自己的射程之外绕圈，一次都不出手**：实测在一个不动的怪物身上，它稳在 58 px 处环绕，射程 55。改成按 `ourRange − desired`（即「我们还在自己射程之外」这一段的宽度，当前取值 4 px）饱和之后，整个接近过程中径向项都是满格，什么时候停由环决定、而不是由切向项决定。实测：接触帧 51369 → 40939（少了两成），拉开距离的比例 65% → 66%，而生存分布一格没动。`KITE_BAND` 因此成了一个死常数，已删除。

**风险是增量（`riskAt(next) − riskAt(here)`），不是绝对值。** 这条是承重的：机器人躲不掉的环境风险不应该让它瘫痪，所以只有**变化**可以操舵。改成给绝对风险打分，机器人一进密集场地就会原地冻死。

**而炸弹要活在增量里，就必须出现在「脚下」那一项 —— 于是这里有两个基准分，它们对炸弹的态度刻意不同。** `hereRisk` 服务于两个承诺门（撤退闩锁的进入与 `DISENGAGE`），它**排除**炸弹：一发落在脚下的炸弹在圆心能读出 `18 × 3 × 2` = 108，远在任何门槛之上，而它值得的反应是「挪两步」而不是「放弃整个区域」。`hereForScore` 服务于候选打分，它**包含**炸弹：基准分里没有那发炸弹的话，「从炸弹下面走开」会和「一动不动」打平，而平局按规则判给静止 —— 机器人会站在炸弹里等它落地。

**增量的第一个代价还在：参照点就是脚下，所以「不动」的增量恒为 0 —— 它是一个有特权的零**，每一次平局都判给它。

**第二个代价换了内容，而换成的这一条是本轮的关键发现。** 曾经的代价是拴区项造成的**空间阶跃**（跨过边界一次点亮 55 的风险，被 `RISK_CAP` 削平）。拴区没了，阶跃也没了 —— 但取而代之的是一个**处处都在**的问题：风险项的摆幅与目标项的摆幅不成比例。

**这个比例关系值得单独记下来，因为它是抖动这一整类缺陷的通用判据，比任何一次调参都重要：**

| 项 | 摆幅 |
|---|---|
| 目标项 `W · dot(…)` | `GOAL[intent]` 6 × \|goal\| ≈ 1.166 → **约 7.0** |
| 风险项 `clamp(Δ)` | ± `RISK_CAP` → **±12** |
| 抗抖动（总承诺） | 当时是 `HYST` **1.5** + `MOVE_MARGIN` **2** → **3.5**（= 风险摆幅的 29%） |

风险项的摆幅是目标项的 **1.7 倍**，而唯一的抗抖动项只有风险摆幅的 **29%**。40 px 的探针落在一个 5–7 只怪常驻（峰值 18）的风险场上时，相邻两个候选方向的分差经常接近整个 ±12；两只怪从相反方向拉扯时场上存在一个**鞍点**，而鞍点随怪移动，候选便在半数帧里从一侧翻到另一侧。测出来的结果就是：**每局 90 次方向反向、最长不间断直线跑只有 1.37 s**。而脱战需要 3.9 s（§6.2）—— 所以那不是「撤退得不好」，是**根本没有撤退，只在原地振动**。

**修法是抬高承诺，而不是压低风险项。** 这一条反直觉，值得记下为什么：压低风险项（`RISK_CAP` 12 → 8 → 6）在 96 颗种子上反而**更差**（中位 2.46× / 1.84×，都是负收益），因为风险项是机器人活下来的唯一原因。抬高承诺则直接对症：总承诺 3.5 → **8** 把反向从 90 次压到 **20 次**、最长直线跑从 1.37 s 抬到 **2.95 s**。代价是逃离率从 66.1% 掉到 46.0% —— 一个「认准方向」的机器人对贴到身上的怪反应得更少。生存中位和最差种子**都没有变差**（见 §14.6 的两个数字），所以这个交换是划算的，但它是一个交换，不是纯赚。

**「总承诺」这个词是这一轮量出来的，不是修辞。** 它当时由两个常数相加：`HYST`（奖励重复上一帧方向）与 `MOVE_MARGIN`（上一帧方向在打平时多得的余量）。两者都是**同一个分数单位下、给同一个候选的同一笔奖励**，所以机器人只感受到它们的和。实测把这一点钉死了：`HYST` 6 + `MOVE_MARGIN` 2 与 `HYST` 8 + 无 `MOVE_MARGIN`，在 96 颗种子上、八项统计上输出**逐字节相同**。于是 `MOVE_MARGIN` 被删掉，`HYST` 提到 8 独自承担全部承诺 —— 一个活儿两个旋钮，就是多了一个旋钮。**这类「两个常数其实是同一件事」的重复，本文件里已经出现过两次**（另一次是 §14.2 那条从未运行过的释放，见下），两次都是靠**输出逐字节相同**发现的，而不是靠读代码看出来的。

**「什么都不做」赢下这些竞标，曾经是用户那条报告的真正机制。** 当时的实测：723892 个「自己射程内没有怪物」的帧里 **72.4% 是静止的**，只有 14.6% 真的在靠近最近的怪物，而逐帧拆开那些静止帧的打分，**166863 / 166919 是被风险项挡下的**，其中 96% 的探测跨了区界，把中位数 4 只原本被拴住的怪物一次点亮。那一轮堵了三个出口：

- **被追的目标本身也在风险项里**（现在仍然是）：一个「朝它走过去」的候选要同时为「它在追我」付钱，而它正是唯一想靠近的东西。环已经是这只怪的安全契约，所以**接近期间把目标自己**从风险项剔除，其余每一只照常计价 —— 目标站在怪堆里时，仍然是怪堆把它拦下。
- **换辖区被当成了「走向危险」**（**已随拴区一起消失**）：`hereRisk` 在 A 区求和、`riskAt(next)` 在 B 区求和，跨一步等于把两个不同集合相减。修法是被减数取「所在世界」与「所去世界」中更危险的那个。拴区没了之后两个集合**恒等**，这整套被减数逻辑已删除。
- **选错了目标**（**已随拴区一起消失**）：`pickTarget` 曾先只在自己辖区内选，自己辖区空了才放眼全场。`pickTarget` 现在**不过滤辖区**。

那一轮的结果是静止帧 71.2% → 54.9%、击杀 7169 → 22504（3.1×）。**但拴区一解除，静止就换成了振动**：空闲帧低到 4.3%，可是反向 90 次/局、最长直线跑 1.37 s —— 机器人不站着了，改成在原地抖。修法是本节的 `HYST` 与 §6.2 的脱战机制凑到一起才成立的。

**`CHASE` 是唯一真正要紧的常数。** 它是「站在有东西追我的地方」和「走向我想要的东西」之间的汇率。太高 → 拒绝交战、饿死；太低 → 走进怪堆。48 颗种子上的实测：生存率随它单调上升到 3 左右后走平，此时中位数达到「原地不动」的约 7 倍，而且 —— 因为更大的风险场意味着**更多风筝而不是更少** —— 击杀数**上升**。这里其它每个常数在它旁边都是装饰。

**陌生怪物用 hunter 做先验，而且只有一个先验。** 这是整个雾设计里最承重的一个选择。需求第 5 条存在的意义是让「接触」**买到**东西，而只有当无知**真的变贵**时才会如此 —— 所以先验不能是平均值，更不能是最弱的那个。假设都是软柿子 → 它会一头撞进蛮牛；假设都是最坏的 → 它永远不交战、饿死。hunter 是中间那档，也最可能是正在朝你逼近的那只。

**脱离是一个闩锁，不是一条阈值。** 一只 hunter 在 `reach` 内把风险抬到 9.6，往外 30 px 就掉到 2.9。一个「在这个数开始逃、在那个数停止逃」的 bang-bang 控制器会每半秒掉一次头，永远走不到两百多像素外的任何安全地方 —— 实测就是这样死的，死在半路，一边抖一边死。所以 `RobotState` 里有一个 `retreating` 布尔：进入容易，退出要求风险**真的**消失。

**本轮把闩锁的两端都改成了局部的**，因为旧的两端都是「对**全场**怪物的**和**」取的阈值，而那些阈值随怪数一起漂：

- **进入**：`nearest.dist <= nearest.reach`（**接触** —— 怪真正打得到你的那一刻）**或** `hpFrac < FLEE_HP && nearest.dist <= DISENGAGE_RADIUS`。
- **退出**：`nearest.dist > FLEE_RELEASE_DIST`（60 px）**或** `hereRisk < KITE_SAFE_RISK`。

进 ≤26、出 >60，方向正确、在人群里可达，周期健康：在 51 px 的站位环上打 → 挨打就退到 60 → 回到环上。实测的形态正落在这个区间里：96 颗种子产生 294 次闩锁进入（约每局 3 次），中位时长 2.15 s，**98.7% 的 `flee` 帧落在 ≥0.5 s 的片段里** —— 上面警告的那种「每半秒掉一次头」的 chatter 没有回来。

第二条进入条件（残血 + `DISENGAGE_RADIUS`）守的是另一个真实陷阱：只看血量就逃的话，血在回满前一直低，于是一个残血、最近的怪却在 240 px 外**且没注意到它**的机器人会永远逃一个不存在的东西，而不是去捡药或回血。`KITE_MAX_RISK`（9）留在 `loot` 档守门 —— 「风险高过这个数就不绕路去捡强化药」—— 而且刻意**管不到 `heal`**：一瓶回复药对残血机器人不是可选项。**早退、常退**才是既活得久**又**拿分多的做法。

**改动前的闩锁是「一进不出」，而那是 bug 不是调参。** 旧的进入条件是 `hereRisk > PANIC`，而 `hereRisk` 是对**每一只**感知怪物的**求和**，所以它描述的等高线半径随在场怪数增长（2 只猎手 141 px、3 只 217 px、5 只 248 px）；退出的 `hereRisk < KITE_SAFE_RISK` 落在同一个随人数漂的半径上。场上常驻 5–7 只怪，于是机器人几乎每一帧都在等高线内，**没有任何固定距离能落在它外面** —— `FLEE_RELEASE_DIST` 调多大都没用。实测：96 颗种子一共只有 **102 次**闩锁进入，`flee` 占全部帧的 **96.1%**。那不是一段一段的撤退，是一整局不间断的撤退。

**另有一处真 bug，值得记下来因为它差点没被发现**：释放条件曾经写成 `if (threatened) … else if (…)`，所以它**只在没有受威胁的帧上才会执行** —— 而在真正需要释放的人群里，每一帧都受威胁。这条释放从未运行过。发现它靠的是一个异常：修完之后 sweep 的输出与修之前**逐字节相同**。改成一对方真正的迟滞之后就正常了。`PANIC` 这个常数随之删除。

**`heal` 排在 `flee` 上面，而且它差点是死代码。** 顺序的理由是：一个残血、脱战、又什么都不捡的机器人没有回头的路 —— 回血只有 1 hp/s，血量会一直低于脱离阈值，于是它逃到死，死在药旁边。但「去拿药」只在药比威胁**更近**时才对，所以那一档额外用距离守了一道。

而它一开始**根本没触发过**：拾取评分只跟踪了一个「场上最值钱的东西」，于是一瓶强化药剂可以轻松压过一瓶回复药，**悄悄否决**了残血机器人的取药行程。实测在 24 局种子里 `heal` 档命中 **0.0%** 的帧 —— 一条穿着规则外衣的死代码。修法是分开跟踪两个赢家：`best` 回答「场上最值钱的是什么」（`loot` 档的问题），`bestHeal` 回答「最近的药在哪」（`heal` 档的问题）。修完之后它**仍然**是 0.0%，但这次理由正当：血量分布显示机器人 74.1% 的帧在 90% 血以上，只有 3.1% 的帧低于 0.62 —— 而那几个帧里地上恰有回复药的概率是 0.01%。也就是说这一档不是接错了线，只是这个策略很少受伤。修法保留了，因为它移除的是一个真实存在的否决。

**`flee` 本轮被收窄成纯局部脱离，避难区整个删掉了。** 用户对这一档的要求是明确的：「flee 只做局部脱离」。曾经的目标是「径向分量 `FLEE_RADIAL = 1` ＋ 切向分量 `FLEE_ORBIT = 0.6`，切向负责把路线弯向**最安全的区域**」—— 现在两半都没了：

- **切向那半** 走的原因就是用户那句话：它一路把撤退导向**跨场地**的避难区，而那不是「局部脱离」。拴区解除之后「哪个区域最安全」也不再是任何东西的避难所 —— 它只是一个**此刻人少一点的地方**（§6.2）。
- **径向那半的参照点**换了。它原本是 `nearest`（逐帧 argmin），而 `nearest` 在人群里每秒换身份约十次，每次换名次都把逃离方向翻转最多 180° —— **那正是振动**。换成**附近威胁的加权质心**（`dangerCentre`，权重取 dps，半径复用 `DISENGAGE_RADIUS` 220）之后，两只怪交换名次时质心几乎不动，而 argmin 会瞬间翻向。

所以现在剩下的**只有一个背离连续点的单位向量**，是本策略能产生的最稳的方向，也是唯一能撑够 3.9 秒去断掉一次仇恨的方向。

**墙。** 贴墙本身就该罚：它拿掉了风筝需要的退路，而角落是跑局结束的地方。惩罚按每轴平方，所以开阔地几乎免费、角落里压过一切 —— 它换掉的那个线性版本太弱，压不住一个朝外的目标方向。还有一个配套的「目标滑墙」：目标指向机器人**已经贴着**的那面墙时，把那个分量归零，否则每个服务它的候选都退化成原地不动，而原地不动风险增量为 0，于是稳赢所有要付代价的真动作。

**对角线不再更快，归一化本身就是一处修复。** `stepSim` 曾经用 `(dx, dy) × moveSpeed × dt` 移动玩家、**不做归一化**，而怪物沿单位向量走 —— 于是斜向实测 226.3 px/s 对正交 160.0 px/s，人类按住两个键就白拿 41%。那不是「手感」，是 `moveSpeed` 这个数在斜向上根本不成立；用户报的「移动跟瞬移一样，明显不符合它的 moveSpeed」就是它。现在按 `Math.hypot` 归一化，八个方向实测都是 160.0 px/s。机器人这边配着一处旧缺陷：候选的探测步长曾经直接取 `(c.dx, c.dy) × step`，于是斜向探 56 px 而正交只探 40 px，跨边界的概率高得多 —— 而跨边界会让风险项饱和，于是**每一个斜向候选都被否决**，实测 172991 个移动帧里斜向被选中 **0.0%**。现在探测步长同样归一化。

**粘滞只奖励「重复上一帧的移动」，静止被排除在外。** 那个奖励的存在意义是压住两个**相反方向**之间的反复横跳，而那是只有移动中的机器人才有的问题；静止不是那两个方向之一，也不缺这份帮助 —— 严格 `>` 的平局规则本来就把所有真正无差别的帧判给它。如果它把静止也算进去，就会赢下它本不该参与的竞标：`lastDx` / `lastDy` 的初值 `(0, 0)` **恰好就是静止那个候选**，于是从每一局的第 0 帧起静止白拿这一整份承诺分，每次停顿又把它赚回来一次。

**而这个奖励的大小是承重的，本轮把总承诺从 3.5 抬到 8 —— 这是抖动的主修**（理由与实测见上表那一段）。抬高它的代价是逃离率（66.1% → 46.0%），而它换来的是反向从 90 次降到 20 次、最长直线跑从 1.37 s 抬到 2.95 s。往上还会继续改善稳定性（总承诺 10 → 反向 11 次），但 **10 就开始破最差种子**（0.92×，比原地不动死得更快），所以 8 是拐点，是按**最差种子**选的、不是按均值选的。

**曾经还有一个同类的承诺项 `MOVE_MARGIN`，现在删了 —— 因为它和 `HYST` 是同一件事。** 它的定义是「保住上一帧方向所需的分差」，听起来是个独立的旋钮（一个奖励**重复**，一个惩罚**改变**），但在这一份打分里两者是同一个算术：给上一帧方向多加 2 分，与要求新方向多赢 2 分，落在同一个比较上。实测证实：`HYST` 6 + `MOVE_MARGIN` 2 与 `HYST` 8 + 无 `MOVE_MARGIN`，96 颗种子、八项统计**逐字节相同**。所以承诺量只有**一个**数，8；`MOVE_MARGIN` 的存在只会让「调 `HYST`」这个动作的效果被另一个常数分摊掉，读代码的人算不出机器人的真实承诺是多少。

**`RobotState` 里没有记忆，只有决心。** 需求第 5 条的公开机制仍然逐帧重算、从不记住 —— `perceive()` 是纯的，视图就是机器人关于世界的全部知识，视图里**没有上一帧**。这里存的全是策略**对自己决定的记忆**，是另一回事：

| 字段 | 是什么 |
|---|---|
| `retreating` | 撤退闩锁（上面那个布尔） |
| `lastDx` / `lastDy` | 粘滞要奖励的那个方向 |
| `objectiveX` / `objectiveY` | 目标锁的点（**世界坐标**，不是「某只怪」的引用 —— 怪是会死的，点是稳的） |
| `originX` / `originY` | 建锁时机器人所在位置，偏离判据那条线段的起点 |
| `locked` | 有没有锁 |

**从「一个布尔加一对方向」长到了这些，而每一格都对应一次被实测逼出来的承诺。** 三条都是同一个道理：策略需要一个比「这一帧的分数」更长的视野，因为**这一帧的分数在这张风险场上是抖的** —— 风险项的摆幅是目标项的 1.7 倍。锁是「去哪」的承诺，闩锁是「撤还是打」的承诺，粘滞是「朝哪走」的承诺。代价是 `decide` 不再是无状态的，所以「同视图 + 全新 state 给出同一走法」这条契约仍然成立（§14.5 测它），但「同一局逐帧重放」现在**依赖 state 被正确地带着走**，测试里也钉住了这一点。

> 计划里写的签名是 `decide(view)`，实现是 `decide(view, state)` —— 那个闩锁需要一个落脚处。`perceive()` 仍然是纯的、无状态的。

### 14.3 模式与重置语义

```
[ 👤 manual │ 🤖 robot ]        ← §10.1 的三号控件，命中后禁用
```

- **切换即重开。** `setMode()` 先把模式推给场景（这样重建出来的场地就是新模式下的场地），再走**既有的** `restart()` 重置路径：新的 sim、`generation++`、全部本局计数器归零（存活 / 等级 / 经验 / 击杀 / 掉落 / 密钥数），然后 `running = false` —— **总是停在 READY**，`▶` 是一个必须被做出的动作。
- 复用 `restart()` 而不是重抄一遍重置，是为了让「切模式」和「死后重开」这两条路不可能走岔。
- `bestSurvival` **不**清零 —— 和死后重开一样，最好成绩是跨局的。
- 命中后开关一并锁定（与下拉框、`▶` 同一套规则）。
- 场景未就绪时选的模式不会丢：`onReady` 会把当前模式重新推一次。
- **`manual` 下与旧版逐帧等价。** 机器人只占输入源那一个插槽：`readInput()` 在 `robotMode` 时走上 `decide()`，否则一个字符都不变。

### 14.4 HUD 读数

```
auto kite · known 2/5
```

意图 + 「已经拿到几只怪物的数值」。渲染**只在机器人模式下**，因为手动模式下它恒为空。

**画布上没有雾。** 用户明确要求机器人的知识不要画到场上，所以 `GameScene.drawFrame()` 除了一句 READY 提示文案之外没有改动。代价是 `known n/m` 成了观察「看到」与「知道」之差的唯一窗口 —— 这也是它值得占一格 HUD 的原因。

### 14.5 模块与测试

见 §11 的数值表和 §12 的模块 / 测试表。要单独点出的是 `robot.ts` 的形状：两个纯函数加一张调参表，与 `sim.ts` / `keymap.ts` 同构 —— 无 Phaser、无 DOM、无时钟、无随机。所以一颗种子能钉住整条轨迹，一个测试不需要浏览器就能复现一局，而雾是可审计的（它的边界就是类型边界）。

**实测（96 颗种子，`i × 1013 + 7`，`dt` = 1/60，上限 10 分钟）：** 中位 **2.48×**，平均 2.94×，P10 1.56×，最差 1.25×，最好 7.81× —— **0/96 颗种子跑满 10 分钟上限**。总计 175 次击杀（每局 1.8）、53 次拾取。空闲帧占 **4.3%**；接触帧 24542 帧（占 31.5%），其中 **46.0% 把距离拉开了**。

**这三个世界必须放在一起看，因为它们量的是三个不同的东西，而比值在它们之间不可比。**

| | 拴区在（更早的 HEAD） | 拴区解除、策略未改 | 本轮：策略改完 |
|---|---|---|---|
| 存活中位 | 6.49× | 3.48× | **2.48×** |
| 跑满 10 分钟 | 96/96 | 0/96 | **0/96** |
| 最差种子 | 3.56× | 0.95× | **1.25×** |
| 击杀（总计） | 23002 | 143 | **175** |
| 空闲帧 | 55.9% | 5.2% | **4.3%** |
| 反向 / 局 | — | 90 | **20** |
| 最长直线跑 | — | 1.37 s | **2.95 s** |
| 接触中拉开距离 | 66% | 66.1% | **46.0%** |

**要如实说清这里有两个方向相反的变化，而不是一个「变好了」。** 从中间那列到最后一列，机器人**最差种子从 0.95× 抬到 1.25×、击杀从 143 抬到 175、反向从 90 次降到 20 次** —— 它不再原地抖，也不再早早死掉。但**中位存活从 3.48× 掉到 2.48×**，掉的原因也清楚：承诺就是「不理会每一次触碰」，所以接触中拉开距离的比例从 66.1% 掉到 46.0%。**中间那 29% 的存活是用稳定性换来的，这是交换不是纯赚。** 唯一称得上「纯赚」的是最差种子：抖动修好之后没有哪一局比站桩死得更快（拴区解除后是 0.95×，也就是有一局还不如站着不动）。

> 「跑满上限」这一列从此不再是一个有意义的指标。它在拴区世界是 96/96，因为拴区让机器人可以把怪停在一个跟不进的地方（那也是用户报「机器人始终在一个区域转悠」的来源）；解除之后它恒为 0/96，与策略好坏无关。任何以「跑满上限」为目标的调参在这个世界里都是在拟合一个已经不存在的地形。

> 拴区那一列的 6.49× 记录于此仅供对照，**它不是本世界的目标**。代价的另一半是站桩存活已从 92 秒塌到约 3.2 秒 —— 那是难度基调问题，与本节策略无关，已单独记在 §13，**不要把两件事并进同一个结论**。
>
> 另记一条这个对比本身的局限：idle 对照的存活**依赖步长**（1/60 → 93.2 秒，`maxDt` → 128.0 秒，隐含比值 6.44× → 4.69×），所以「机器人比站桩强几倍」只在注明 `dt` 之后才有意义。上面这组以及 `tests/game-sim.mjs` 里的那一组都取 1/60，与场景的常规帧率一致。

### 14.6 两条曾记录的缺陷：一条已修，一条残留

这两条曾被认为来自同一个根因 —— **探测视界与实际步长的比例**（`PROBE_S = 0.25` 让每个候选都在约 40 px 之外被评判，而机器人一帧实际只走约 2.8 px）。**这个归因对第一条是错的，而错了整整一轮。** 第二条才是它的真实作用域。

**（一）静止（原「边界僵持」）：已修。根因不是探测视界，是拴区。** 机器人会在满血、离任何墙都有 140 px 的地方**站着不动**，一分不得。上一轮把根因定位到了正确的地方 —— 拴区项在空间上是一个**阶跃**：跨过边界会一次点亮好几只怪物，实测阶跃约 55，而没有一个目标权重能到那个量级；在 `RISK_CAP = 12` 之上风险项从「操舵」变成「否决」，而原地不动的增量恰好是 0，于是它永远赢 —— **但结论写成了「要真正治好它就得改探测视界」，而那是另一个东西。** 实测反驳了它：拴区一解除（§6.2），在**没有任何策略改动**的情况下空闲帧从 55.9% 掉到 5.2%；本轮策略改完是 **4.3%**。探测视界从头到尾没动过。

**这一轮之前堵的三轮口，堵的全是症状，值得作为一条教训留下来。** `KITE_CONTACT_WEIGHT`、粘滞排除静止、以及 §14.2 记的那三个出口（目标剔除、跨区被减数、`pickTarget` 只选本区），每一个都让数字好看了一点（空闲帧 77% → 71% → 54.9%），但没有一个碰到阶跃本身。**而其中 `KITE_CONTACT_WEIGHT` 在拴区解除后变成了一段永不执行的死代码** —— 它守的判据（目标已在 `reach` 内）恰好也是撤退闩锁的进入判据，闩锁先一步把那些帧全部接走了。它和本节下面那条一起，构成了同一种失败模式：**一个常数或分支的职责已经被别的东西接管，而它还在原地以旧的理由被记录着。**

**（二）探测 / 步长震荡：大幅减轻，残留仍在，但残留的性质变了。** 机器人会在相隔约 6 px 的两个位置之间来回，净位移为零。机制仍然是 40 px 的探测对上 2.8 px 的实际步长：当两个探测端点的风险差得够狠时，反向的收益盖过承诺奖励。**本轮的量级：反向 90 → 20 次/局，最长不间断直线跑 1.37 s → 2.95 s**（中位 2.58 s，最好 7.02 s）。残留是明确的：脱战需要 3.9 s 不中断的直线（§6.2），而**中位局的最长直线跑只有 2.58 s，还差一截** —— 所以「接触中拉开距离」只有 46.0%，它有时能脱战，不是每次都能。

> 上一版记的「`HYST` 调大反而**加长**这些片段（最坏连续帧数 3 → 8 时从 747 涨到 1817）」**在拴区世界里量的，在这里不复现**：最长直线跑在 3.5 → 8 → 10 上单调上升。那时的「最坏片段」是拴区阶跃造成的另一种现象，被错误地归到了本缺陷名下 —— 与上面那条错误归因是同一件事的两面。

**炸弹没有治好它，这是一次落空的期望 —— 而它在新世界里比上一版记的更彻底。** §15.4 把重装者的炸弹设计成反站桩工具，理由是「落点画在地上 + 0.4 秒引信」对一个静止的人是确凿的惩罚，而这条缺陷恰好就是静止。拴区世界里实测就已经否掉了它：`BOMB_WEIGHT` 取 **0 / 1 / 20** 三组跑同一套 96 颗种子，中位倍数三组都是 6.49×、都是 96/96 跑满，只有极小的分布差异（空闲帧 55.7% / 55.9% / 56.0%，击杀 23020 / 23002 / 23096）。**本轮重测，连那点差异也没有了：0 与 20 的完整 sweep 输出逐字节相同**，唯一的差别是打印覆盖值的那一行。权重从「完全不躲炸弹」拉到 20 倍，一格都不动。

> **但这一条与上面那两条死代码不是同一回事，分寸要留住。** `KITE_CONTACT_WEIGHT` 与 `MOVE_MARGIN` 能删，是因为有**机制上的证明**：前者守的判据与撤退闩锁的进入条件逐字相同，闩锁先接走了那些帧；后者与 `HYST` 是同一个算术。`BOMB_WEIGHT` 只有**聚合输出相同**这一条证据 —— 那可以说明它在这 96 颗种子上没有改变任何决定，但**不能说明它不可达**：炸弹项可能只是很少成为某一帧的胜负手。所以它**保留**，且以「正确性」而非「修法」的身份保留 —— 人类能读懂预警圈并走开，忽略它的机器人玩的是另一个更瞎的游戏（§14.1）。**删一个常数需要机制，不是需要相关性。**

**结论翻了面。** 上一版写「生存对比是压倒性的，96/96 颗种子都跑满上限」—— 这一条**已不成立**：0/96 跑满上限，而这个指标在无拴区世界里恒为 0，与策略无关（§14.5）。但「机器人大部分时间在玩」这句上一版**部分收回**的话，现在可以**收回那句收回**：空闲帧 4.3%，机器人不再站着不动，击杀 175（拴区解除未改策略时是 143）。**它现在是真的在打，而它付出的代价是活得更短**（§14.5 的表）。

## 15. 弹道与爆炸（bullet / bomb）

> 本轮新增。战斗在此之前是**瞬间命中**（hit-scan）：冷却归零、目标在射程内，就在同一次函数调用里扣血。现在两边都发射**看得见的弹体**，伤害在弹体到达时结算 —— 这不是纯视觉改动，见 15.1。

弹体形状跟着原型走，沿用 §6 已经确立的「一种原型一种剪影」的语言：

| 发射者 | 弹体 | 速度 | 剩余射程 | 备注 |
|---|---|---|---|---|
| 玩家 | 子弹 | 520 px/s | 110 px | 直线、单体 |
| 游荡者 | 子弹 | 280 px/s | 110 px | 同上 |
| 追猎者 | 子弹 | 280 px/s | 110 px | 同上 |
| 重装者 | 炸弹 | `距离 / 引信` | —— | 落到**投掷瞬间**玩家所站的位置，引信 0.4 s 归零即爆 |

子弹与炸弹共用一张 `s.projectiles` 数组和一个 `kind` 判别字段：一个循环、一趟绘制、一次 diff 扫描，而不是两套几乎相同的代码。`kind` 为 `bomb` 时 `blast` 是爆炸半径（32 px）、`fuse` 是剩余引信；为 `bullet` 时两者恒为 0，`range` 是剩余射程。

**为什么玩家和怪物的子弹速度不同（520 / 280）。** 玩家的攻击是自动的（§5.1）：他无法瞄准，也就无法补偿一次打空，而打空是纯损失。怪物打空则相反 —— 那是玩家自己的走位在兑现。所以这个不对称是刻意的，不是疏漏。`bulletRange` 取 110 px（玩家射程的 2 倍）是为了让「朝外逃跑的目标」仍然追得上，同时让流弹死在它自己那个区域里，而不是穿过整个场地打到陌生人。

### 15.1 伤害在命中时结算，于是多了第二个躲避窗口

§7 主张「躲避是空间性的，不是数值赌博」。真实弹道是这条主张的**加强**而不是背离：原本只有一个窗口（在冷却走完之前走出 `m_attackRange`），现在多了一个**飞行途中的窗口** —— 目标在弹体到达之前走开，这一枪就是空的。三个瞄准决定都是这条规则的推论：

- **不做追踪弹。** 追踪会悄悄把 hit-scan 的「必中」还回来，躲避也就没得躲了。
- **不做提前量。** 开火时瞄准的是目标**此刻**的位置，不是预测位置。「目标走开就打空」是这条规则的语义本身；加了提前量，能躲开的动作就只剩下「反向走」。
- **瞄准是连续的。** 速度向量是浮点（`vx` / `vy`）而不是 8 方向 `Dir`：到最近怪物的连线几乎从不是一个罗盘方向，整数化会把 55 px 的一枪变成最多偏 21 px —— 比一只怪物的身体还宽。

### 15.2 画出来的就是判定的

沿用 §10.3 已经为半径立下的规则：

- 子弹的**身体**半径 `bulletRadius = 2.5`，同时也是画出来那条亮线的粗细。命中是「两个圆相触」（§8.4 的同一套写法），所以门槛是 `bulletRadius + 目标半径` —— 对玩家是 11.5 px，对三种怪物分别是 8.5 / 9.5 / 13.5 px。
- 炸弹的**预警圈**画在 `blast = 32` 上，与爆炸判定用的是同一个常量（判定再加 `playerRadius`）。

**判定取的是本步移动前后两点构成的线段，不是终点** —— 和 §8.4 的拾取同一个理由，而且这里更严重：`dt` 被 clamp 到 `maxDt = 0.05`，玩家的子弹一步走 `520 × 0.05` = **26 px**，比任何一种怪物的身体都宽，只判终点会让子弹在两帧之间**穿过**一只怪。反过来，怪物的子弹一步只走 14 px，小于「两圆相触」的 11.5 px 门槛两侧的余量，所以它**不可能**穿透玩家 —— 那一侧的线段判定是形式上的对称，不是修复。

### 15.3 炸弹的躲避规则（这组数值是这么定的）

炸弹落在投掷瞬间玩家所站的位置上，引信固定 `bombFuse = 0.4` 秒，所以它的**速度由距离推导**（`距离 / 引信`）而不是一个固定值。保持恒定的是**预警时间** —— 这也是重装者的弹体被做成最慢的那一个的原因：预警时间恒定，而只有一个慢速攻击者才需要预警。

于是躲避可以写成一个不等式，整组数值都是它的推论：

```
站桩的人需要走出的距离   bombBlast + playerRadius = 32 + 9 = 41 px
扔出后立刻开跑能得到的位移   moveSpeed × bombFuse = 160 × 0.4 = 64 px
```

余量 23 px。而 `dt` 被 clamp 到 `maxDt = 0.05`，20 fps 下一步就是 `160 × 0.05` = **8 px** 的位移 —— 所以**余量必须大于一步**，否则「迟疑一帧就等于没躲」，「躲避窗口」只对已经在跑的人开放，那就不是躲避。

这条不等式是本轮实测**改过一次数值**的原因。原定 `bombFuse = 0.3`：`160 × 0.3` = 48 px 对 41 px，余量 7 px **小于一步** —— 实测确认它确实是假的，在 `maxDt` 下扔出后迟疑一步的玩家最后离落点 40 px，仍然吃到全额伤害。改成 0.4 之后同一组实测：`maxDt` 下迟疑两步仍能走掉、第三步（0.15 s）才吃到伤害；60 fps 下能容忍八步（约 0.13 s）。也就是说炸弹从「必须恰好在这一帧起跑」变成了一个有真实余量的窗口。

### 15.4 炸弹是反站桩工具

重装者的 `m_range` 只有 110 px 而攻击力 18（§6.1），它的圈可以绕开 —— 但只要你**站在**它附近，炸弹就会落到你脚下。设计意图是让它成为 §14.6 那条缺陷的对症药：机器人最严重的毛病是**静止**（55.9% 的帧一动不动），而子弹的飞行只有 0.05–0.1 秒量级，人类来不及反应；炸弹不一样，预警圈画在那里、落点固定、0.4 秒足够读完并走开。它是场上唯一一个**人类和机器人都看得见、也都躲得开**的机制。

**实测：药没有生效，这个期望落空了。** 把 `BOMB_WEIGHT` 拆成 **0 / 1 / 20** 三个对照组跑同一套 96 颗种子（§14.5）。拴区世界里三组的中位倍数都是 6.49×、都是 96/96 跑满、最差都是 3.56×，只有极小的分布差异（空闲帧 55.7% / 55.9% / 56.0%，击杀 23020 / 23002 / 23096）。**拴区解除后重测，连那点差异都没有了：0 与 20 的完整 sweep 输出逐字节相同。** 权重从「完全不躲炸弹」一路调到 20 倍，一格都不动。

**它治错了地方，而这一点现在比当时更清楚。** 当时归因于「静止的根因是拴区阶跃，而机器人静止的那些帧里附近通常根本没有炸弹」—— 那个归因是对的，而拴区阶跃本身随后就随拴区一起消失了（§6.2），静止也随之从 55.9% 掉到 4.3%（§14.6）。**也就是说这条机制在它想治的缺陷已经不存在之后，依然一格都不动** —— 那说明它对机器人行为的实际影响力本来就接近零，与缺陷在不在无关。所以它按**正确性**留下：人类看得见也会躲，忽略它的机器人玩的是另一个更瞎的游戏（§14.1），它不该按修法记账。详见 §14.6。

**不做友伤。** 炸弹只伤玩家。§6 的 AI 和 §14.2 的风险模型都建立在「怪物只伤害玩家」之上，一次会减少场上怪物数量的爆炸是没人预料到的平衡改动。

### 15.5 弹体不是密钥材料

`ProjectileStats` **刻意不进 `GameSnapshot`**，因此不占 `V` 的字节 —— 与药剂（§8.4）同构的理由：飞行中的弹体不是密钥材料，它只通过移动 `V` 已经携带的玩家 / 怪物属性间接影响密钥；而 `V` 定长承载不动一个新窗口（§3.4），加进去会让每个字节的归属随开火抖动。

**弹道路径不消耗任何随机抽样。** 瞄准是确定性的（开火瞬间的目标位置），所以 `s.rng` 的流不会因为多了一次射击而错位 —— 与 `rollDrops` 刻意固定抽样次数（§8.3）是同一条契约。`tests/game-sim.mjs` 里有一条断言专门守着它（「firing spends no randomness at all」：同一个 rng 在「开火」与「不开火」两次运行里被抽样的次数必须完全相等），另有一条守着「同种子逐帧重放弹体的 id / 种类 / 位置」。

### 15.6 机器人只躲炸弹，不躲子弹

`RobotView` 多了一项 `hazards`：只有**飞行中的炸弹**，取它的落点（`bombLanding`）和 `blast + playerRadius` 作为半径，在风险场里按 `damage × BOMB_WEIGHT × CHASE × proximity` 计价。它与怪物项有三处刻意的不同：**没有拴区项**（这一条写在拴区还在的时候；现在整个风险场都没有拴区项了，§6.2），**在半径处硬截断**（圈外一分钱不算，因为爆炸确实只炸圈内），以及**引信不参与**（危险的是那个圈，而不是还有多久落地 —— 这恰好也是画面上能读到的信息）。

三条理由：

1. **子弹不进风险场是诚实，而不是偷懒。** 0.05–0.1 秒的飞行快于人类反应时间；让机器人躲一个人类躲不掉的东西，就是在偷偷放宽 §14.1 的边界。
2. **炸弹的可见性不多于画面。** 预警圈画多久，机器人就看见多久 —— 两者读的是同一个条件（弹体还在飞），圈消失的那一刻它也忘了。
3. **它计入「脚下」的基准分，但不计入承诺门。** 这一条是实测调出来的：`hereRisk`（当时是 `PANIC` / `DISENGAGE` 两个承诺门用的那个）**排除**炸弹，否则一发落在脚下的炸弹在圆心读出 `18 × 3 × 2` = 108（圈边 54），越过当时的 `PANIC` 44，触发整区撤退 —— 对一个「走两步就没事」的东西反应过度；而 `hereForScore`（候选打分用的基准）**包含**它，否则「从炸弹下面走开」会和一个不动的人打平，而平局按规则判给静止。

`BOMB_WEIGHT` 实测是**完全不敏感**的：0 / 1 / 20 三组的完整 sweep 输出逐字节相同（§14.6 有完整数字）。留在 1 的理由是它按炸弹自己的伤害计价 —— 一个能自圆其说的默认值，而不是一个调出来的值。机器的行为不依赖它，正是因为这个量在机器人的活动分布里很少非零。
